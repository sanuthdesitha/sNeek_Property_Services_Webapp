## Section A — Platform Foundation & Cross-Cutting Systems

### A1. Architecture overview

The platform is a single **Next.js 14 App Router** application (`next@14.2.18`) backed by **Prisma + PostgreSQL**, operating on **Australia/Sydney** time for all scheduling. One codebase serves the public marketing site, all API routes, and six authenticated portals: admin (shared with ops-manager), cleaner, client, laundry driver, QA inspector, and maintenance.

Repo layout, in broad strokes:

- `app/` — routes. `app/api/**` holds every API handler; `app/admin`, `app/cleaner`, `app/client`, `app/laundry`, `app/qa`, `app/maintenance` are the **v1 (classic)** portals; `app/(public)` is the marketing site; `app/v2/**` is the **v2 "Estate"** experience with per-role subtrees (`app/v2/admin`, `app/v2/cleaner`, `app/v2/client`, `app/v2/laundry`, `app/v2/qa`, `app/v2/maintenance`), its own themed login (`app/v2/login`), onboarding, and theme layer (`app/v2/estate.css`, `app/v2/_theme-shell.tsx`).
- `components/v2/` — Estate UI, mirrored per role (`admin/`, `cleaner/`, `client/`, `laundry/`, `qa/`, `maintenance/`) plus `ui/` (the `EButton`/`ECard`/etc. primitive kit), `shared/`, `portal/`, and `public/`.
- `lib/` — all domain logic, one folder per concern (`lib/auth`, `lib/notifications`, `lib/ops`, `lib/gps`, `lib/finance`, `lib/quotes`, `lib/accountability`, `lib/laundry`, `lib/ical`, `lib/xero`, …). API routes are thin; behaviour lives here.
- `prisma/schema.prisma` + `prisma/migrations/` — the data model. `workers/` holds the optional dedicated pg-boss worker; the web process carries a full fallback scheduler (A7).
- `mobile-app/` — an Expo companion app (push tokens registered via `UserPushDevice`); `sneek-nextgen/` is a **separate, self-contained prototype workspace** (own `package.json`, own `prisma/`) for a future SaaS rebuild — it shares no code with the live app.

**v1 vs v2.** Both versions are fully routable forever; all new work targets v2 (v1 is legacy). The v2 pages generally call the *same* API routes as v1 — Estate is a re-skin plus workflow upgrades on a shared backend. Which version people *land in* is the "default look" system:

- `AppSettings.defaultPortalVersion` (`"v1" | "v2"`, default `"v1"` in `lib/settings.ts`) is the house default.
- A **personal override cookie** `sneek.portal-version` (90-day TTL) always beats the house default. Appending `?look=v2` (or `?look=v1`) to any URL sets it: `middleware.ts` catches the param, drops it, sets the cookie and redirects — plain-anchor switch links that work without JavaScript.
- `lib/portal-version.ts` is the pure, edge-safe half: `effectivePortalVersion(houseDefault, override)`, `portalRootIn()`, `versionOfPath()`. The critical design decision (documented in its header comment): **only portal roots are redirected** (`/admin ↔ /v2/admin` etc.). Deep links are never rewritten, so bookmarks/emailed links keep working and a page that exists in only one version stays reachable. `portalRootIn()` returns `null` when the path is already in the right version, which is what makes redirect loops impossible. The stored default lives via `lib/portal-version-store.ts` and rides to the edge middleware on the `/api/auth/validate-session` response (middleware cannot read Prisma).

### A2. Authentication & roles

Auth is **NextAuth with JWT sessions** (`lib/auth/auth-options.ts`), credentials-based (bcrypt password hashes on `User.passwordHash`). The `Role` enum (`prisma/schema.prisma`) is: `ADMIN`, `OPS_MANAGER`, `QA_INSPECTOR`, `CLEANER`, `CLIENT`, `LAUNDRY`, `MAINTENANCE`.

Role resolution deliberately does **not** trust the JWT alone — three layers re-check the database:

1. **Edge middleware** (`middleware.ts`) — the single choke point (matcher excludes only static assets). For page requests it calls `/api/auth/validate-session` (with the request cookies) to confirm the user is still active, pick up the *live* role, and learn `requiresPasswordReset` / `requiresOnboarding` / the house look. A fetch failure returns `"indeterminate"` and fails open to v1 rather than bouncing users. It then enforces the portal gates: `/admin` requires ADMIN or OPS_MANAGER (with `/admin/settings/pricebook` and `/admin/settings/pay-rates` further restricted to ADMIN); `/cleaner`, `/client`, `/laundry` require their exact role; `/maintenance` allows the worker plus admin/ops. For `/v2/*`, unauthenticated traffic is sent to `/v2/login` (the Estate-themed login — same NextAuth credentials/2FA, shared session cookie, different landing), `/v2` root goes to the role's home, and each `/v2/<portal>` subtree is checked against the owning role (admin/ops pass everywhere). The middleware also stamps security headers (CSP allowing Google Maps and blob: PDF previews, `X-Frame-Options: DENY`, etc.).
2. **`requireSession()` / `requireRole()`** (`lib/auth/session.ts`) — every API handler re-reads the `User` row, refuses inactive accounts, and overwrites `session.user.role` with the DB role. This is also where impersonation is layered in (A3).
3. **Login-time protections** — `lib/auth/login-lockout.ts` (attempt lockout), `lib/auth/temp-password.ts` / force-password-reset routing, invitation and registration OTP flows (`lib/auth/invitations.ts`, `registration-otp.ts`).

**2FA** (`lib/auth/twofactor.ts`) is per-user opt-in with two methods (`User.twoFactorMethod`): **TOTP** (otplib, secret in `User.totpSecret`, issuer "sNeek Ops") and **email one-time codes** (via `lib/auth/otp.ts`). Ten single-use **backup codes** are stored sha256-hashed in `User.twoFactorBackupCodes`. The flow's shape matters: the 2FA check runs *before* NextAuth `signIn` and mints a short-lived HMAC proof cookie (`sneek_2fa_ok`, 10 min); `authorize()` then only validates that cookie, so no second factor logic lives inside NextAuth. **Remember-device** issues a 30-day trusted-device token (`sneek_td`). Recovery lives at `/recover-2fa` (`lib/auth/recovery.ts`).

**WebAuthn / passkeys** exist too (`lib/auth/webauthn.ts`, `@simplewebauthn/server`): platform-biometric sign-in with challenges stashed in short-lived signed httpOnly cookies (`sneek-wa-reg` / `sneek-wa-auth`, 5-min TTL, single-use), rpID derived from the request hostname so localhost and production both verify.

### A3. Impersonation — admin "Test as"

An admin can view the app as any non-admin user. The design (thoroughly documented in `lib/auth/impersonation.ts`) rests on **not touching the real session**: because both middleware and `requireSession()` re-read the DB role, spoofing the JWT wouldn't even work. Instead a second, **NextAuth-signed cookie** `sneek.test-as` carries an `ImpersonationTicket` (`actorId`, `targetId`, `targetRole`, `mode`, `startedAt`) with its own **1-hour TTL**. Consequences: sign-out/expiry/deactivation behave normally, dropping the cookie is an instant complete revert, and the audit trail always names the real admin.

- **Edge half** (`lib/auth/impersonation.ts`, importable from middleware): verifies signature and shape; `isReadOnlySafeMethod()` defines GET/HEAD/OPTIONS as safe. `middleware.ts` enforces **READ_ONLY mode** at the choke point: any non-safe method while a READ_ONLY ticket is present is refused with a 403 (`IMPERSONATION_READ_ONLY`) — except the `/api/admin/impersonate` endpoints themselves, or you could never exit. READ_ONLY is the default; FULL exists for end-to-end testing, is chosen explicitly, and is recorded in the audit row.
- **Server half** (`lib/auth/impersonation-server.ts`): a valid signature is *not* sufficient authority. On every request `resolveImpersonation()` re-checks live rows: the ticket must belong to this session (a leaked cookie is useless elsewhere), the actor must still be an **active ADMIN** (OPS_MANAGER never qualifies; demotion revokes instantly), and the target must exist, be active, and **not be an admin** — so impersonation can only move sideways or down, never escalate.
- `requireSession()` swaps `session.user` for the target (so every downstream query "just works") and attaches `session.impersonation` for the warning banner. **`requireRealSession()`** ignores impersonation entirely and is used wherever the human at the keyboard must be attributed — including the impersonate endpoints themselves (otherwise an impersonated CLEANER session could never pass the ADMIN check needed to stop).
- **Unlock gate (2026-07).** Being an admin is no longer enough: the Test-as console is password/PIN-locked. `lib/auth/test-as-unlock.ts` mints a **15-minute HMAC proof cookie** `sneek.test-as-unlock` (`<userId>.<expiryMs>.<hmac>`, same shape as the 2FA proof) after the admin re-enters their credentials via `POST /api/admin/test-as/unlock` (which uses the existing `verifySensitiveAction` bcrypt check and is rate-limited to **5 attempts per 15 minutes** per admin). Crucially it is a *cookie*, not sessionStorage, so `POST /api/admin/impersonate` (`app/api/admin/impersonate/route.ts`) can enforce it server-side — a direct POST without a fresh unlock gets a 403 `TEST_AS_LOCKED` regardless of what the browser claims. Start and stop are both audited (`IMPERSONATE_START` written *before* the cookie is issued, so a crash can't produce an unrecorded impersonation; `IMPERSONATE_STOP` records duration).

### A4. Settings system

All tunable behaviour lives in one JSON blob per key in the `AppSetting` table (`key` / `value Json`), read through **`lib/settings.ts`** (~72 KB — the platform's control panel). The pattern is uniform: every settings group has a **TypeScript interface**, a **default**, and a **sanitizer** that coerces whatever is stored back into shape, so a partial or legacy row can never crash a read. `getAppSettings()` merges DB over defaults; admin pages under `/v2/admin/settings/**` write back.

Notable groups on the `AppSettings` interface:

- **Identity/branding**: `companyName`, `companyPhone`, `logoUrl` / `logoDarkBgUrl` / `reportLogoUrl`, `timezone`, `portalTheme`, `websiteContent` (the whole public site's copy), `defaultPortalVersion` (A1).
- **`accountability`** — the cleaner quality system: `scoring` (minor/major/critical deductions, score floor, band thresholds), `bonuses` (quality-streak and monthly-ranking amounts and eligibility minima), `rectification` (time-banded deduction amounts, manager-review threshold, rework-offer TTL), admin-defined `issueCategories`, pattern-detection windows, `requireJobStartConfirmation`, `selfInspectionBlocksSubmit`.
- **`autoClockOut`** — `enabled`, `stopAtEstimatedDuration` (legacy cut-off, default false — the timer runs past the estimate), `graceMinutes`, `fallbackAtMidnight`, `maxJobLengthHours`, and **`geofenceExit` (2026-07, default true)** — the kill-switch for GPS departure auto clock-out (A8).
- **`finalCheckup` (2026-07)** — the pre-submit acknowledgement dialog for cleaners: `enabled` + admin-authored `items[]` (`FinalCheckupItem`: title, detail, `referenceImageKeys` uploaded via `/api/uploads/direct` folder `final-checkup`, and `appliesTo` job types).
- **`qaPay` (2026-07)** — global defaults for what a QA inspection pays: `defaultMode` (`FIXED | HOURLY | NONE`), `defaultFixedAmount`, `defaultHourlyRate`, `defaultHoursPerInspection`. Resolution order is assignment override (`QaAssignment.payMode/payAmount/...`) → inspector's `User.hourlyRate` → these settings (`lib/finance/qa-pay.ts`).
- **Visibility toggles** — `clientPortalVisibility` (some two dozen flags controlling what clients can see/do, including **`showLiveProgress` (2026-07, ships OFF)** — live mid-clean checklist progress on the client job page), `cleanerPortalVisibility`, `laundryPortalVisibility`.
- **`laundryOperations`** — pickup cutoff/default times, `maxOutdoorDays`, fast-return behaviour when no next clean exists.
- **Automation groups** — `sla`, `caseAutomation` (severity-gated auto case opening with dedupe and auto-resolve), `recurringJobs`, `autoAssign`, `routeOptimization`, `qaAutomation`, `scheduledNotifications`, `notificationDefaults`, `emailAutomation`, `notificationAudienceControls`, `evidenceStamp` (date/time format burned into photos), `pricing` (cleaner cost / rack rate / margin floor), `pricingVariables`, `invoicing` (bank details, ABN, terms), `emailTemplates` / `notificationTemplates`.

**Integrations are settings-first with env fallback.** Credentials for every external service live in the `AppSetting` row `integrationCredentials`, edited at `app/api/admin/integrations/credentials/route.ts`: Resend, Twilio, Cellcast, S3/R2, Stripe, Square, PayPal, Xero, Google Maps, VAPID web-push keys, bootstrap admin. Consumers (e.g. `lib/s3.ts`, `lib/xero/client.ts`, `lib/notifications/web-push.ts`, `lib/maps/server-key.ts`) prefer the DB value and fall back to the corresponding env var, so a fresh deployment works from env alone and the UI can take over later. Sensitive keys are never returned unmasked (masked round-trip: bullet-containing values mean "unchanged"), changing or *clearing* any `SENSITIVE_KEYS` entry requires the admin to **re-enter their account password**, changes are audited with secrets redacted, and the truly system-critical values (`DATABASE_URL`, `NEXTAUTH_SECRET`) are env-only and shown read-only.

### A5. Notifications

The in-app feed is the `Notification` model (`userId`, `jobId`, `channel` PUSH/EMAIL/SMS, subject/body, status, plus `externalId`/`deliveryStatus` for provider webhook matching; indexed on `(userId, channel, createdAt)` because the SSE stream polls it per connected user).

The **single chokepoint** is `deliverNotificationToRecipients()` in `lib/notifications/delivery.ts`. For each (deduped) recipient it resolves three gates per channel — the per-user **category preference** (`lib/notifications/preferences.ts`; categories are `account`, `jobs`, `laundry`, `cases`, `reports`, `quotes`, `shopping`, `billing`, `approvals`, `ical`), the **audience-level controls** (`lib/notifications/audience-controls.ts`: global + per-audience email/sms/push switches that override user opt-ins), and for email the **email-automation kind switch** (`lib/notifications/email-kinds.ts`; each send carries an `EmailAutoKind` so one toggle no longer silences the whole pipeline). Then:

- **Web**: writes the feed row *and* fires real browser **Web Push** (`lib/notifications/web-push.ts`, VAPID via `web-push`; keys resolved settings-first — `getServerVapidPublicKey()` reads `integrationCredentials` then env — and served to the browser via `/api/public/push-config`; no-ops gracefully when unconfigured). Deep links fall back to a role-appropriate href from `lib/notifications/feed.ts`.
- **Mobile push**: the separate Expo channel (`lib/notifications/mobile-push.ts`) sends to `UserPushDevice` tokens through the Expo push API.
- **Email**: `lib/notifications/email.ts` sends through **Resend**, wrapping non-full-document HTML in the branded shell (`wrapEmailHtml` from `lib/email-templates.ts`) and absolutizing inline links. A **suppression list** (`lib/email/suppression.ts`: hard/soft bounces, complaints, unsubscribes) blocks marketing sends; `transactional: true` (password reset, OTP, invoices) bypasses it, and `critical: true` additionally bypasses audience gating so auth emails can never be silenced. Every send is logged back as a Notification row with the Resend message id.
- **SMS**: `lib/notifications/sms.ts` supports **Twilio or Cellcast** (chosen by `AppSettings.smsProvider`), normalizes AU numbers (04… → +61…), and clamps bodies to 459 chars (~3 GSM segments) to bound per-message billing.

**The email gate, narrowest-last (2026-08).** `sendEmailDetailed` now applies four decisions in order, each narrower than the one before: the **master** switch, the **kind** switch, a **per-audience override of a kind** (`EmailAutomationSettings.audienceKinds` — "cleaners don't need inventory mail" without also silencing the ops manager who does), and finally the **person's own preference** (`UserEmailPreference` rows, plus `User.allEmailOff` for "stop emailing me entirely" — one flag rather than a row per kind, so it keeps working when new kinds are added later). Every link fails **open**: a missing map, audience, kind or preference row means allowed, so a switch can only ever remove mail someone chose to remove, never withhold it by omission. `critical: true` (auth, OTP, 2FA) bypasses all of it, or a person could lock themselves out of their own account by ticking a box. The audience/preference checks run **per recipient**, so a multi-recipient send now drops only the people who opted out instead of all-or-nothing. A caller-supplied `audience` still skips the user lookup, but only for a single recipient on a **kindless** send — otherwise the row is needed to answer the per-person question. Migration: `20260803000000_email_preferences`. Regression: `tests/lib/email-audience-kinds.test.ts`.

Alongside that, automatic sends that carried **no `kind`** were backfilled — job assignment and bulk-assign digests, pay-adjustment decisions and requests, workforce/document emails, QA client invites, lost-and-found and client-approval alerts, public quote responses. Those sends were unswitchable, which is why the `pay_adjustment` and `workforce_update` toggles existed in the admin UI while controlling nothing. Admin-*clicked* sends (quote send, invoice send, report share, PO email, test notification, invitations, OTP) stay deliberately kindless: they are a person pressing send, not the system deciding to.

**Who decides, and who is told (2026-08, wave 4 part 2).** The gate above is now editable rather than API-only: the comms control center carries an audience x kind grid (a cell only ever stores `false`, so unticking removes mail someone chose to remove and a kind added later arrives allowed for every group), and a per-person section with select-all, "turn this type off/on for the selected people" and "all email off" — writing `UserEmailPreference` rows and `User.allEmailOff` through `POST /api/admin/users/email-preferences/bulk`. That route only touches the kinds it is given, so setting one preference cannot silently reset the others, and an "allowed" choice deletes the row rather than storing `true`. The settings PATCH schema had to learn `audienceKinds` explicitly — zod strips unknown keys, so without it the grid would have appeared to save and come back empty.

**Three changes that used to happen in silence (2026-08).** `job_task_added`: `syncAdminJobTasks` added work to someone's job and notified nobody, so a cleaner who had already read their brief arrived without the extra task — it now tells the job's current cleaners about NEWLY created tasks only (renaming one is not worth a 6am push), skipping finished jobs, and a notification failure can never undo the tasks that saved. `special_note_changed`: the admin job PATCH tested the *payload* (`if (body.internalNotes ?? "").trim()`), so re-saving an unchanged job announced a change that hadn't happened while CLEARING a note registered nothing at all — the case that matters most, since the cleaner keeps following a withdrawn instruction. It now diffs the old and new note and puts the text in the summary. `timing_rule_changed`: a job edit that is ONLY the turnaround rules, or ONLY the note, now carries its own kind, while a mixed edit stays on the general job-update kind so silencing note changes can never silence a reschedule.

**Reassignment is now a decision, not a side effect (2026-08).** Replacing a job's primary cleaner used to fire the `CLEANER_ASSIGNED` "meet your cleaner" email again — stating a change as though it were the original news, before anyone had decided whether to explain it. A new `CLEANER_REASSIGNED` stage leads with the change, names the replacement, carries an optional reason and reassures that the time and access arrangements are unchanged. The assign route no longer auto-sends in that case: it returns the rendered draft, and the shared assign modal (used by the job page, the board and the calendar alike) opens a confirm dialog with an editable subject and body plus a plain "Don't send". `sendLifecycleEmail` gained an `override`, because offering an edit and then sending the template anyway would be worse than never offering it. A FIRST assignment is uncontroversial and still sends automatically.

**Pay-adjustment notifications (2026-07)** — `lib/notifications/pay-adjustments.ts` is a dedicated module for money changes: a `CleanerPayAdjustment` moving to APPROVED (or an approved one being edited/reversed), and the QA-rework transfer path that writes an already-approved deduction against the cleaner and credit to the inspector, now notify both parties about the *money* through the full chokepoint (web push + email + SMS, preference-aware). The helpers fire only on a real state transition, so retried requests cannot double-notify. (Legacy note: two route-local `createRoleNotifications()` helpers still exist in the laundry status routes, e.g. `app/api/laundry/[taskId]/status/route.ts`, fanning feed rows out to whole roles — pre-chokepoint code that newer work no longer copies.)

### A6. Uploads & media

Object storage is **S3-compatible (Cloudflare R2)** via `lib/s3.ts` — an `aws-sdk` v2 client, settings-first (A4) with a 60-second credential cache, plus `publicUrl()` (CDN base from `S3_PUBLIC_BASE_URL`) and presigned GET/PUT helpers.

**Uploads died because the page reloaded itself (2026-08).** `next.config.mjs` had `reloadOnOnline: true` — a `@ducanh2912/next-pwa` option (its default) that injects `addEventListener("online", () => location.reload())` into the service-worker register script. Any momentary connectivity blip therefore hard-reloaded the page, and an upload is the longest, heaviest network operation in the app, so it was the thing most likely to be in flight when that happened. The browser aborted the POST and the server logged `Error: aborted … ECONNRESET` from `abortIncoming` — a body that started arriving and then stopped. It presented as "I pick a photo, press OK, the page refreshes and nothing uploads", looked account-specific because it tracks the person's *network* rather than their identity, and never reproduced locally because the service worker is disabled in development. Now `false`: reloading on reconnect discards whatever the user was in the middle of, and refreshing data after a genuine absence is `components/shared/return-sync.tsx`'s job — which itself now excludes file-dialog round trips, since opening a picker hides the tab and used to be mistaken for the user leaving.

**ROOT CAUSE FOUND — the gallery path still decoded at full resolution (2026-08).** The `decodeScaled` fix below covered only `stampImage` (camera shots). Gallery picks — the main path in cleaning-report submission — went through `compressImage` → `browser-image-compression`, which decodes the photo at FULL resolution in a worker before shrinking it: 190–430 MB of RGBA for a modern 48–108 MP phone photo, allocated the instant the picker returns. Android answers by killing the tab, which reloads — the "quick flash, nothing uploaded" report. This also explains every observed asymmetry: cleaners only (only evidence flows compress client-side), the laundry portal fine on the same phone (no image processing), unreproducible on desktop (memory headroom). Fixed at the chokepoint: `compressImage` now uses `downscaleImage` (new export in `stamp.ts`, same `createImageBitmap`-scaled decode as `stampImage`, peak memory ≈ the 2400 px working bitmap ≈ 23 MB) with the library kept only as a fallback for files the scaled decoder refuses. Every caller — v1 + v2 cleaner, QA, upload-dropzone — is covered with no call-site changes.

**Decode at the target size, never at full resolution (2026-08).** `stampImage` (`lib/uploads/stamp.ts`) used to load the photo through `new Image()`, which materialises the entire bitmap before anything is drawn — a 48MP phone photo is roughly 190MB of RGBA, allocated the instant the file picker returns. Desktops absorbed it; phones did not. iOS Safari and Android Chrome answer that spike by discarding the tab and reloading, which cleaners experienced as "I picked a photo, the page went back to the start, and nothing uploaded" — on phones and the installed app only, and on *every* upload in the portal, because every evidence photo goes through this function. It now decodes with `createImageBitmap(file, { resizeWidth, resizeHeight, resizeQuality })` so the browser produces the reduced image directly, and releases the source (`bitmap.close()`) as soon as it is drawn rather than holding it for the rest of the stamp. Browsers without `createImageBitmap`, and files it rejects (some HEIC paths), fall back to the previous element decode.

**Upload watchdog — removed (2026-08-04).** While the "picking a photo refreshes the page" bug was open, a temporary diagnostic (`components/shared/upload-watchdog.tsx` + `POST /api/debug/upload-watchdog`) instrumented every teardown shape an upload can die by — in-flight beacons, file-pick and picker-open sessionStorage crumbs read on the next load, and app-remount reports. It was deleted once the root cause was confirmed fixed (the workspace-refresh unmount; see the Change Log). Two portable lessons survive it: `location.reload` is an unforgeable, non-configurable property (`defineProperty` throws, so no wrapper can ever capture the caller's stack), and page-level `window.fetch` instrumentation must install once at module scope — two wrappers that each restore "the original" on unmount clobber each other, and a diagnostic that can uninstall itself reports nothing while looking exactly like proof that nothing happened.

The workhorse is **`POST /api/uploads/direct`** (`app/api/uploads/direct/route.ts`): a server-side upload that accepts multipart form data, validates folder + content type (`lib/uploads/validate.ts`), enforces 20 MB for images and ~150 MB for videos, transcodes/compresses videos to MP4 on the server (`lib/media/video-compression.ts`, keeping the original when compression doesn't help), and puts the object under `<folder>/<userId>/<uuid>.<ext>`. **Why server-side rather than presigned browser PUTs**: the presign path (`/api/uploads/presign`) *silently did nothing in production* — the bucket has no CORS configuration for browser PUTs, so uploads appeared to succeed and dropped the bytes. That failure and the switch to the direct route are recorded in comments at each former call site (e.g. `components/v2/client/quote-wizard.tsx`, `components/v2/admin/forms/builder/theme-editor.tsx`, `components/forms/reference-media-editor.tsx`). The presign and multipart routes still exist for legacy/large-file paths (`lib/uploads/multipart-client.ts`).

Reads go through **`GET /api/uploads/access`** (`app/api/uploads/access/route.ts`): session-checked, key-validated (no `..`), role-gated, returning a time-limited presigned GET — so evidence is never publicly enumerable. Cleaner evidence photos are **stamped client-side before upload** (`lib/uploads/stamp.ts`: timestamp, weekday, logo burned into the image per `AppSettings.evidenceStamp`), and form evidence is persisted as **`SubmissionMedia`** rows (per submission + field: `s3Key`, `url`, optional `originalS3Key` and `annotatedS3Key`/`annotationData` so annotation never destroys the original).

**The unauthenticated failure log (2026-08).** `POST /api/admin/system/uploads/log-failure` records client-side upload failures and is deliberately **unauthenticated** — an upload can fail before or independently of a session (an expired cookie, a guest form), and capturing exactly those is the point — which made it the only unauthenticated write handler on the surface, reachable from the internet. It accepted unbounded strings and a `z.record(z.any())` `context`, so a single request could push megabytes of arbitrarily nested JSON into a row, and `await req.json()` sat outside any try, so a malformed body rejected out of the handler as an unhandled 500. It now caps every field, restricts `context` to scalars under both a key-count and a serialised-size limit, rate-limits per IP (`lib/security/rate-limit.ts`), and answers 400 on an unparseable body. The rate limit is defence-in-depth only and is documented as such at the call site: `getClientIp` trusts the first `x-forwarded-for` hop, which a caller can spoof, and the limiter is per-process rather than shared — the field caps are the real bound on what any one request can cost.

### A8. GPS & Live Ops

**Ping pipeline.** While a job is active, the cleaner's browser runs `useGpsTracker` (`lib/gps/client.tsx`): high-accuracy `watchPosition` fixes are queued in IndexedDB and flushed to `/api/cleaner/location/ping` every **30 s** (immediately on `online`), with a **45 s heartbeat** that re-emits the last fix when stationary — `watchPosition` only fires on movement, so without it a cleaner standing still would go stale on the admin map. Driving mode (`components/v2/cleaner/driving-mode.tsx`) is a separate, faster loop: while a stop is EN_ROUTE it heartbeats `/api/cleaner/jobs/[id]/location-ping` every **12 s**, recomputing the ETA (same endpoints as v1: start/pause/resume/mark-delayed/arrived/stop-driving). Pings land in `CleanerLocationPing` (indexed by job+time and user+time; 7-day retention via the scheduler).

**Geofence.** `lib/gps/geofence.ts` (`checkGeofenceForPing`) evaluates each fresh ping against the active job's property coordinates with the default **75 m radius** (`DEFAULT_GEOFENCE_RADIUS_M` in `lib/gps/distance.ts`). First inside-fence ping stamps `Job.arrivedAt`; an inside ping on a job marked departed clears `Job.departedAt` (re-entry — resuming the job stays manual). An outside ping on a job the cleaner had reached only *signals* a possible departure.

**Departure detection + auto clock-out (2026-07).** Confirmation is deliberately conservative and pure (`lib/gps/departure.ts`, unit-tested): a departure is confirmed only when the **3 most recent accurate pings** (accuracy ≤ 60 m; null counts as accurate for older clients) are **all outside the fence + 25 m hysteresis** (>100 m for the default fence) **and span ≥ 2 minutes**. Absence of pings never confirms (a dead phone is not a departure). The consumer, `lib/gps/departure-clockout.ts` (`handleGeofenceDeparture`, called after ping ingestion and never allowed to fail a ping), stamps `Job.departedAt` (added by migration `20260725090000_job_departed_at`) regardless of settings — the truth powers the labels — then, gated by the **`autoClockOut.geofenceExit` kill-switch** and only for an IN_PROGRESS job with an open timer: closes the `TimeLog` (annotated "Auto clocked out — left job site (GPS)"), moves the job to **PAUSED** only when no teammate still has an open timer and never drags a submitted/completed job backward, writes an `AUTO_CLOCK_OUT` audit row with the distance, and notifies the cleaner plus all admins (best-effort).

**Truthful live status (2026-07).** `lib/ops/live-status.ts` is one pure derivation shared by the API route, admin dashboard, and both map components — replacing the old logic that called anyone with an open timer ON_SITE regardless of GPS. States: `ON_SITE` (open timer + fresh ping ≤ 3 min + inside fence, or no geofence to judge against — labelled "On job (no geofence)"), `OFF_SITE` ("Clocked in · off site"), `NO_SIGNAL` ("Clocked in · no signal 12 min ago"), `PAUSED` (shows "Left site X ago" when departed), `LEFT_SITE`, `EN_ROUTE`, `IDLE`, with shared relative-age formatting so server and client labels match.

**On-site check-in gate (2026-08).** Until this wave GPS distance was *computed, stored and never acted on*: a cleaner check-in 40 km from the property returned `200 OK` with a friendly "Check-in recorded 40219m from the property", and the v2 workspace caught a geolocation **permission denial** into a blue info toast and clocked in anyway — so "location required" was advisory in both directions. Now:

- `lib/gps/distance.ts` gains `classifyCheckInLocation()` → `ON_SITE | OFF_SITE | UNRELIABLE` against `ON_SITE_RADIUS_M = 150` (`resolveOnSiteRadius()` honours the new per-property `Property.geofenceRadiusM` override). The check-in radius is deliberately **wider than the 75 m passive geofence**: the geofence answers "has this phone left?" from a debounced ping stream, while this answers "is this person here?" from one fix taken indoors, in a stairwell or in a basement. A fix coarser than `UNRELIABLE_ACCURACY_M = 200` is judged **neither way** — a ±3 km fix is not evidence of presence or of absence, and accusing someone standing in the kitchen destroys trust in the gate.
- **Off-site starts require a coded reason.** `lib/gps/off-site-reasons.ts` defines 8 codes (`POOR_SIGNAL`, `UNDERGROUND_PARKING`, `LARGE_COMPLEX`, `WRONG_PIN`, `KEY_PICKUP`, `STARTED_EARLY_ELSEWHERE`, `ON_THE_WAY`, `OTHER`), each flagged `claimsOnSite` so admin wording distinguishes a data-quality problem from a genuine off-site start. Codes, not the existing free-text note, because "no signal"/"couldn't get gps"/"phone wouldn't locate me" is one fact written three ways and prose cannot be counted. Both `POST /api/cleaner/jobs/[id]/gps-checkin` and `POST /api/qa/jobs/[id]/checkin` return **409 `OFF_SITE_REASON_REQUIRED`** (with distance, radius and the reason list) and record nothing until a valid code arrives; it is then stored on `Job.gpsCheckInReasonCode` / `QaAssignment.checkInReasonCode`, pushed to admins, and written as a `GPS_CHECKIN_OFF_SITE` audit row. Admin job details renders it beside the check-in distance.
- **GPS permission is hard-required to clock in** (`job-workspace.tsx`): a denial or unavailable fix blocks the clock-in and opens a dialog with per-platform re-enable instructions; the server's `lowAccuracy` flag (previously discarded by the client) is surfaced to the cleaner.
- **`arrivedAt` is stamped by an on-site check-in.** It was previously set *only* by an inside-fence ping, and `lib/gps/geofence.ts` refuses to evaluate departure until it is set — so a cleaner whose phone never produced an accurate inside-fence ping had `arrivedAt = null` forever and **auto clock-out could never fire for them**. Migration: `20260801020000_on_site_check_in_gate`.

**Map rendering.** The Estate ops map (`components/v2/admin/ops/estate-ops-map.tsx`) plots cleaners as filled dots colour-tiered by ping staleness; a cleaner whose position is only the *property's* coordinates (no GPS fix) renders as a **hollow marker** so it cannot be mistaken for a live dot, and a cleaner with no plottable position at all appears only in the side panel, never as a pin.

### A9. Audit logging & approval history

**`AuditLog`** is the universal trail: `userId` (actor), optional `jobId`, free-form `action` verb, `entity` + `entityId`, `before`/`after` JSON snapshots, `ipAddress`, indexed on `createdAt`, `(entity, entityId)`, `(userId, createdAt)`, and `jobId`. Security-sensitive flows write it directly (impersonation start/stop, integration-credential changes with secrets redacted, auto clock-outs, pay reviews, self-code-level actions), and the admin activity viewer reads it.

**Approval-decision history (2026-07)** is a *convention on top of AuditLog*, not a new table — `lib/admin/approval-history.ts` documents why: AuditLog already carries and indexes every needed field; a parallel table would drift from the audit rows routes already write. The pieces:

- `lib/admin/approval-history-write.ts` — `recordApprovalDecision()`, the **one writer** for every Approval Center decision across all fifteen queues (`continuations`, `timingRequests`, `payAdjustments`, `timeAdjustments`, `clientApprovals`, `flaggedLaundry`, `rescheduleRequests`, `clientRequests`, `qaReworkTransfers`, `qaOutcomes`, `skipRequests`, `rectificationAdjustments`, `bonusProposals`, `falseConfirmations`, `managementReviews`). Every approve/decline/dismiss/reverse/edit/delete lands as `action = "APPROVAL_DECISION"` with a consistently shaped `after` payload (queue, decision, label, amount/value, note, subject, from/to status), so a single indexed query serves the whole History tab. Fire-and-forget by contract: a lost history row is a reporting gap; a rolled-back approval because logging hiccuped would be a money bug.
- `lib/admin/approval-history.ts` — the pure half: the payload contract and parser, plus **`approvalCapabilities()`**, the single source of truth for what a decided item may still have done to it. A verb is enabled only when a server route implements it end-to-end; per-item guards stack on top — **settled money** (already in a payroll run or on a cleaner invoice) is fully immutable with the verbatim `SETTLED_IMMUTABLE_REASON` used in both the UI and the 409 responses; APPROVED rows can't be deleted without reversing first. The UI renders from the same map the routes enforce, so no button the server would refuse is ever offered.

## Section B — Jobs lifecycle, scheduling, forms & the cleaner portal

This section covers the operational heart of the platform: how a cleaning job is born (manually or from an Airbnb iCal feed), how it moves through its status ladder, how the per-property checklist becomes the form the cleaner fills in, and the five-stage v2 cleaner portal that executes it end-to-end. All work targets the v2 (Estate) portals; v1 remains as legacy parity reference only.

### B1. Job model & lifecycle

#### The Job record

`Job` (in `prisma/schema.prisma`, ~line 1187) is the largest model in the system. Its core identity is `jobNumber` (unique, human-facing), `propertyId`, an optional one-to-one `reservationId` (for iCal-driven turnovers), a `jobType`, and a `status`. Around that core the row carries scheduling, GPS/presence, rework, skip, priority and payment-locking state, plus relations out to assignments, time logs, form submissions, QA reviews, laundry, invoicing and reporting.

**Job types** (`JobType` enum): `AIRBNB_TURNOVER` is the flagship type (the only one that gets laundry, reservations and same-day check-in priority). The rest are one-off/recurring service types: `DEEP_CLEAN`, `END_OF_LEASE`, `MOVE_IN_CLEAN`, `GENERAL_CLEAN`, `POST_CONSTRUCTION`, `PRESSURE_WASH`, `WINDOW_CLEAN`, `LAWN_MOWING`, `SPECIAL_CLEAN`, `COMMERCIAL_RECURRING`, `CARPET_STEAM_CLEAN`, `MOLD_TREATMENT`, `UPHOLSTERY_CLEANING`, `TILE_GROUT_CLEANING`, `GUTTER_CLEANING`, `SPRING_CLEANING`. Note that a **rework** job is *not* a job type — it is a normal `Job` (usually an `AIRBNB_TURNOVER`) with `isRework: true` plus the rework block (`reworkOfJobId`, `reworkReason`, `reworkAreas` JSON of `{id,label,note,photoKeys}`, `reworkPayAmount`, `reworkPayeeCleanerId`, `reworkDeductFromCleanerId`, `reworkSourceReviewId`). The pay rule is documented on the model: the same cleaner redoing their own failed clean earns nothing; a different cleaner is paid `reworkPayAmount` and that amount is deducted from the original cleaner.

**Status ladder** (`JobStatus` enum): `UNASSIGNED → OFFERED → ASSIGNED → EN_ROUTE → IN_PROGRESS → PAUSED → WAITING_CONTINUATION_APPROVAL → SUBMITTED → QA_REVIEW → COMPLETED → INVOICED`. In practice:

- `UNASSIGNED/OFFERED/ASSIGNED` are the pre-start dispatch states (`PRE_START_JOB_STATUSES` in `lib/jobs/job-reset.ts`).
- `EN_ROUTE` is set when a cleaner starts driving mode; a sweep (`lib/ops/stale-en-route.ts`) reverts jobs abandoned in `EN_ROUTE` for 6h back to `ASSIGNED`.
- `IN_PROGRESS`/`PAUSED` are the on-site states; `WAITING_CONTINUATION_APPROVAL` parks a job whose pause/continue request needs an admin decision (`lib/jobs/continuation-requests.ts`) — the submit route refuses to accept a submission while such a request is pending.
- `SUBMITTED → QA_REVIEW → COMPLETED → INVOICED` are the locked, read-only states from the cleaner's perspective. `completedAt` is stamped on QA pass (and is admin-editable) and drives which payroll/invoice period the job falls into.

**Assignments** are many-per-job: `JobAssignment` rows (unique per `jobId+userId`) carry `isPrimary`, the `payRate` frozen at assignment time, and an offer/response state machine (`JobAssignmentResponseStatus`: `PENDING → ACCEPTED / DECLINED / TRANSFERRED`, with `respondedAt`, `responseNote`, `transferredFromUserId`). Removal is soft (`removedAt`), so history is preserved. Multi-cleaner teams are first-class — see the team-state gates in B5.

**Scheduling fields**: `scheduledDate` is a UTC start-of-day "date key"; `startTime`/`endTime`/`dueTime` are `HH:mm` strings in property-local (Sydney) time; `estimatedHours` (backed by the property's `assignedCleaningHours`/`cleaningDurationMinutes`) is the expected clean length that clock rules and accountability read; `actualHours` is derived from time logs.

**Priority**: `priorityBucket` (1–4) plus a human `priorityReason`, computed by `classifySameDayCheckinPriority` in `lib/jobs/priority.ts` from the same-day check-in time: check-in ≤ 12:30 → bucket 1 ("Early check-in due by …"), ≤ 15:00 → bucket 2, later same-day → bucket 3, no same-day check-in → bucket 4. `compareJobsByPriority` sorts date → bucket → dueTime → startTime → property name and is used by dispatch/list surfaces.

**Job meta in `internalNotes`**: rather than adding a column per feature, structured per-job metadata is serialized as versioned JSON into `Job.internalNotes` and parsed everywhere through `parseJobInternalNotes` / `serializeJobInternalNotes` in `lib/jobs/meta.ts`. The `JobMeta` envelope holds: free-text internal note, `isDraft`, tags (including internal `rework-of:<id>` tags), reference attachments, admin special-request tasks, the **early check-in / late checkout timing rules** (see B3), per-cleaner transport allowances and custom payouts, commercial `serviceContext`, the iCal-derived `reservationContext` (guest name/code/contact, party sizes, check-in/out local times, geo), quote-carried `additionals` + reference images, and the job-start `startConfirmation` record (property code + laundry bag confirmed, by whom, when).

#### Skip flow

A clean can be skipped without deleting the job: `cleanSkipStatus` (`NONE | REQUESTED | SKIPPED | DECLINED`) plus reason/requester/decider/timestamp columns. Clients request skips from their portal; admins set/approve/decline/unskip via `PATCH /api/admin/jobs/[id]/skip`, surfaced in the "Skip" section of the job manage modal (`components/v2/admin/jobs/job-manage.tsx`).

#### Reset-job dialog (2026-07) and restart-transition artifact clearing (2026-07)

`lib/jobs/job-reset.ts` is the pure, unit-tested single source of truth for "what does resetting this job touch?". Two concerns live there:

1. **`startArtifactResetFields()` + `isRestartTransition()`** — whenever a job moves from any started status (`EN_ROUTE`…`INVOICED`) back to a pre-start status (`UNASSIGNED/OFFERED/ASSIGNED`), the *job-level* start scalars must be wiped: both GPS check-in and check-out blocks, `arrivedAt`/`departedAt`/`safetyCheckinAt`, the whole en-route/driving/ETA-notification block, and the early-clock-out park flags. These fields are job-global while the start gate is per-cleaner; leaving them behind is exactly what used to make a reassigned job unstartable for the new cleaner (see the team-state fix in B5). Time logs, submissions, assignments and pay are deliberately *not* touched by this patch — they are opt-in.
2. **`planJobReset(options, context)`** — the option-driven admin reset. Options: target status (`ASSIGNED` default — "keep the crew, they start again" — or `OFFERED`/`UNASSIGNED`), plus opt-in destructive extras: clear time logs, clear form data (submissions + photos + reversing stock), unassign cleaners, clear QA, reset the laundry task to `PENDING`. Guards: an `INVOICED` job, or any job whose pay is committed (`payrollRunId` set or `cleanerPaidAt` set), may **never** have data cleared — the plan comes back `allowed: false` with an explanation; only the status-only reset is permitted, and even that demands an extra confirmation. A `COMPLETED` job allows destructive options but also requires the extra confirm. The guard checks what was *requested*, not what would apply, so ticking an empty box can't sneak past. The plan also flags `notifyCleaners` when logs/forms are being deleted.

The dialog (`components/v2/admin/jobs/job-reset-dialog.tsx`, reached from the "Danger" section of `job-manage.tsx`) runs the **same** planner client-side to render the preview — each option row shows its consequence, destructive rows are red, and the summary lines shown pre-confirm are exactly the audit lines the server writes. Execution is `POST /api/admin/jobs/[id]/reset` (security-verified), which re-runs `planJobReset` server-side with `normalizeJobResetOptions` on the untrusted payload.

### B2. Property model

`Property` (`prisma/schema.prisma` ~line 854) is the per-site configuration hub the whole jobs pipeline reads from:

- **Identity & geometry**: name, address/suburb/state/postcode, `latitude`/`longitude` + `placeId` (geofencing, ETA and evidence stamps), `bedrooms`/`bathrooms`/`hasBalcony`/`sofaBedCount`, `floorCount`. (`propertyType` and `sizeSqm` were dropped from Property in the ACCESS-3 audit — see below; they live on `PropertyOnboardingSurvey`, which is where the intake UI and the cleaner-count estimator read them.)
- **Timing defaults**: `defaultCheckinTime` (14:00) and `defaultCheckoutTime` (10:00), plus `jobTimeSource` (`"PROPERTY"` default vs `"ICAL"`) which decides whether iCal event times or the property defaults drive turnover job times (see B3).
- **Duration & pay**: `cleaningDurationMinutes` (QA baseline + job-start display), `assignedCleaningHours` (first-class expected clean length — new jobs prefill `estimatedHours` from it), `cleanerServiceRate` (per-clean override of hourly maths).
- **Onboarding capture (ACCESS-3 audit, 2026-08)**: several columns were written on survey approval and then read by nothing. `laundryDetail`, `floorCount` and `recurringSchedule` are now displayed read-only on the v2 property detail ("From onboarding" card in `components/v2/admin/properties/property-detail.tsx`) — read-only because they are not in `updatePropertySchema`, and half-wiring a write path is precisely what caused the laundry-allocation wipe above. `emergencyContact` was **dropped** (migration `20260814000000_drop_property_emergency_contact`): one write in `lib/onboarding/approval/workflow.ts`, zero reads; the survey's copy still reaches the onboarding job's `internalNotes`, so intake data is not lost. `recurringSchedule` was audited alongside it and deliberately **kept** — `lib/marketing/segments.ts` reads it to derive `hasRecurringSchedule`, and quote→job conversion writes it. `propertyType` and `sizeSqm` were dropped in the same audit (migration `20260814010000_drop_property_type_and_size`) — one write each on approval, zero reads; both remain on `PropertyOnboardingSurvey`, which the intake UI and `lib/onboarding/estimation/calculator.ts` actually read. Every remaining onboarding-captured Property column now has either a reader or a display.
- **Access info**: legacy scalars (`accessCode`, `alarmCode`, `keyLocation`, `accessNotes`, `accessInfo` JSON) plus the rich image-backed `accessGuide` JSON — an array of `{id, kind: LOCKBOX|KEYS|ENTRY|ALARM|PARKING|BIN_ROOM|SUPPLIES_CUPBOARD|WIFI|OTHER, label, instructions, images[]}` rendered to cleaners by `components/v2/cleaner/property-access-guide.tsx`. `setupGuide` uses the same shape (kinds `SETUP|REFERENCE_POSITION|SOFA_BED|OTHER`) and feeds the Set-up stage reference strip.
- **Laundry fields**: `laundryEnabled` (false = no laundry service at all for the property — the single opt-out the eligibility predicate honours), `linenBufferSets`, `laundryBagLabel` + `laundryBagColor` (bag identity confirmed at job start), and `laundryDetail` JSON captured at onboarding (washer/dryer types, location, detergent, supplies).
- **`keyLostMode` (2026-07)**: `keyLostMode: Boolean` + `keyLostSince`. Normal laundry scheduling picks linen up the day *after* a clean and drops it the day *before* the next, using the spare key. When the spare key is lost the driver can't enter alone, so `lib/laundry/key-lost.ts` short-circuits the planner: pickup AND drop-off are scheduled on the cleaning day itself, after the clean starts — 12:30 when the job has a late-checkout rule, else 10:00 (`resolveKeyLostServiceTime` in `lib/laundry/clean-start.ts`). The draft item carries a `KEY_LOST` tag in both `scenario` and the persisted `flagNotes` so boards can badge the task even if the property toggle is later flipped back.
- **Checklist inputs**: `features` JSON (amenity flags — dishwasher, oven, pool, petFriendly… — copied from the onboarding survey on approval and editable on the property) drives module auto-application in the checklist library; `customFields` stores values for admin-defined intake fields whose *definitions* live in the `propertyFormConfig` AppSetting (`lib/property-form/config.ts`).
- **Misc**: `preferredCleanerUserId` (auto-assigned on iCal job creation via `lib/jobs/preferred-cleaner.ts`), `inventoryEnabled` (gates stock deduction on submit), `emergencyContact`, `recurringSchedule`, `isActive`.
- **Cleaner supply scope (2026-08)**: which properties a CLEANER sees supplies for is one predicate — **active AND assigned** — in `lib/inventory/cleaner-scope.ts`. Four surfaces previously disagreed: restock filtered on assignment but not `isActive` (retired properties kept appearing), while the shopping-plan route and the cleaner branch of `lib/inventory/stock-runs.ts` had **no assignment filter at all** and listed every active property in the business — a privacy leak and the reason the supplies screen was unusable. Admin and client branches are untouched. Migration `20260802000000_enable_inventory_on_active_properties` turns `inventoryEnabled` on for every currently-active property (owner decision); the flag is kept as the per-property opt-OUT and retired properties are left alone.

- **Access secrets were stored in plaintext (2026-08).** `Property.accessCode` and `alarmCode` are meant to be encrypted at rest by `lib/security/encryption.ts` (`enc:v1:<iv>:<cipher>`, AES-256-CBC keyed by SHA-256 of `ENCRYPTION_KEY`). They were not. `ENCRYPTION_KEY` had never been set in **any** environment, so `getKey()` returned null and `encryptSecret()` silently returned the value it was handed — every call site read as though it were encrypting while the database held bare door codes. A second copy leaked independently: `lib/properties/access-info.ts` copied the raw code out of the request body into `accessInfo.codes` as plain JSON, readable by every accessInfo consumer (briefings, portal payloads, admin list responses). Both write paths are now closed. `encryptSecret()` **throws** rather than storing plaintext — the same refusal `lib/auth/impersonation.ts` makes when `NEXTAUTH_SECRET` is missing — and `buildPropertyAccessInfo()` drops `codes` on every save, so each write scrubs the row it touches. `decryptSecret()` stays deliberately tolerant (a value without the prefix passes straight through), which is what lets rows from the plaintext era keep serving while `scripts/backfill/backfill-encrypt-access-codes.ts` re-encrypts them — dry-run by default, `--apply` to write, idempotent, and it promotes a JSON-only code into the encrypted column *before* scrubbing so no code is lost. Two operational consequences: **`ENCRYPTION_KEY` must exist before this code runs anywhere**, or every property save carrying a code 500s; and any code stored before the backfill must be treated as disclosed and physically rotated. Anything that *prints* a code must call `decryptSecret` — `lib/briefing/cleaner-briefing.ts` did not, and would have shown cleaners `enc:v1:…` instead of a door code the moment encryption began working, which is why that fix could not ship separately from this one. Covered by `tests/lib/encryption.test.ts` and `tests/lib/property-access-info.test.ts`.

The one-to-one `PropertyChecklistProfile` (see B4) and `Integration` (see B3) hang off the property.

### B3. iCal sync — reservations → jobs

#### Feed → Reservation → Job

Each property can have one `Integration` row (provider default `ICAL_HOSPITABLE`) holding the feed URL, enable flag, etag/modified caching and sync status. Every sync writes an `IcalSyncRun` row with a `summary` (counts + warnings) and a `snapshot` (before/after state of every touched reservation and job) — `undoIcalSyncRun` in `lib/ical/sync.ts` can revert a run from that snapshot.

`lib/ical/sync.ts` (~1,600 lines) is the whole pipeline. `syncPropertyIcal` fetches and parses the feed, then:

1. **`createOrUpdateReservations`** upserts `Reservation` rows keyed on `(propertyId, uid)`. The parser extracts far more than dates: guest name, reservation code, phone/email/profile URL, adults/children/infants, location text and geo, and local check-in/checkout datetimes (Hospitable feeds embed these as label/value blocks in the event description).
2. **`syncTurnoverJobsForReservations`** creates one `AIRBNB_TURNOVER` job per reservation, scheduled on the reservation's **end date** (the turnover day). Raw time candidates: `startTime` = previous guest's checkout (or the property default), `dueTime` = the same-day incoming check-in time (or the property default check-in). Which source wins is `Property.jobTimeSource`: `"PROPERTY"` (default) makes the configured defaults authoritative; only `"ICAL"` lets feed times drive. Priority is classified from the same-day check-in (B1). The reservation's guest context is merged into the job's `internalNotes` meta as `reservationContext` (or, with no same-day check-in, a "prepare for property max guests" context), and pending carry-forward and admin tasks are attached, plus the preferred cleaner auto-assigned.
3. **Booking moved while assigned**: if a reservation's turnover date moved and the job has active assignments and `manuallyRescheduledAt == null`, the sync removes the assignments, notifies each cleaner ("Shift cancelled — booking moved"), moves the job to the new date as `UNASSIGNED`, and records the cleared shifts in the summary.
4. **Re-sync updates**: for existing linked jobs (skipping terminal statuses), dates/times are only rewritten when `updateExistingLinkedJobs` is on **and** `manuallyRescheduledAt == null` — a manual admin/client reschedule is never overridden by the feed. Estimated hours are backfilled from the property, and the reservation context is re-merged.
5. **`pruneVanishedReservationJobs`** deletes jobs whose reservation disappeared from the feed (cancelled or re-UID'd), but only inside the window the feed actually covers and only for `UNASSIGNED/OFFERED/ASSIGNED` jobs — anything from `EN_ROUTE` onward is never auto-deleted. Assigned cleaners are notified first.

Per-property sync behaviour flags (`lib/ical/options.ts`, stored in `Integration.notes` JSON): `ignorePastDates`, `autoCreateTurnoverJobs`, `updateExistingLinkedJobs`, `verifyFeedDuplicates`, `verifyExistingJobConflicts` (skips creating a job when another turnover already exists that day). `syncAllIcalIfDue` runs from the schedulers (B8), gating each feed by its own due time.

#### Early check-in / late checkout rules, end-to-end

The rules are **stored once** — in the job's `internalNotes` meta as `earlyCheckin` / `lateCheckout` `JobTimingRule`s (`{enabled, preset: "none"|"11:00"|"12:30"|"custom", time?}`), edited by admins in the job manage modal and the new-job form. `applyJobTimingRules` (`lib/jobs/meta.ts`) is the pure resolver: a late-checkout rule **overrides `startTime`** (don't start before guests leave), an early-check-in rule **overrides `dueTime`** (finish before the next guests arrive), and if the two conflict the due time is clamped to the start time.

**The timing-rule re-application fix (2026-07).** Historically iCal re-syncs recomputed start/due from raw reservation times and overwrote the columns, silently undoing an admin's "late checkout 12:30" override — the badge said one thing, the columns another. The fix makes `lib/ical/times.ts` `resolveJobTimesFromReservation()` the **single choke point**: both sync paths (create and re-sync update, including the booking-moved path) run the reservation-derived raw candidates through the job's own meta rules before persisting, so the label and the actual columns can never diverge after a sync. The internalNotes rules are the single source of truth; the columns are derived.

**The one-shot reconcile job (2026-07).** Jobs whose times drifted *before* the fix are repaired by `lib/ops/timing-rule-reconcile.ts`: gated by the `timingRuleReconcilePending` AppSetting flag (absent = pending, `false` = done), it scans future jobs whose `internalNotes` contain `"enabled":true`, re-applies `applyJobTimingRules`, updates only rows that differ (capped at 500), writes one `TIMING_RULE_RECONCILE` audit row, then clears the flag so it never runs again. The web scheduler checks the flag every ~30 minutes.

**Surfacing**: admins see the rules as "Late checkout: start after …" / "Early check-in: complete before …" highlight strings via `getJobTimingHighlights` / `mergeUniqueJobHighlights` (which de-dupes semantically equivalent lines by normalized key) across job detail, reminders and briefings. Cleaners get the **timing banners (2026-07)**: `components/v2/cleaner/job-stages/timing-banner.tsx` renders one red chip for late checkout ("Do not enter or start before HH:mm — guests still inside") and one amber chip for early check-in ("The property must be guest-ready by HH:mm"), placed at the very top of the Set-up stage and echoed in the Clean stage, fed by the structured `timingRules` block the form read route returns.

### B4. Forms system

#### FormTemplate & schema shape

`FormTemplate` stores the full template as JSON `schema` (sections → fields → one level of `children` → conditional logic), typed by `serviceType: JobType` and `kind: FormKind` (`AIRBNB_TURNOVER`, `END_OF_LEASE`, …, `CUSTOM`), with versioning through `version` + `parentTemplateId` lineage, and `publishedAt`/`archivedAt`/`isActive` lifecycle. Field types and their behaviours (checkbox, yesno, photo, video, longtext, select, rating, signature, divider, …) are defined in `lib/forms/field-types.ts`; conditional visibility (`{fieldId, operator, value}` or property-field conditions) is evaluated by `lib/forms/visibility.ts`, which also exposes the `collectRequiredUploadFields` / `collectRequiredAnswerFields` collectors the submit route enforces.

#### normalizeFormSchema — one canonical shape

`lib/forms/normalize-schema.ts` is the single source of truth for turning *any* stored or generated schema (legacy or new) into one canonical shape, applied **identically** wherever a form is read (`app/api/jobs/[id]/form/route.ts`) and validated (the submit route). Canonicalisations: legacy section `label` → `title`; legacy `{fieldId, equals}` conditionals → `{fieldId, operator:"equals", value}`; field-type aliases `upload`→`photo`, `textarea`→`longtext`; deterministic id backfill; then `withStandardSections` applied idempotently. If read and submit ever normalized differently, the cleaner would satisfy one required-field set on screen and the server would enforce another — the historical "can't advance to uploads" bug this module exists to prevent.

#### Standard sections

Three template-owned standard sections (`lib/forms/standard-sections.ts`): **Arrival evidence** (walkthrough video + before photos), **Reported exceptions**, and **Sign-off**. Historically injected invisibly at read time by `withStandardSections` (`lib/checklists/compose.ts`); a template whose schema carries `standardSections: false` opts out because the sections are baked into the stored schema (via `scripts/bake-standard-sections.ts`), which makes them editable in the builder. Un-migrated templates (`undefined`) still inject, so the evidence gates can never silently disappear. Deleting one in the builder shows an explicit consequence warning.

#### Checklist library → per-property template generation

The checklist system is a DB-backed content library that composes into per-property forms:

- **`ChecklistModule`** (rooms/appliances/outdoor/safety/extras) with an `appliesWhen` auto-apply rule evaluated against the property (`{feature: "dishwasher"}` → `features.dishwasher === true`; `{propertyField:"hasBalcony", equals:true}`; `null` = always) and an optional `repeatBy` (`"bedrooms"`/`"bathrooms"`) that repeats the section per counted room.
- **`ChecklistModuleItem`** — stable key doubling as the generated field id (`kitchen.benchtops`), field type, required/minPhotos/stampTag, per-item `appliesWhen`, per-item `jobTypes` filter, and the evidence taxonomy: `evidenceCategory` (LIVING/KITCHEN/…/FINAL), `frequency` (`EVERY_CLEAN` | `CONDITIONAL` + `conditionKey` — item appears only when that exception is reported — | `ROTATIONAL` + `rotationEveryNCleans`), and a default QA `severity`.
- **`PropertyRotationState`** tracks, per property+itemKey, how many standard cleans have passed since a rotational item was last done; composition includes the item when `cleansSinceDone + 1 >=` its cadence, and the submit pipeline resets/advances the counters.
- The in-code catalog (`lib/checklists/catalog.ts`, ~3,900 lines) seeds and version-syncs the library (`CATALOG_VERSION` in `lib/checklists/library.ts`, currently "7" — the STANDARD Airbnb photo-proof content), including the mandatory evidence photo set, the conditional exception module, and the final **self-inspection module** (14 required checkboxes composed last).
- **`PropertyChecklistProfile`** stores per-property selections (module/item on-off with per-job-type flags, plus custom items) with a `DRAFT | APPROVED | STALE` status. Approval calls `generatePropertyTemplates` (`lib/checklists/compose.ts`): for each requested job type it composes the schema (`composeFormSchema`: library + property attributes/features + selections + rotation state), creates a new versioned `FormTemplate` (parent = the previous generated one, which is archived), records the ids in `generatedTemplateIds`, and **registers the templates in the `propertyFormTemplateOverrides` AppSetting** keyed `[propertyId][jobType] → templateId`.

**Per-property overrides at read time**: `app/api/jobs/[id]/form/route.ts` resolves the template as `propertyFormTemplateOverrides[job.propertyId][job.jobType]`, falling back to the active global template for the job type. Past jobs are immune to re-generation because every submission snapshots `__templateSchema` (B5).

#### The v2 form builder

`components/v2/admin/forms/builder/form-builder.tsx` is the Estate-native builder: field palette (left), canvas (centre), properties panel (right), theme drawer (`theme-editor.tsx`, stored on `schema.theme`), reference-media editor (`reference-media-editor.tsx` — per-field how-to images/videos), condition editor, lint pass (`lib/forms/lint-template.ts`) and a read-only live preview. It saves via `PATCH /api/admin/form-templates/[id]` and publishes/archives/duplicates via sibling endpoints. Two settings ride on the schema root:

- **Inventory selection config (2026-07)** — `schema.inventoryConfig` (`lib/forms/inventory-config.ts`): `{mode:"all"}` (default, every active `PropertyStock` row appears in the cleaner's "Stock & consumables used" block) or `{mode:"selected", itemIds:[...]}` to narrow the list (empty selection = show none). Edited in `inventory-settings.tsx`; the form read route applies `filterStockByConfig` to the `inventoryStock` payload, and `normalizeFormSchema` carries the config through read→save round-trips so it can never silently widen back to "all".
- **Laundry auto-off indicator (2026-07)** — a dashed info card in the builder stating "Laundry update: automatic — Airbnb turnovers only (per-property toggle in Property settings). Rework jobs never show it." Laundry is deliberately *not* builder-configurable; the card exists so admins know where the real switch lives (the eligibility predicate, B5).

### B5. The cleaner portal journey (v2, five stages)

The cleaner job workspace is `components/v2/cleaner/job-workspace.tsx` (page: `app/v2/cleaner/jobs/[id]/page.tsx`). It wires the same endpoints as v1 (`GET /api/jobs/[id]/form`, `GET /api/cleaner/jobs/[id]/briefing`, the draft endpoint, start/stop/submit, GPS check-in/out, uploads) into a 5-stage journey. `deriveJobStage` (`lib/cleaner/job-stage.ts`) is a pure presentation-only derivation: **1 Accept** (assignment still `PENDING`), **2 Get there** (actively en route), **3 Set up** (accepted, not clocked in — the default), **4 Clean** (clocked in), **5 Wrap up** (submitted/locked). Ordering rules: acceptance always wins; locked wins over started; a cleaner already at the door is never pushed back to a travel screen (stage 2 shows only while actively en route). Stage chrome lives in `components/v2/cleaner/job-stages/` (`stage-nav`, `job-header`, `stage-footer`, `action-fab`).

**Pause/resume from any stage (2026-08).** The clock control originally lived only inside `stage-setup.tsx` (stage 3), and clocking in auto-advances the workspace to stage 4 — so the Pause button unmounted at the exact moment it became useful, and the only way back was tapping a step already rendered as complete. In practice **jobs could not be paused in v2 at all**. A compact Pause/Resume control now sits beside the live timer chip in `job-stages/job-header.tsx`, which renders on every stage; stage-setup keeps its larger card for the initial clock-in. The endpoint (`POST /api/cleaner/jobs/[id]/stop`) was never at fault. The workspace also **re-reads on focus/visibility and every 90 s**, because the geofence sweep can close the TimeLog and set PAUSED server-side — previously the UI kept a client-side timer ticking against a closed log, showing the cleaner time that was not being recorded.

#### Stage 1–2: Accept and Get there (driving mode)

`stage-accept.tsx` presents the offer with `JobOfferActions` (accept/decline via `POST /api/cleaner/jobs/[id]/assignment-response`). `stage-travel.tsx` embeds **driving mode** (`components/v2/cleaner/driving-mode.tsx` / `route-driving.tsx`): `POST …/start-driving` sets `EN_ROUTE` and stamps `enRouteStartedAt`; a heartbeat loop pings `…/location-ping` so admins and clients see live ETA (`enRouteEtaMinutes`, ETA-notification de-dupe columns on the Job); `…/arrived-driving` stamps `arrivedAt`; `…/mark-delayed` records `drivingDelayedAt/Reason`. The **working pause/resume (2026-07)**: `POST …/pause-driving` (with a reason from the mode's reason list) and `…/resume-driving` set/clear `drivingPausedAt`/`drivingPauseReason`; the client keeps an optimistic pause override reconciled against the server, and — the actual fix — the heartbeat loop now stops while paused (previously it kept pinging through a pause, so location kept flowing and the ETA machinery stayed warm even though the drive was "paused").

#### Stage 3: Set up, start verification, and the team-state gates

`stage-setup.tsx` orders the pre-start sequence: timing-rule banners (B3) → **booking card** (`booking-card.tsx`: guest party from the iCal `reservationContext`, sofa beds, check-in/out times) → collapsed **setup reference** strip (the property `setupGuide` entries) → briefing card (prior QA warning, rework notes, access vault) → the clock-in gate card with property code, expected duration, laundry-bag identity (label + colour), READ FIRST items, restock needs and watch-outs → the confirmation checkboxes → CLOCK IN.

- **Previous-clean laundry cycle card (2026-07)** (`laundry-cycle-card.tsx` + `lib/laundry/previous-cycle.ts`): shows the laundry cycle *belonging to the previous clean of the same property* — the pickup/drop that stocks THIS clean's fresh linen — replacing the old "last drop from any job" block that kept reading like the wrong property. Selection is pure and unit-tested (`pickPreviousCleanJob`: latest other non-rework turnover before this job that has a `LaundryTask`; `pickDropConfirmation`: the latest confirmation whose meta event is `DROPPED`, tolerant of status reverts). The card renders four live states — **delivered** (green proof card with drop time + tappable delivery photo), **en_route** (live driver update polled from `GET /api/cleaner/jobs/[id]/laundry-eta` every 25s while visible: next-stop flag, stops before, ETA minutes), **no_signal**, and **scheduled**.
- **Start verification**: `POST /api/cleaner/jobs/[id]/start` requires (when the accountability gate is on) `propertyCodeConfirmed` + `laundryBagConfirmed`, recorded into the job meta `startConfirmation`; a GPS check-in (`…/gps-checkin`) captures position/accuracy/distance against the property geofence.
- **Team-state gates and the per-cleaner fix (2026-07)** (`lib/cleaner/team-state.ts`): a job can have multiple cleaners, and two different "has this started?" questions must not be conflated. *Visibility* (`isStartedForVisibility`) is true as soon as **anyone** started — the second cleaner must reach the checklist of an in-progress clean. *Own time* (`isOwnStarted`) is strictly per-cleaner — pay and timesheets are personal, so the second cleaner still clocks in. `requiresStartConfirmations` decides whether the heavyweight before-you-start confirmations apply: only the *first* person to start does them, keyed on `isTeamActive` (job actively `IN_PROGRESS`/`PAUSED` **and** someone on the clock) rather than `isTeamStarted` (which a *stale* time log also satisfies). That distinction is the fix for the reassignment deadlock: when an admin moved a started job back to `ASSIGNED` and handed it to a new cleaner, the old time log and immutable `gpsCheckInAt` made the workspace think the job was started (never showing the verification) while the server — keyed on the *current* cleaner's TimeLog — kept rejecting the clock-in. The job-level `gpsCheckInAt` is accepted as input but deliberately never treated as a bypass. The server-side half of the fix is the restart-transition artifact clearing (B1).

#### Clock in/out, time logs, auto clock-out

`TimeLog` rows record each work segment (`startedAt`, `stoppedAt`, `durationM`); a raw-SQL **partial unique index** enforces at most one open log per `(jobId, userId)` (migration `20260703120000_timelog_open_unique` — deliberately not a Prisma `@@unique`, which would block re-clock-in). `POST …/start` opens a log and sets `IN_PROGRESS`; `POST …/stop` closes it and moves the job to `PAUSED` unless a teammate still has an open timer. Cleaners can request time corrections via `TimeLogAdjustmentRequest` (admin-reviewed).

Auto clock-out has two rails:

1. **Time-based** (`lib/time/auto-clockout.ts` + `buildClockReview` in `lib/time/clock-rules.ts`): configured cutoff rules cap a runaway clock; on submit, the open log is closed at the review's suggested stop time and capped duration, with an optional cleaner-initiated `clockAdjustmentRequest` creating a pending admin review.
2. **Geofence-based (2026-07)** (`lib/gps/departure-clockout.ts`, summarised here — the GPS/geofence platform itself is Section A): when the background ping route sees an outside-fence ping, `evaluateDeparture` (`lib/gps/departure.ts`) demands ≥3 accurate outside-fence pings spanning ≥2 minutes before confirming — a single drift spike never confirms. On confirmation `Job.departedAt` is stamped regardless of settings (it powers "Left site X ago" ops labels); then, only if `settings.autoClockOut.geofenceExit` is on and the job is `IN_PROGRESS`, the cleaner's open log is closed ("Auto clocked out — left job site (GPS)"), the job moves to `PAUSED` only when no teammate is still clocked in, an `AUTO_CLOCK_OUT` audit row is written, and both the cleaner and admins are notified.

Additionally, `autoPauseStaleJobs` (`lib/ops/auto-pause.ts`, **2026-07**) sweeps jobs stuck `IN_PROGRESS` more than 24h: closes open logs like the manual stop route and moves the job to `PAUSED` so it lands back on the admin radar.

#### Stage 4: Clean — the form renderer

`stage-clean.tsx` renders the normalized schema through `components/v2/cleaner/form-renderer.tsx` as a sectioned accordion: checkboxes/yes-no/text/select fields, conditional children, per-field **reference media** (builder-authored images/how-to videos), and uploads via `media-capture.tsx`. Every camera photo gets the **evidence stamp** burnt in client-side (`lib/uploads/stamp.ts`: before/after/damage tag, sNeek logo, large time + date + weekday + street address block; gallery images are compressed but never double-stamped); `guided-capture.tsx` is the fast "keep snapping" surface for multi-target photo requirements. **Inventory usage** appears as the "Stock & consumables used" block, filtered by the template's `inventoryConfig` (B4), and its quantities are deducted from `PropertyStock` on submit. Rework jobs render a per-area fix checklist instead, generated from `reworkAreas` by `buildReworkFormSchema` (`lib/qa/rework-jobs.ts`), grouped or flat per the `reworkCategorized` meta flag.

#### Stage 5: Wrap up and submit

`stage-wrapup.tsx` orders: **Laundry** (turnover-only) → restock/inventory summary → **Pass to next clean** (carry-forward flags) → damage / extra-pay entries → SUBMIT, with live validation errors rendered as tappable rows that jump to the offending stage/field. When locked, the stage becomes the "Job submitted" review screen (time on site, pay for the job, quality-pending note).

- **Laundry update state machine + eligibility**: `isLaundryUpdateEligible` (`lib/laundry/eligibility.ts`) is the single shared predicate — laundry applies only to `AIRBNB_TURNOVER`, never on rework jobs, and only when the property hasn't set `laundryEnabled: false`; it is imported by the submit route, the standalone `…/laundry-status` route (early update from site) and the workspace, replacing three hand-mirrored copies. Outcomes: `READY_FOR_PICKUP` (requires bag location + laundry photo), `NOT_READY`, `NO_PICKUP_REQUIRED` (both require a skip reason code). `applyCleanerLaundryStatusUpdate` (`lib/laundry/cleaner-status.ts`) writes the `LaundryTask`/confirmation state, ensures the task exists, and notifies the property's assigned laundry partners with the pickup/drop schedule, bag location and photo.
- **Damage / extra pay / maintenance**: draft damage items become `DAMAGE` cases (`lib/cases/service.ts` `createCase`, client-visible, with attachments) — one case per item, each opened independently post-commit; pay-request items become `PENDING` `CleanerPayAdjustment` rows in the admin queue; maintenance issues flow through `report-maintenance.tsx` into the maintenance system.
- **Self-inspection**: the composed final-inspection section's 14 checkboxes are server-gated — `collectUntickedSelfInspection` in the submit route rejects (or, when `accountability.selfInspectionBlocksSubmit` is explicitly off, records `__selfInspectionIncomplete` for QA visibility).
- **Start briefing (2026-08)** (`lib/forms/start-briefing.ts` + `start-briefing-dialog.tsx`): what the cleaner must have **read** before the clock starts, in the only moment the answer can still change what happens — a late-checkout rule is worthless once someone has already walked in on the guests, and an admin task discovered at submit time is a task that did not get done. `resolveStartBriefingItems` collects, in order: **TIMING_RULE** (late checkout, then early check-in), **ADMIN_TASK** (meta special-request tasks + `JobTask` rows with `source: ADMIN`), **CLIENT_TASK** (`source: CLIENT`, **APPROVED only** — an unapproved request is not yet work), **SPECIAL_NOTE** (the free-form internal note); ids are de-duplicated so a meta task and its materialised row are read once. An empty list means no dialog — a prompt that fires on every job is one people learn to dismiss unread. `POST /api/cleaner/jobs/[id]/start` recomputes the list server-side and returns **409 `START_BRIEFING_REQUIRED`** with `{ items, reason }`; the workspace opens the dialog and replays the acks on retry. Acks persist in the job meta as `startBriefingAcks[cleanerId] = { hash, items }` (no migration) and are **content-hashed**: editing "start after 12:30" to "14:00" keeps the item id but changes the hash, so the gate re-arms with `reason: "STALE"` rather than silently counting the old acknowledgement. Only ever gates the FIRST start for that cleaner — a resume is never blocked mid-job.
- **Final check-up acknowledgement (2026-07)** (`lib/forms/final-checkup.ts` + `final-checkup-dialog.tsx`): admin-defined check-up items (AppSettings `finalCheckup`, filtered by job type) plus two auto-items — a guest-count item built from the reservation context ("Guests this stay: 4 (2 adults, 2 children) — confirm setup") and one per admin special-request task. The dialog collects a tap-acknowledgement per item; the submit route **recomputes the list server-side** with the same resolver and validates via `validateFinalCheckupAck`, returning a 422 `FINAL_CHECKUP_REQUIRED` with the missing items (the workspace merges acks already given this session into the retry, so a 422 never loses progress).

**The submit pipeline** (`app/api/cleaner/jobs/[id]/submit/route.ts`, ~1,100 lines) runs its gates strictly in order, all read-only before any write: assignment check → pending continuation-request block → locked-status block → never-started guard (a pre-start job with zero time logs and no form-pending park can't jump to SUBMITTED) → template resolution (rework accepts the hidden inactive template) with `normalizeFormSchema` producing the same required-field set the UI enforced → missing required uploads → missing required answers → self-inspection gate → final check-up gate → admin-requested-task completeness (done + note + photo where required) → unified `JobTask` decisions (every task completed-with-proof or not-completed-with-reason) → laundry payload validation. Then the **atomic status claim**: a conditional `updateMany` flips the job to `SUBMITTED` only if it isn't already locked — of two concurrent submits, only the one that flips the row proceeds; the loser gets a 409 with zero side effects. The critical section — `FormSubmission` (with `__templateSchema` snapshot, `__adminRequestedTasks`, `__jobTasks`, `__finalCheckup` embedded in `data`), `SubmissionMedia` rows, stock deduction, and clearing the form-pending flag — is **one transaction** (20s timeout), so a mid-write failure rolls everything back together with the status revert: no orphaned submission, no double stock deduction. Everything after commit is best-effort and individually guarded: low-stock side effects, rotational-counter update, carry-forward task creation on the *next* clean at the property, laundry status update, damage cases, pay requests, unified-task application, QA assignment scaffolding (`tryEnsureQaAssignmentForCompletedJob`), rework-resubmit notifications, clock close + adjustment request, client "clean complete" notification + post-job automations, report generation → `REPORT_READY` lifecycle email, and clearing the shared draft.

**Clock-out-early path**: `POST …/clock-out-early` is restricted to cleaners on the `clockOutWithoutFormAllowedCleanerIds` allowlist. It stops the clock and parks the job `PAUSED` with `formPendingAfterClockOut: true` + `clockedOutEarlyAt` — explicitly *not* complete until the form is later submitted (the Set-up stage shows a "Form still pending" warning and the submit route's never-started guard exempts this park state).

### B6. Drafts & reliability

Progress on a job is held in **one shared draft envelope per job** — `lib/cleaner/shared-job-draft.ts` stores `{updatedAt, updatedByUserId, updatedByName, editorSessionId, state}` in an `AppSetting` row keyed `cleaner_job_shared_draft_v1:<jobId>`, served by `GET/PATCH/DELETE /api/cleaner/jobs/[id]/draft`, shared across devices *and* co-cleaners. The workspace additionally mirrors the state to `localStorage` (`cleaner-job-draft-v2:<jobId>`) so an instant reload survives even if the server flush hadn't landed.

Because a naive whole-envelope replace could clobber a teammate's work, restore always **merges** the local mirror with the server envelope via `mergeDraftStates` (`lib/cleaner/draft-merge.ts`): uploads and media arrays are *always unioned by storage key* (media loss — a file that exists on S3 but the draft forgot — is treated as the worst outcome); answers are per-key last-write-wins from the newer state with older-only keys surviving; task drafts merge decision/note by recency with proofs unioned; laundry/carry-forward scalars follow the newer state with photo arrays unioned.

Persistence is a debounced autosave plus **flush-on-hidden**: `visibilitychange`(hidden) and `pagehide` listeners call `flushDraft({keepalive: true})` — the synchronous localStorage write plus a `fetch` with `keepalive` so the request survives the page being killed mid-navigation. The draft is deleted server-side after a successful submit.

**Upload reliability**: the shared stamp→compress→upload pipeline (`prepareAndUploadFiles` in `media-capture.tsx`) runs uploads in parallel and *never rejects* — successes are kept and a failed count is surfaced ("N file(s) failed to upload") for the cleaner to re-shoot, while everything already uploaded is safe in the draft union. Large videos go through `lib/uploads/multipart-client.ts` (5 MB parts against pre-signed URLs). Failed uploads are recorded in the `UploadFailure` telemetry table (reason codes like `S3_TIMEOUT`, `PRESIGN_REJECTED`, `CLIENT_ABORT`) and surfaced to admins at `app/admin/system/uploads/page.tsx`.

### B7. Submissions & reports

`FormSubmission` holds the cleaner's answers keyed by field id, plus the laundry outcome block (outcome, skip reason code/note, admin override columns, bag location) and an `autoQaScore`. Crucially the `data` JSON embeds `__templateSchema` — the exact normalized schema in force at submit time — so QA review and report rendering are immune to later template edits or re-generation. `SubmissionMedia` rows link every uploaded photo/video to its field, with original/annotated variants (`annotatedS3Key`, `annotationData`) for QA markup.

**Report generation** (`lib/reports/generator.ts`, `generateJobReport`) renders the submission into a themeable HTML report (template version `v5-estate-modern`): it walks the snapshot schema with the same visibility logic the form used (`lib/forms/visibility.ts`), formats values via `lib/forms/field-types.ts`, groups evidence media, applies a `ReportTheme`, and stores the result on the one-to-one `Report` row (HTML + optional PDF on S3, rendered by Playwright Chromium print). The default skin is now **Estate** (2026-07): a pure view-model module (`lib/reports/report-view-model.ts`) maps submission + snapshot schema + QA into a testable render model — every visible field renders with its actual answer (ticks, yes/no pills, rating dots, captioned + timestamped photo grids, signature; unanswered optional fields show "—", nothing filled is ever dropped) — and `lib/reports/estate-template.ts` lays it out with a brand cover band, at-a-glance stat tiles + flag pills, per-section cards in form order, and tasks/QA/rework/laundry/supplies cards, print-safe with page-break-aware sections. The client-facing QA summary mirrors the legacy exclusions exactly (no costs, no pay). Luxury/Compact/Magazine/Detailed remain selectable for rollback; seed via `scripts/seed/report-themes.ts` (idempotent — required once per environment to make Estate the default).

**Clock truth in the report (2026-08).** The report's times come from `TimeLog` only: the generator query loads the job's clock segments and the view model derives `clockInLabel` (earliest `startedAt`), `clockOutLabel` (latest `stoppedAt`) and a summed duration. A job with any open segment renders "not clocked out" — the form-submission time is **never** substituted for a clock-out (forms are often submitted after the clean); it stays on its own "Submitted by X · form submitted <time>" line. The at-a-glance Timing tile uses clock data exclusively when TimeLogs exist (sub-line "clock-out not recorded" when honest data is missing) and falls back to the GPS check-in/out pair only for jobs with no TimeLogs at all; `completedAt` is never used.

**Report presentation (2026-08).** Estate photos render **uncropped** (natural aspect ratio, no `object-fit` crop) and every image is wrapped in its own link that opens the full file in a new tab — same behaviour as videos — across checklist fields, tasks, QA inspection photos and rework areas. The cover logo is larger (max 76×300px) and the estate skin prefers `settings.logoDarkBgUrl` (the white-letter logo) because the cover band is a dark primary gradient; a theme's own `logoUrl` still wins, standard logos remain the fallback. A **GPS attendance** card (view model `gps`/`ReportGpsVM`) renders check-in/check-out coordinates as Google-Maps links with capture times, accuracy, distance-from-property, and an "Amended by admin" pill when `gpsCheckInAdjusted` is set; jobs with no captured coordinates show no card.

**Admin clock & GPS editing (2026-08).** The v2 job detail **Activity** tab is now editable (`components/v2/admin/jobs/job-clock-gps-editor.tsx`): per-segment clock-in/out edits go to `PATCH /api/admin/jobs/[id]/time-logs/[timeLogId]` (recomputes the pay-driving `durationM`, enforces >0 and ≤24h segments, honours the one-open-log partial unique index when reopening, notifies the cleaner, audit-logs before/after as `ADMIN_EDIT_TIME_LOG`); GPS check-in/out coordinates and timestamps go to `PATCH /api/admin/jobs/[id]/gps` (validates lat/lng ranges, requires lat+lng set/cleared together, stamps `gpsCheckInAdjusted`, audit-logs as `ADMIN_EDIT_JOB_GPS`). Both endpoints are ADMIN/OPS_MANAGER-only and regenerate the stored report in the background when one exists, so a corrected clock never leaves a stale PDF behind. The cleaner-initiated `TimeLogAdjustmentRequest` approval flow is unchanged.

**"No photo taken" exemption (2026-08, NOIMG).** Admin-selected cleaners (`settings.noPhotoExemptCleanerIds`, roster UI in Settings → Accountability) get an understated "I couldn't take a photo…" option on photo-capable upload fields. Recording a **coded reason** (`lib/forms/no-photo-reasons.ts`: locked area / guest privacy / device failure / no signal / safety / other+note) waives that field's required-upload and minPhotos rules — client mirror in `collectFormErrors` (new `noPhoto` arg, all four cleaner-flow call sites) and authoritative re-check in the submit route, which verifies the settings grant, sanitizes entries, drops any waiver for a field that actually has uploads, and stores the sanctioned map as the controlled `__noPhotoReasons` system key. The form payload (`GET /api/jobs/[id]/form`) exposes `canUseNoPhoto`. The report renders waived fields as an explicit amber answer ("No photo — reason"), never an unanswered blank. QA: every waived field is a **scored miss** — `buildNoPhotoPenalties` (`lib/qa/no-photo-penalty.ts`) maps waivers to points (field's `noPhotoPenalty` or default 2) and `computeQaScore` adds them to the achievable max with zero earned (synthetic "Missing photo evidence" section), so the stored QA percent drops automatically in proportion to the points assigned; wired in the QA submit route for canonical nested-scoring templates (the legacy default-template rating path deliberately ignores penalties). UI copy stresses photos remain the expectation — this is for unavoidable circumstances only.

**Laundry truth (2026-08).** The report's Laundry card renders from the **LaundryTask** (via `buildLaundryVm`) — status → outcome (CONFIRMED "ready for pickup", PICKED_UP, DROPPED, SKIPPED_PICKUP "no pickup required", FLAGGED "not ready"), bag location from the latest confirmation, skip reason from the task — because the task carries the cleaner's explicit mid-job updates and admin overrides that the form's laundry answers miss when the form is submitted hours later; form answers remain only as a legacy fallback. Same principle in the write path: `applyCleanerLaundryStatusUpdate` refuses a `FINAL_SUBMISSION` downgrade of a CONFIRMED task whose partners were already notified (`blocksLaundryFinalSubmissionDowngrade`) — the confirmed pickup is kept and admins get a "laundry contradiction" alert instead; an explicit `EARLY_UPDATE` correction may still downgrade.

**Public report verification (2026-08).** Every generated report carries a stable crypto-random code (`ReportVerification`: one per job, 16-char Crockford base32 ≈80 bits via `crypto.randomBytes`, unique + non-enumerable, `revokedAt` disables without deleting). `generateJobReport` ensures the code and renders a "Verify this report" card with the display-grouped code (`ABCD-EFGH-JKMN-PQRS`), the public URL and a QR (`qrcode` data-URL; skipped gracefully when no base URL is configured). The public pages — `/verify` (code form) and `/verify/[code]` (result) — live in `app/(public)/`, are whitelisted for anonymous access in `middleware.ts`, and are deliberately NOT gated by `requireWebsitePageEnabled` (printed codes must always resolve). The result page rate-limits lookups per IP (20 / 10 min, `lib/security/rate-limit.ts`) and renders ONLY the dedicated minimal `PublicVerificationVM` from `lib/reports/verification.ts` — suburb, service date, job type, cleaner FIRST names, clock-in/out (honest "not clocked out"), issued date, verified/revoked — never the internal report VM; unknown and malformed codes render identically so responses don't reveal which codes exist. Pure code helpers live in `lib/reports/verification-code.ts` (client-safe, imported by the form).

**Client visibility**: `Report.clientVisible` / `cleanerVisible` / `laundryVisible` flags (with `visibilityNote` and audit columns) control who sees it; `sentToClient`/`sentAt` track delivery. On submit the client automatically receives the "clean complete" notification, and once generation finishes the `REPORT_READY` lifecycle email offers the report — the two are deliberately distinct so neither duplicates.

**QA handoff**: submission immediately opens a `QaAssignment` via `tryEnsureQaAssignmentForCompletedJob` (`lib/qa/auto-assignment.ts`) so an inspector can claim it from the queue; the QA review/issue/rework machinery itself (QAReview, QaIssue, rework transfer, rectification pay) is covered in the QA section of this reference — from this section's perspective, a failing review produces the rework job described in B1 and the job returns through the same submit pipeline.

The detail page `app/v2/admin/jobs/[id]/page.tsx` is a **server** component whose sections are `?tab=`-addressed via the new `ETabs` primitive (`components/v2/ui/primitives.tsx`) — link-based, not client state, so every tab is deep-linkable and survives a reload. **CP-9 (2026-08) — parity with v1 plus the booking record.** Four things the v2 detail either never selected or showed too thinly. (2) **Same-day check-in**: `Job.sameDayCheckin`/`sameDayCheckinTime` existed but were not in the page's select; the Schedule card now carries a warning-toned banner with the guest arrival time, because a same-day arrival is the case where a clean running late actually costs the client a guest. (3) **Guests (iCal)**: a new card. **Read this before touching it — the direction is counter-intuitive.** A turnover job is linked to the booking whose *checkout* triggered it (`lib/ical/sync.ts` sets `reservationId` from the reservation whose `endDate` is the turnover date), so `Job.reservation` is the guest who just **left**. The guest **arriving** — the one the property is being prepared for — is a different reservation, captured onto the job by the same sync as `jobMeta.reservationContext`. (4) **Laundry**: the tab showed only the *planned* `pickupDate`/`dropoffDate`, so a task read as scheduled whether or not it had happened. It now pairs each leg with its actual stamp (`pickedUpAt`/`droppedAt`, `confirmedAt`), plus supplier, bag weight, drop-off cost, and every evidence image (`pickupKeyPhotoUrl`, `dropoffKeyPhotoUrl`, `receiptImageUrl`, and each `LaundryConfirmation.photoUrl`). The clock-in/out GPS is also plotted on `components/shared/clock-locations-map.tsx` above the existing `GpsRecordEditor` — same numbers, but an off-site clock-in is obvious at a glance; it degrades to "open in Google Maps" links with no API key.

Editing happens **inline in the tab that owns the concern**. `components/v2/admin/jobs/job-manage.tsx` now exports `JobManagePanel({ job, section, onChanged })` — the same controls, the same endpoints and payloads, no modal — mounted through `JobDetailManage` (`job-detail-reviews.tsx`), which holds the `router.refresh()` so inputs re-hydrate from what was persisted rather than from what was typed. ### B9. Form template identity, field types & authoring (2026-07)

**Which template a job renders** is now one pure, total-ordered rule — `lib/forms/resolve-job-template.ts`, shared by the cleaner form route, the progress calculator and the client portal (each previously had its own drifting copy): **job pin → property override → newest active global** (property- and job-scoped rows excluded from the global fallback), with a deterministic tie-break (`version → publishedAt → updatedAt → createdAt → id`). The tie-break matters: version numbers are allocated per `FormKind` but resolution happens per `serviceType`, so ties were routine and the winner was previously whatever Postgres returned first — the same edit could apply one day and not the next.

**Job pin.** `Job.formTemplateId` + `FormTemplate.isJobScoped` (migration `20260729090000_job_pinned_form_template`). Converting a quote to a job mints a one-off form for **that job only** (`lib/forms/job-scoped-template.ts`) and pins it; it no longer writes a permanent `propertyFormTemplateOverrides` entry, which used to make every future job of that type at the property render the quote's form and quietly ignore all later edits to the real template. `isJobScoped` keeps those one-offs out of global resolution and protects them from publish-archiving. Backfill: `scripts/backfill/unpin-quote-form-overrides.ts` (dry-run default).

**Why an edit may legitimately not apply**, now surfaced rather than silent: per-property generated checklist templates and property overrides outrank the global template, and re-approving a checklist profile replaces the generated row (discarding manual builder edits). `GET /api/admin/form-templates/[id]/impact` + the builder's "Where this template applies" panel state the publish state, whether jobs actually render this row, which properties override it, how many open jobs resolve to it, and warn when none do.

**Field types.** All 25 registry types are covered end-to-end (editor → normalize round-trip → preview → renderer → conditions as source and target → submit validation → report) by `tests/lib/forms-field-type-round-trip.test.ts`, `forms-condition-operators.test.ts` and `forms-validate-field-types.test.ts`. Notable rules: Yes/No answers are **booleans** (v2 briefly stored `"yes"`/`"no"` strings, which silently killed every yes/no-driven conditional and blanked the answer in reports — readers stay tolerant of the legacy strings); `normalizeFormSchema` preserves unknown root keys; conditions support `contains`/`notContains` (multiselect membership, case-insensitive text substring), numeric `gt`/`lt` are numeric-only, and `equals:false` no longer matches an unanswered field. Sections can be made conditional/collapsible from the builder, and the preview evaluates conditions with the same `lib/forms/visibility` engine the cleaner and submit route use.

**Submit gates (2026-07).** A required `checkbox` counts as answered even when unticked *unless* the admin setting `accountability.requiredChecklistTicksBlockSubmit` is on (**default off**) — because generated checklist items are themselves required checkboxes, switching it on makes the entire checklist hard-blocking, not just confirmations. The rule lives in one pure helper (`isRequiredAnswerMissing` in `lib/forms/visibility.ts`) used by BOTH the client gate and the submit route, so the two can never disagree; the final self-inspection section is exempt and keeps its own gate + the `selfInspectionBlocksSubmit` opt-out. Video `maxDurationSec` was removed from the builder (nothing enforced it); stale values on saved templates are dropped on normalize.

**Authoring.** Creating a form offers: blank, one of eight starter blueprints (`lib/forms/starter-templates.ts` — Airbnb turnover, end-of-lease/bond, recurring, deep, post-construction, office/commercial, QA inspection, rework; each with photo-proof minimums and a demonstration conditional), duplicating a form already in use, or the legacy seed templates. Duplicates are created as **drafts** — the forms list now requests drafts (`includeDrafts=1`) and has a "Show archived" toggle; previously it asked only for live rows, so a duplicate existed but was invisible and read as "nothing happened".

### B10. Damage reporting (D1, 2026-08)

One visit produces ONE `DamageReport` holding MANY `DamageItem`s, each with its own `DamageItemPhoto`s. This replaced a single-damage form (`DamageReport` in `components/v2/cleaner/job-actions.tsx`) that forced a cleaner who found two faults to submit twice, with nothing recording that they came from the same visit.

**One case per item, and why it is load-bearing.** Every `DamageItem` opens exactly one DAMAGE `IssueTicket`, and `createCase()` raises the repair through CP-7 (`lib/cases/service.ts` → `autoCreateMaintenanceForDamageCase`). `DamageItem.caseId` is UNIQUE so the database refuses to let two items share a case — batching them would make CP-7 raise a single repair for several separate faults. The FK is `ON DELETE SET NULL`, not cascade: deleting a case must never destroy the photographic evidence of the damage it was opened for.

**Two severity scales, deliberately.** Cleaners grade what they can see (`DamageSeverity`: MINOR|MODERATE|MAJOR|SEVERE); ops runs on urgency (`IssueTicket.severity`: LOW|MEDIUM|HIGH|CRITICAL). `lib/damage/severity.ts` is the only bridge, and `tests/lib/damage-severity.test.ts` asserts the end-to-end consequence — that a SEVERE report still arrives as an URGENT repair, and that the four grades stay four distinct priorities. The old path hardcoded `severity: damage.severity ?? "HIGH"`, so anything unexpected collapsed to MEDIUM and every grade queued alike.

**The client sees nothing until admin review, and that gate now actually holds.** `DamageReport.clientVisible` defaults false, and — critically — the per-item cases are created `clientVisible: false` too. Previously both cleaner damage paths (`app/api/cleaner/jobs/[id]/damage-report/route.ts` and the `draftDamageItems` loop in the submit route) opened cases with `clientVisible: true`, so the client saw reported damage the instant a cleaner submitted, through the cases workspace, regardless of any report-level flag. Both were flipped to false; a report-level gate alone was decorative.

**No cost field on the cleaner side.** The old form asked cleaners for an estimated cost. `DamageItem.estimatedCost` is admin-write-only, decided on the investigation page (D2), and it is absent from every schema in `lib/damage/validation.ts` — the routes build their Prisma payload from the PARSED object, so a cleaner sending it has it stripped rather than merely ignored (`tests/lib/damage-validation.test.ts` pins this).

**Draft and submit are different contracts.** `PUT /api/cleaner/jobs/[id]/damage` autosaves on a debounce and accepts half-finished work — a card with photos and no text yet must save, because the failure mode being designed against is a phone dying mid-documentation. `POST` requires an area, a category, a description of at least a sentence, and at least one photo per item. Blank cards are dropped at submit rather than rejected: an empty extra card is a normal artefact of "add item", and failing the whole submission over one is hostile to somebody standing in a property. Saves replace the whole item list rather than patching — the form owns the list, and a dropped partial write must never leave a draft the cleaner never saw.

**Submit is resumable, not atomic.** Cases are opened one at a time after the rows commit, each guarded, and an item records its `caseId` as soon as it has one. If case 3 of 5 fails the report stays submitted, the first two keep their cases, and re-running submit fills only the gaps. Wrapping five external-effect calls in a transaction would instead roll back a report the cleaner was already told was sent. Annotated photos are flattened at submit via `lib/qa/annotation-composite.ts#ensureFlattened` (idempotent, best-effort) so cases attach the composite rather than an un-marked original — the bare overlay is marks on transparency and renders as a black tile once anything converts it to JPEG.

### B11. Damage investigation — admin and client (D2, 2026-08)

`GET /api/admin/damage/:reportId` and `GET /api/client/damage/:reportId` render the same report through one assembler, `lib/damage/investigation.ts`. The audience is a parameter, not a second query: two separately-shaped reads are how a field ends up visible on one screen and hidden on the other.

**What the client never receives.** `estimatedCost` is nulled for CLIENT — a client seeing an internal working figure would read it as a quote — as are `CaseTransition.reason` (internal triage notes) and the reviewer's name. They are removed from the payload before it leaves the server, so a template mistake cannot leak them; `tests/lib/damage-investigation.test.ts` asserts the serialised JSON contains neither the cost nor the note text. The rendering rule and the security rule are deliberately different mechanisms.

**Client access is decided in the query, not after it.** `getDamageInvestigationForClient` matches on `clientVisible: true`, a non-DRAFT status, and `property.clientId` in the `where` clause. A report failing any of those returns the same 404 as one that does not exist — a 403 would confirm the report is real, telling one client that another client's property has damage on file.

**Release is two writes in one transaction.** `reviewDamageReport` (`lib/damage/review.ts`) sets `DamageReport.clientVisible` *and* flips the linked `IssueTicket.clientVisible`/`clientCanReply` together, because the client also reads damage as cases through the cases workspace. Lifting only the report would show a report whose cases stay invisible; lifting only the cases would leak damage the admin has not approved. Retraction is the same call with `release: false`, so a mistaken release can be taken back and the cases go with it. It refuses to act on a DRAFT — an unsubmitted report is the cleaner's working notes.

**Status is read live, never snapshotted.** Case state, the linked maintenance status, the assigned worker and the transition timeline are all joined at read time, so the page reflects whatever CP-7's sync currently says rather than a copy taken at submit. Photos resolve to the flattened composite when one exists and the original otherwise — never the bare overlay, which is marks on transparency and renders as a black tile once anything converts it to JPEG.

**Cost is admin-only in three independent places**: absent from every cleaner schema (`lib/damage/validation.ts`), nulled in the client view model, and written only by the admin-role route. Any one alone would be a single point of failure.

### B12. The damage report document + verification (D3, 2026-08)

`GET /api/damage/:reportId/report` renders the damage PDF (`?format=html` for a preview). It follows `lib/reports/qa-report.ts`, **not** `generator.ts`: built on demand and never persisted. The cleaning report is stored because one exists per completed job; damage is not like that — a job can produce several reports, admins edit costs afterwards, and a released report can be retracted, so a stored HTML blob would go stale on any of those. `Report.jobId` is UNIQUE anyway, so there is nowhere to put a second document per job.

**The audience is derived from the session, never from a query parameter** — the same decision the QA report route made. The internal copy carries per-item repair costs; if audience were a parameter, a client could ask for it by editing the URL. A client must additionally clear the same gate as the on-screen page, and that check calls `getDamageInvestigationForClient` rather than reimplementing the rule, so the PDF can never be obtainable when the page is not. Redaction itself is not re-implemented in the template: the audience is handed to `lib/damage/investigation.ts`, the one place that decides it.

**Images are presigned, not public URLs.** Playwright renders on `about:blank` with no session, so a cookie-gated or private-bucket URL arrives as a broken image. `toInvestigationViewModel` therefore takes a `resolveKeyUrl` seam (the same pattern `report-view-model.ts` uses): the in-app pages pass the default public resolver, the PDF passes a presigning map built in one pass up front.

**`ReportVerification` gained a kind.** It was one-code-per-job — `jobId` UNIQUE, no discriminator — so a damage PDF could not carry its own `/verify` code at all. Now: a CLEANING row keeps `jobId` set with `damageReportId` NULL, and `@@unique([jobId, kind])` preserves the old one-per-job guarantee; a DAMAGE row leaves `jobId` NULL (Postgres treats NULLs as distinct, so a job with several damage reports gets a code for each) and is made unique by `damageReportId`. Migration `20260816010000_report_verification_kind` is backfill-free — every existing row is a cleaning verification, so the `CLEANING` default is already correct for all of them.

**The public damage check says less than the cleaning one.** A code can be forwarded to anyone, so `buildDamageVerificationVm` returns only that the report exists, its suburb, date, reporter's FIRST name and the item COUNT — no descriptions, severities, causes, photos or costs. `tests/lib/report-verification.test.ts` pins the exact key set of both VMs; that assertion is what caught the new `kind` field and forced a deliberate judgement that it is safe to publish.

### B13. Job-level Forms & QA centre (D4, 2026-08)

One panel per job listing every document it produced — cleaning report, QA report, and each damage report — on the admin job detail (`forms` tab) and, in a reduced form, on the client job page. Damage reports were previously reachable from **nowhere** on a job: a submitted report existed only as its cases, so nothing led back to the report that grouped them.

**One download dialog, not three.** `components/v2/shared/report-download-dialog.tsx` handles all three kinds, tone-coded — cleaning gold, damage danger, QA info — built on the existing `EModal` and `downloadFromApi`. This was a stated requirement and the codebase shows why: four hand-rolled `fixed inset-0` modal shells already exist (`jobs-workspace`, `quotes-pipeline`, `job-action-hub`, `reports-manager`), and damage would have been the fifth.

**"Include the cleaning report" is chosen at download time**, not baked into the damage PDF, because whether the two belong together is a per-download judgement — an insurer wants both, an internal triage does not. The two arrive as separate files rather than merged: merging PDFs would add a dependency, and two named files can be forwarded selectively. They download sequentially, because concurrent renders contend for the single-flight Playwright lock anyway.

The client card renders **nothing** when there are no released reports — an empty "Damage" heading on every clean would imply damage is expected — and the client list query filters on released + non-draft + own-property, so an unreleased report is absent rather than hidden.

### B14. Voiding a damage submission, and the client's sign-off (D4, 2026-08)

**Reports are never hard-deleted.** An admin VOIDs a submission, and every void appends a `DamageReportVoid` row — a list rather than a field, because a report can be voided, redone and voided again, and each is an audit event carrying who, when, why and which mode.

Two modes, chosen at void time because the right answer depends on why it is being sent back. **KEEP_AND_REOPEN** leaves items and photos untouched and undoes the submission, so the cleaner corrects what is already there. **CLEAR_AND_REDO** archives the items into `DamageReportVoid.archivedItems` as JSON *and then* clears them, so the cleaner starts from a blank form — nothing is destroyed, and the S3 objects behind the photos are never touched.

**The reason is mandatory (10 characters minimum) and shown to the cleaner verbatim**, with a notification. Voiding somebody's documented work without saying why is how the same mistake gets made twice.

**A void un-releases the report and its cases together**, for the same reason release lifts them together, and posts an internal `CaseComment` on every linked case recording the void and its reason. That comment is the stale flag. It is deliberately *not* a case status change: the repair may genuinely still be needed, and closing the case would tell CP-7 to resolve a maintenance item nobody has fixed. A DRAFT cannot be voided — there is no submission to undo, and voiding one would only destroy in-progress work.

**KEEP_AND_REOPEN forced a fix in the draft writer.** `saveDamageDraft` replaces items wholesale, which silently dropped `caseId`; a reopened report would then have resubmitted into a *second* case per damage and CP-7 would have raised duplicate repairs for one fault. The form echoes each server item id back as `clientId`, and the save now carries the existing `caseId` across on that match.

**Client verification is two things, and neither substitutes for the other.** The public `/verify` code proves the document is genuine to anyone holding it — including an insurer with no portal login — while `DamageReport.acknowledgedAt`/`acknowledgedById`/`acknowledgedName` records that the client themselves read and accepted it. Sign-off is once: a repeat POST returns the existing record rather than restamping it, so a double-tap is not a failure, and "when did the client accept this" has one answer. The eligibility gate is the same query the read path uses, so a client can never sign something they were never shown. Voiding nulls the acknowledgement — a signature belongs to the report the client actually read, not to whatever replaces it.

**Void history is admin-only** (`tests/lib/damage-investigation.test.ts` asserts the client payload contains neither the reasons nor the mode): "we sent this back twice" reads as doubt about the damage rather than about the paperwork. The client's own signature is shown to both sides.

### B15. VA logins — schema and the client-portal chokepoint (V1, 2026-08)

A `Role.VA` acts on behalf of a client. `VaTeam` (many teams per client, many logins per team) owns the `clientId`, the `permissions` Json and the `propertyIds` scope — **the user row does not**. Revoking an agency is therefore one row, and a departing staff member never leaves behind a login carrying its own private grant. `User.vaTeamId` is the only link, and it is `ON DELETE SET NULL`: deleting a team leaves the person with no team, which the chokepoint reads as *no access* rather than *all access*.

**`requireClientPortal()` (`lib/auth/client-portal.ts`) is the one place that authorises a portal request**, returning `{clientId, actor, userId, team, permissions, propertyIds, visibility, actorLabel}`. Adding `Role.VA` to the ~36 existing `requireRole([Role.CLIENT])` calls would compile and look fine, and would be wrong in a way nobody notices for months: each route would then need its own permission check and its own property filter, on top of the **six different client-id resolution patterns those routes already use** (several of which silently ignore per-client `portalVisibilityOverrides` by passing raw `AppSettings` to `isClientModuleEnabled`). One function, one set of rules.

**The actor is never swapped.** Impersonation swaps `session.user` to the target and lets downstream code stay ignorant, which is safe because the admin could already read everything the target can. A VA is the opposite — their access is a *subset* — so subject (`clientId`) and actor (`actor`/`userId`/`team`) are returned separately and both stay visible. `auditClientPortalAction` writes the real acting user to `AuditLog.userId` (as the impersonation route does) and carries the delegation in `after`, because `AuditLog` has a single actor column and a VA's action would otherwise be indistinguishable from the client's.

**Money is not a permission.** A VA never approves a quote or extra, never approves a cost, never pays an invoice. Those are absent from the grantable set *and* enforced independently by `assertVaMayAct`, so no permissions blob — hand-edited, half-written, or from an older shape — can switch one on. Invoice *visibility* is separate and grantable: a client may want an assistant reconciling invoices they cannot pay. `parseVaPermissions` fails closed on anything malformed, and requires boolean `true` (the string `"false"` is truthy in JS and must not grant).

**Middleware had to change too.** `middleware.ts` bounced any non-`CLIENT` role off `/client/**` and `/v2/client/**` before route code ran, so an API-only chokepoint could never have worked. Middleware now decides only *which portal* a VA may enter; what they may do inside remains `requireClientPortal()`'s job.

**Known gaps.** Seven client routes now go through the chokepoint (`properties`, `properties/[id]`, `jobs`, `laundry`, `available-slots`, `booking`, `attention-counts`); the remaining 28 still call `requireRole([Role.CLIENT])` and reject a VA outright — fail-closed, so the gap costs reach, never safety. The approvals trio resolves a *set* of client ids by email match, which the chokepoint preserves via `clientIds` for the CLIENT actor only. The v2 client pages still wrap their portal context in `.catch(() => null)` — a fail-open pattern that must not be carried into the rest of the migration.

### B16. VA team management — the half that makes a VA possible (V2, 2026-08)

B15 built the lock; nothing could cut a key. `VaTeam` was referenced only by `requireClientPortal` and `lib/va/permissions.ts`, and no code path in the product could create a team, attach a login to one, or set its grants — so `Role.VA` was unreachable in practice. `lib/va/teams.ts` plus four routes under `/api/client/va-teams` and the `/v2/client/team` page are that missing half.

**Managing a team is not a permission — it is not delegable at all.** There is deliberately no `team` key in `VA_PERMISSION_KEYS`; `assertTeamManager` refuses any VA actor outright, on the actor rather than on a grant. This is the money rule taken one step further: the money rule stops a VA approving a spend, but a VA who could edit their own team could simply tick the boxes and then approve it, which would make every other check decorative. The page guards with `requireRole([Role.CLIENT])` and the nav item is hidden from a VA via `useSession`, so the refusal is stated three times rather than left to the API alone.

**Property scope is validated against ownership, not trusted.** `VaTeam.propertyIds` is a Json filter with no foreign key, so nothing in the database stops a client posting *another* client’s property id and scoping a VA onto it. Every write checks the ids belong to the acting client and **rejects unknown ones rather than quietly dropping them** — a scope that silently shrinks leaves a client believing their assistant can see something they cannot.

**The invitation flow needed no VA special case.** `lib/auth/invitations.ts` already takes a userId and reads the role off the user, and `/accept-invite/[token]` never gated on role — so inviting a VA is the generic flow with `Role.VA`. The account is created **without a password hash**, and `auth-options` refuses any credentials login without one, so the row is inert until the person accepts. An email already belonging to any other account is refused (`EMAIL_IN_USE`) because re-pointing a live login at a team would be an account takeover; re-inviting someone already on *this* team is treated as a resend, since the first email is the one that gets lost.

**Removal is two writes, and both matter.** Clearing `vaTeamId` makes the chokepoint fail closed for them; `isActive: false` stops the credential signing in at all. Without the second, a removed assistant still holds a working login that merely resolves to no client. Deleting a whole team does the same to its members first — the `VaTeamMembers` relation is `ON DELETE SET NULL`, which would otherwise leave live logins behind as orphans.

**Send failures are reported, not swallowed.** The invitation row is valid whether or not the email left the building, so the API returns `emailSent`/`emailError` and the UI says which happened, letting the client resend or pass the link on themselves. Covered by `tests/lib/va-teams.test.ts` (15 tests, all on the invariants above).

### B16b. VA go-live: pages, nav and the remaining routes (2026-08-19)

B15 built the chokepoint, B16 the management UI — but every v2 client PAGE still guarded with requireRole([Role.CLIENT]), so a VA passed middleware and bounced off all 22 pages. The fix is one page-side twin, **requireClientPortalPage({ module?, permission? })** (lib/auth/client-portal.ts): same chokepoint underneath, but failures REDIRECT (signed-out → /login, wrong role or missing grant → /unauthorized, hidden module → portal home) because a page answers a person mid-navigation, not a machine. 13 pages migrated with a session shim (portalCtx.userId keeps every downstream resolver call working); approvals/quotes/shopping/stock-runs/referrals/profile/settings/team stay CLIENT-only by design.

**getClientPortalContext is now VA-aware**: it resolves the client THROUGH resolvePortalScopeForUser instead of user.clientId (null for a VA — the exact fail-open B15 flagged), so per-client visibility overrides reach VAs and every route still calling it inherited the fix.

**Calendar and inventory stopped resolving user.clientId directly** and now feed propertyScopeWhere(portalCtx) — a scoped VA sees only granted properties, and the inventory filter chips are built from the scoped list so an ungranted property is never offered.

**Routes migrated to the chokepoint this pass** (now 21 of 41): messages (GET+POST, "messages"), reports ("reports", merged visibility instead of raw settings), cases (GET+POST, "maintenance", with NEW ownership validation — body propertyId/jobId were previously trusted), jobs/[id] (any VA, scope-narrowed), cancel/reschedule/skip/requests/task-requests ("bookings" — closing the last 2 V1 routes from the queue), damage/[reportId] + jobs/[id]/damage-reports ("damage"). findJobInScope() joins propertyScopeWhere as the standard job-bound scope check.

**Nav is gated server-authoritatively**: /api/client/attention-counts now returns { portal: { actor, permissions } } alongside counts; useClientPortalCounts (a separate hook — five other portals share the plain one) feeds VA_NAV_GATE in the client layout. Unknown destinations default to client-only, so a new nav item is hidden from VAs until someone decides otherwise. Pay buttons on money/finance render only for actor CLIENT — the API refused a VA anyway, but offering a tap that bounces is an issue, not a safeguard.

### B16c. Admin-side VA onboarding — the invite an agency actually needs (2026-08-20)

B16 let a CLIENT create their own assistants; nobody could do it FOR them. Real onboarding is an admin sitting with a new account, standing up an offshore team of five in one pass — so `POST /api/admin/va-invites` (ADMIN/OPS_MANAGER) plus the **Assistants** tab on /v2/admin/accounts is that path, and the client picks up management afterwards on their existing /v2/client/team page.

**The client link is compulsory, in two independent places.** `lib/validations/user.ts` now accepts `VA` as an admin-creatable role but a superRefine makes `clientId` required for it, and the invite route resolves the client from the TEAM. A VA with no client is not a limited account, it is an unreachable one: `requireClientPortal()` deliberately refuses to fall back to `user.clientId`, so it would resolve to nothing at all.

**One email to the client, listing only who actually got in.** Bulk invite is the point — five invitations must not become five separate "someone new can see your properties" notices. Per-member errors are isolated (one bad address cannot cost the other four their invitations) and the notification is assembled from the successes only, skipped entirely if none succeeded. `EMAIL_IN_USE` surfaces as "Already used by another account" rather than re-pointing a live login at this team, which would be an account takeover.

**Starting permissions are offered for a NEW team and never for an existing one.** An assistant with an empty grant set is useless on day one, so the admin screen exposes `VA_PERMISSION_KEYS` as toggles and an optional property scope when naming a new team. Adding a sixth member to an existing team does NOT touch its grants — the client may have deliberately narrowed them, and an admin widening a team as a side effect of adding staff is exactly the silent-regrant this model exists to prevent.

**The route is a thin wrapper over `lib/va/teams.ts`, on purpose.** `createVaTeam`/`inviteVaMember` already own temp-password generation, the invitation row, the fail-closed permission parse and the ownership check on property scope. A second implementation here is the same two-copies-of-one-rule that produced the access-info divergence. For the same reason the permission LABELS moved to `VA_PERMISSION_LABELS` in lib/va/permissions.ts and both screens read them — a grant described differently in two places is a grant the client does not understand.

### B16d. VA portal identity, detail-page guards, and accounts by account type (2026-08-20)

**The VA portal crashed on every detail page.** B16b migrated 13 client LIST pages to `requireClientPortalPage`, but `jobs/[id]`, `properties/[id]` and `damage/[reportId]` still called `requireRole([Role.CLIENT])`. Job detail takes any VA (scope narrows it), property detail takes `properties`, damage takes `damage` — each page now matching the endpoint behind it.

**The portal stopped pretending to be the client.** The shell labelled a signed-in VA "Client". It now reads "Assistant · <client>", and a standing banner names the assistant, the account they are working in and their team. **Accounts is now one tab per ACCOUNT TYPE** — Team, Cleaners, Client logins, Assistants, Partners — replacing "staff" (every login behind a dropdown) and "clients" (a second copy of the client list). The clientId is resolved from the TEAM, never the body. `Role.VA` is deliberately absent from the staff manager: an assistant login is meaningless without its VaTeam, which owns the client link, the grants and the property scope, so editing one as a loose user row could strand it. After every write the client payload is refetched rather than patched locally — the client may be editing the same team from their own portal, and optimistic state would show one grant while the chokepoint enforced another.

### B18. Client bookings become requests, not jobs (2026-08-20)

A client self-serve booking created a `Job` the moment they tapped submit. Nobody had agreed to it, nobody had checked whether a cleaner was free that day, and it landed on the jobs board indistinguishable from work the office had actually scheduled — then sat UNASSIGNED until someone noticed, or got handed on the day to whoever was left.

**The request lives on the QuoteLead the flow already created.** `status: NEW` plus `structuredContext.createdVia === "client_booking"`, now also carrying jobType, scheduledDate and requestedByUserId so approval never has to re-derive what was asked for. No new table and no migration: a lead already means "someone wants work done, we have not committed yet", CONVERTED already means "this became a job", and declining is LOST. `lib/booking/requests.ts` owns all of it.

**Deliberately NOT a new JobStatus.** Statuses are read by dozens of lists, filters and aggregates across three portals, and this codebase has repeatedly shipped one that several of those never learned about — EN_ROUTE most recently, missing from four lists. A booking with no job cannot be missed by a job query that does not know it exists.

**Approval is where the job is created, and it is race-safe.** `approveBookingRequest` flips the lead to CONVERTED with an `updateMany` guarded on `status: NEW` BEFORE creating the job, inside one transaction. Two admins clicking approve together would otherwise produce two jobs for one booking; the second update matches no row and the transaction rolls back. An admin may approve on a different date than requested, and the move is audit-logged because the client will notice it.

**Availability is the point of the queue.** `getTeamAvailability(dateKey)` counts DISTINCT active cleaners already holding work on that Sydney day — one cleaner with three cleans is one unavailable person, and counting jobs would make a productive day look overbooked. The Booking requests queue shows "N of M cleaners free" per request, in red at zero, and the confirm button then reads "Nobody free — approve anyway" rather than blocking: it is the office's call, made with the fact in front of them. Availability is computed per distinct date, so ten bookings for one Saturday cost one lookup.

**The client is told the outcome.** Approve and decline both return a `BookingDecisionNotice` — built from the lead the decision already loaded rather than re-read afterwards, since a second read could disagree with what was actually decided — and the route emails the client. The client RECORD's address wins over the copy snapshotted onto the lead, which may be months stale. Best-effort and after the fact: the job exists whether or not the mail lands, and failing the request on a bounce would leave an admin re-clicking approve on something already approved, so the outcome is reported instead. Declining REQUIRES a typed reason (the API rejects a blank one) and it is emailed — a booking that dies in silence becomes a phone call anyway. Approve can also move the date inline, because the office can usually do the job just not on the day asked for, and decline-and-rebook was a heavy way to change one field.

**Preferred-cleaner auto-assignment moved behind approval.** Holding a cleaner for work that may be declined is the same double-booking this change exists to prevent. The client's confirmation copy no longer quotes a job number, because there is not one yet.

### B19. Client request rules, and the VA case dead end (2026-08-20)

**A client could ask to cancel a clean a cleaner was standing in the middle of.** All three request routes — cancel, reschedule, skip — blocked only COMPLETED and INVOICED, so EN_ROUTE, IN_PROGRESS, PAUSED, SUBMITTED and QA_REVIEW all sailed through. The request was created, queued, and read by an admin hours after the work had finished: a decision about something that had already happened.

**The rule was written out four times.** Three routes plus `job-action-hub.tsx`, which gated its buttons on its own `status === "COMPLETED" || status === "INVOICED"` — so the portal kept OFFERING cancel and reschedule mid-clean. `lib/jobs/client-request-rules.ts` is now the single copy, and `isClientSchedulable` is what the UI asks. The module imports `JobStatus` as a TYPE only: the cleaner-facing bundle shares this rule, and a value import would drag @prisma/client into the browser. String literals are still checked against the enum, so a typo or a removed status fails tsc. A test asserts the two exported helpers agree across every member of the enum, which is the drift this module exists to stop.

**Refusals are 409, not 400**, because nothing about the request was malformed — the job moved on. The message says *"your cleaner is already on the way… please call us"* rather than a flat refusal, because a fact the client can act on is what stops them retrying.

**A VA who raised a case could not open it.** `/api/client/cases/[id]` still used `requireRole([Role.CLIENT])` while the LIST route beside it had been migrated in B16b — the fourth list-migrated/detail-missed pair after jobs, properties and damage. It carried a second bug behind the first: the handler read `User.clientId`, which is null for a VA, so even past the role check it answered "Client profile missing". Both handlers now go through `requireClientPortal({ permission: "maintenance" })`, and the case comment's actor label is the ACTING person — an assistant's reply must not read as though the client wrote it.

`/api/client/properties/[id]/preferred-cleaner` moved to the chokepoint under `properties`: choosing who cleans a property is ops work, not a money decision.

### B20. Cleaner bulk upload — bounded, ordered, and honest about failures (2026-08-20)

**The "random upload issues" were unbounded concurrency.** `prepareAndUploadFiles` did `files.map()` into `Promise.allSettled`, so a cleaner selecting thirty photos opened thirty simultaneous multipart POSTs AND thirty canvas compressions on a phone. Browsers run about six connections per host, so the rest queued at the socket layer where a flaky mobile connection killed them silently; the compressions competed for memory at the same moment, which is what took whole tabs down on older handsets. A pool of three is not a throttle — uploads that are not fighting each other for bandwidth finish sooner, and the ones that finish stay finished.

**Order is now the order the cleaner picked.** Each worker claims the next index and writes its result into that slot, rather than pushing on completion, so the gallery no longer reflects whichever upload happened to win the network.

**Failures are named.** The pipeline returned a bare `failedCount`, so "3 files failed" left a cleaner re-picking all thirty to work out which. It now returns `{ name, reason }` per failure and both call sites print them.

**One retry, and only where a retry could help.** A 4xx is the server saying no (too large, wrong type, signed out) and is thrown as `PermanentUploadError` — retrying only makes the cleaner wait longer for the same answer. 5xx and network errors get one more attempt after 700ms, because cleaners work in stairwells and basements and a connection dropped mid-POST is not worth showing a person.

**Progress counts instead of spinning.** On a slow connection a lump spinner is indistinguishable from a hang, and cleaners kill the tab; the control now reads "Uploading 4 of 12".

### B21. Admin jobs list — the row that had eight children in a seven-column grid (2026-08-20)

At `lg` those buttons are `opacity-0` until hover, so the wrap was invisible while still claiming a full row of height — the empty band beside every job, and the reason rows stood roughly twice as tall as their content. Seven children now, and the actions column keeps a reserved `min-w-[9rem]` so the row does not reflow when they fade in.

**Property names stopped being abbreviations.** The name is what an admin scans for, so it takes the flexible track and wraps (`overflow-wrap:anywhere`) instead of truncating — "Jackson-Pr…" is not an identifier. Client and cleaner still truncate because their columns are fixed, but both now carry a `title`, so the full value is one hover away rather than lost.

### B22. Cleaner task evidence reached nobody (2026-08-20)

A cleaner finishing an admin- or client-requested task uploads photos and writes a note. Both were stored correctly and displayed nowhere.

**Three filters, one symptom.** `updateJobTasksFromSubmission` writes proof as `JobTaskAttachment` rows with `kind: COMPLETION_PROOF` (or `FAILURE_PROOF`), and the note as a `TASK_COMPLETED` / `TASK_NOT_COMPLETED` event. **Admin-raised tasks were invisible as well.** The detail page scoped `jobTasks` to `source: CLIENT`, so an admin could attach a task to a job and never learn whether it was done. Now `CLIENT` and `ADMIN` both. `CARRY_FORWARD` stays out because those belong to the job they were carried TO and surface there on their own.

**Reference images and proof stay separate** rather than merging into one attachment list. One is what was asked for, the other is what came back; merging them would make an unfinished task look evidenced.

### B23. Task proof in the report — the field id that nothing wrote to (2026-08-20)

B22 surfaced cleaner task evidence in the admin UI. It was still missing from the report PDF, and the reason sat upstream of the report entirely.

**Nothing ever wrote media under `proofFieldId`.** The submit route computes `unifiedJobTaskProofFieldId(taskId)` for each task and stores it in the `__jobTasks` snapshot, and the report's task section looks up `submission.media` by that field id. But `SubmissionMedia` rows are built from `uploads`, while task proof arrives as `body.jobTasks[].proofKeys` — so the report searched for media nothing had ever stored. Writing those keys into the media rows under their proof field id makes the report's EXISTING task section work with no template change.

**Merged for the media rows only, never back into `uploads`.** The required-photo validation reads `uploads`, and a task photo must not satisfy a form field's requirement.

**The admin's choice is a job-level flag, not a download variant.** `JobMeta.includeTaskPhotosInReport` (no migration — it rides in `Job.internalNotes`) is read by `buildReportHtml` and honoured by `buildUnifiedJobTasksHtml`. A per-download query param was rejected: the report is generated once and served to everyone, so a per-click variant would quietly change what the client sees too. Toggling it PATCHes the job and calls the existing regenerate endpoint, because a stored report does not care about a setting until it is rebuilt.

**Excluded photos are still marked `usedMediaIds`.** That set is what keeps media OUT of the general gallery lower down the report; skipping it when the flag is off would not hide the photos, it would relocate them somewhere with less explanation.

**Absent means true.** Every job predating the flag keeps its task photos on the next regeneration. Two persistence bugs surfaced only because the round trip was tested: `hasStructuredData` did not count the flag (so a job whose only meta was this setting serialised back to a plain note and lost it), and the JSON writer omitted the key entirely. Both would have looked correct in the UI right up until a reload.

### B24. A reschedule is not a task (2026-08-20)

The reschedule and cancel routes tag `metadata.type` instead, so they never matched it. One predicate, `isAdminOnlyRequest`, now recognises BOTH shapes — which also clears the rows already sitting in cleaners' lists rather than only fixing new ones.

**The auto-approve sweep never had the guard at all.** `autoApprovePendingClientJobTasks` set `visibleToCleaner: true` unconditionally, so anything nobody decided before the job started became cleaner work by default — including the very light requests the admin path was careful to exclude. ### B25. Video uploads — ffmpeg was running inside the request (2026-08-20)

B20 bounded the upload pool, which fixed the random photo failures. Videos kept failing almost every time, for a different reason entirely.

**The transcode ran inside the POST.** `/api/uploads/direct` spawned ffmpeg at crf 34 and awaited it before responding, so the cleaner's phone held the connection open for the whole encode. A 100MB clip takes minutes on a modest box; the proxy timed the request out long before that, and the cleaner saw a failure for a file that had uploaded perfectly. The client then retried — re-uploading AND re-transcoding the same video. One clip could occupy the server for ten minutes and still be reported as failed.

**The original now goes to S3 first and the response goes out immediately**, with compression continuing in the background against the same key. The URL handed to the client is final either way, so no database row is revisited; if the transcode fails or the process dies, the original stays, and a bigger file is a far better outcome than a missing one. Temp files are cleaned by the background job on success and by the request on failure — deleting them in a plain `finally` would have pulled the rug from under the encoder.

**Uploads moved from fetch to XHR.** fetch cannot report UPLOAD progress, only download, so a cleaner sending a large clip watched a spinner that never moved, concluded the app had hung, and killed it partway through. `xhr.upload.onprogress` drives a real per-file bar.

**Videos get their own lane.** Three 80MB uploads sharing one phone's uplink each take three times as long and all three stay exposed to the same dropout, so heavy files run one at a time while photos keep flowing four at a time. Serialising the heavy lane makes a video batch finish sooner in practice, not later.

**Large files are never auto-retried.** Re-sending 100MB over mobile data to paper over a blip that may well repeat is worse than surfacing it. Anything over 25MB goes straight to the failed list with a Retry button; small files still get one automatic second attempt.

**The failed list persists and holds the File objects.** A message that disappears is no use to someone who looked away while thirty photos uploaded, and re-picking is often impossible on a phone — the camera-roll entry for a photo taken a minute ago is not easy to find again. Retry re-sends exactly the files that failed.

### B26. Early check-in — two notices, one of them wrong (2026-08-20)

A cleaner opening a job with an early check-in saw "Same-day check-in — guest arrives 15:00" sitting directly above "Early check-in — finish before 12:00". Two banners for one event, giving two deadlines, one of which described a time nobody was arriving.

An early check-in also implies same-day even when the sync flag is missing, because a guest is arriving today either way.

**Late checkout stays separate.** It is the other end of the day, a different instruction (do not START before), and it can be true at the same time as an arrival.

**The duplicate render was a second bug.** `TimingRuleBanners` was rendered by `job-workspace.tsx` above every stage AND again by `stage-setup.tsx` — and the stage copy was never passed `sameDayCheckin`, so the second banner was missing the very arrival it existed to warn about. The workspace copy is the one that survives.

## Section C — Laundry operation & the QA/accountability system

### C1. Laundry scheduling engine

The linen cycle for Airbnb turnovers is generated by the planner in `lib/laundry/planner.ts`. Each eligible turnover job (jobType `AIRBNB_TURNOVER`, not a rework, property has `laundryEnabled`, job not `INVOICED`) gets exactly one `LaundryTask` (Prisma model in `prisma/schema.prisma`, `jobId @unique`) carrying `pickupDate`, `dropoffDate`, `status` (enum `LaundryStatus`: PENDING / CONFIRMED / PICKED_UP / DROPPED / FLAGGED / SKIPPED_PICKUP), and optional `flagReason` (`NO_WINDOW`, `BUFFER_REQUIRED`, `EXPRESS_OR_EXTRA_LINEN_REQUIRED`) + `flagNotes`.

**The normal rule** (`computeDraftItem`): pickup = clean date + 1 day; drop-off = the day before the *next known clean* at the same property (found by `getNextTurnoverCleanDate`), never earlier than pickup + 1 (the 24h laundering minimum). Every draft item is tagged with a **scenario** based on the gap to the next clean: `BACK_TO_BACK` (gap ≤ 1 day), `MICRO_CYCLE` (≤ 3), `COMPRESSED` (> 3), or `FALLBACK` when no future clean exists yet. In the fallback case the drop-off is either a fast return (`fastReturnDaysWhenNoNextClean`, capped by `maxOutdoorDays`) so linen is on-site for late bookings, or the full outdoor window — both from `settings.laundryOperations`. **Buffer sets**: a `BACK_TO_BACK` scenario with `property.linenBufferSets <= 0` flags the task `EXPRESS_OR_EXTRA_LINEN_REQUIRED`; if the computed window ever collapses below 24h the task is flagged `NO_WINDOW`. All dates are normalized to `startOfDay` and keyed to the Sydney calendar day (`todaySydneyDateOnlyForLaundryPlanner`).

**Triggers.** Three paths run the planner:
1. *Job creation* — `ensureLaundryTaskForJob(jobId)` is called when a turnover job appears; it no-ops for reworks, laundry-off properties, and jobs that already have a task.
2. *Weekly plan* — `buildLaundryPlanDraft(weekStart)` computes a sorted draft (pickup date → suburb → property) which an admin reviews and applies via `applyLaundryPlanDraft`; `generateWeeklyLaundryPlan` is the draft+apply shorthand used by the scheduled weekly job.
3. *Per-property resync* — `refreshLaundrySyncDraftForProperty` / `buildLaundrySyncDraft` recompute desired dates for all future jobs at one property (used when clean dates move, e.g. after an iCal sync) and stage CREATE/UPDATE items into a pending sync-draft store (`lib/laundry/sync-draft.ts`) for review, skipping tasks that are already completed.

**Planner-respects-human-status fix (2026-07).** `canPlannerOverrideStatus(task)` is the single rule: the planner only owns a task's status while it is `PENDING` or `FLAGGED`. Anything a human moved — `CONFIRMED`, `PICKED_UP`, `DROPPED`, and critically `SKIPPED_PICKUP` (what an admin soft-delete and a cleaner's "no pickup required" outcome both write) — is preserved. `applyLaundryPlanDraft` used to clobber status unconditionally on its upsert; it now pre-loads existing tasks and keeps human-owned statuses (`keepHumanStatus`), so a weekly plan run can no longer resurrect deleted sets. The sync-draft path applies the same rule and also compares **raw instants** rather than day-normalized dates, which matters for key-lost tasks (below).

**Key-lost mode (2026-07).** When a property's spare key is lost (`Property.keyLostMode`), the driver cannot enter alone, so *both* pickup and drop-off are scheduled **on the clean day itself, after the clean starts**. `computeDraftItem` short-circuits at the top into `computeKeyLostDraftItem` in `lib/laundry/key-lost.ts` — the normal path is deliberately untouched, guarded only by that single branch point. The service time comes from `lib/laundry/clean-start.ts`: `resolveKeyLostServiceTime` returns **12:30** when the job has an enabled late-checkout timing rule (parsed from job `internalNotes` meta), otherwise **10:00**; `resolveCleanStart` (used by the plan-brief deadline check) resolves the actual clean start with precedence late-checkout rule → `job.startTime` → `property.defaultCheckoutTime` → 10:00. Key-lost tasks store a real local wall-clock time (`atTimeOnDay`, deliberately `setHours` not UTC so the boards render "10:00" correctly), unlike normal tasks which sit at midnight. The scenario is `KEY_LOST` and the `flagNotes` carry the `KEY_LOST` marker tag (`isKeyLostNotes`), which is what persists onto the row so the boards and week feed can badge the task even after the property is toggled back. Toggling the mode triggers a per-property resync; the raw-instant comparison in `buildLaundrySyncDraft` is what lets the resync both apply the 10:00/12:30 times to pending tasks and move stale timed tasks back to midnight when the mode is switched off. Both branches are pinned by `tests/lib/key-lost.test.ts`.

### C2. Laundry task lifecycle

The driver-facing verbs live in `app/api/laundry/[taskId]/status/route.ts` (POST). Every transition writes a `LaundryConfirmation` row whose JSON `notes` carry an `event` discriminator plus the structured payload — this is the audit trail, the media index, and (later) the actor-attribution source for team stats.

- **Pickup** (`PICKED_UP`, only from PENDING/CONFIRMED): requires `confirm:true` and a `bagCount` (1–50); optional pickup photo and a **key photo** (`pickupKeyPhotoUrl` — evidence the key was taken).
- **Drop** (`DROPPED`; the wire also accepts legacy `RETURNED`, mapped to DROPPED; only from PICKED_UP): requires a drop-off location, a drop photo when `settings.laundryPortalVisibility.requireDropoffPhoto` is on, and — when dropping **earlier** than the scheduled `dropoffDate` — an `earlyDropoffReason` (setting-gated). Records `loadWeightKg` → `bagWeightKg`, `totalPrice` → `dropoffCostAud`, a receipt image, an optional external `supplierId` (`LaundrySupplier`), and a drop-side key photo. Completing a pickup/drop also best-effort stamps `completedAt` on the matching stop of any ACTIVE `LaundryRoute` (`markActiveRouteStopComplete`), so the runner advances automatically.
- **Reverts**: `REVERT_TO_CONFIRMED` (from PICKED_UP/DROPPED, clears both timestamps) and `REVERT_TO_PICKED_UP` (from DROPPED). Each writes its own confirmation event, which is why downstream consumers (e.g. `pickDropConfirmation`) select the *latest DROPPED-event* row instead of trusting the current status.
- **Failed pickup — reschedule** (`FAILED_PICKUP_RESCHEDULE`): requires a reason and a new pickup date strictly later than the current one and no later than the drop date; resets status to CONFIRMED, writes an `AuditLog` (`LAUNDRY_FAILED_PICKUP_RESCHEDULED`) and pushes a notification to ADMIN/OPS_MANAGER.
- **Failed pickup — approval request** (`FAILED_PICKUP_REQUEST`): the driver asks for a SKIP or DELETE; the task goes `FLAGGED` with a summary in `flagNotes`, a PENDING-approval confirmation event is filed, and admins are notified — this feeds the "Laundry" queue in the Approval Center.

**Post-completion edits** (PATCH on the same route): only DROPPED tasks; requires an explanatory note (min 3 chars). The handler diffs before/after across bag count, weight, location, price, photos, receipt, supplier and notes, refuses no-op saves, updates the task and the original PICKED_UP/DROPPED confirmation rows in a transaction, appends an `EDIT_COMPLETED` confirmation carrying `changedFields`/before/after, and writes an `EDIT_LAUNDRY_COMPLETION` AuditLog. Team scoping is enforced on both POST and PATCH via `propertyIsVisibleToLaundry`.

**Delete (2026-07).** `DELETE /api/laundry/[taskId]` with pure decision logic in `lib/laundry/deletion.ts`. Because `LaundryTask.jobId` is unique and the planner upserts on it, a plain row delete is not durable — so there are two modes: **SUPPRESS** (default, "Remove from the board") sets `SKIPPED_PICKUP` + `noPickupRequired` + skip reason `ADMIN_INSTRUCTION`, which every board filters out and `canPlannerOverrideStatus` refuses to touch; **PERMANENT** really deletes the row and its confirmations (durable only while the source job stays gone or laundry-disabled — the route computes and reports `mayBeRecreated`). Role rules in `evaluateLaundryDelete`: LAUNDRY users are refused with 403 `USE_APPROVAL_REQUEST` (their path is the failed-pickup approval flow); ADMIN/OPS_MANAGER may delete in-flight tasks; a completed (DROPPED) task 409s unless a full ADMIN passes an explicit `force`. Either mode also strips the task's stops from every route via `stripTaskFromStops` (re-indexing survivors so "stop X of Y" stays honest) and notifies admins. Unit-tested in `tests/lib/laundry-deletion.test.ts`.

**One list of skip reasons (2026-08).** `LAUNDRY_SKIP_REASONS` (`lib/laundry/constants.ts`) had diverged into three copies — the canonical one, and a different set declared independently in both `components/v2/cleaner/job-stages/shared.ts` and `job-workspace.tsx`. The cleaner write path validated the code only as `z.string().max(120)`, so a v2 cleaner could store `LINEN_STILL_DRYING` / `NO_LINEN_ON_SITE` / `NO_PICKUP_REQUIRED` — codes the admin PATCH (`app/api/admin/laundry/[taskId]/route.ts`) z.enums against the canonical list and rejects. Because the admin edit form seeds itself from the stored code and sends it straight back, one such value made **every** admin save on that task 400, not merely an edit to the reason field: dates, status and notes were all blocked, and the task was permanently unsavable. The three lists are now one, imported everywhere, and `lib/validations/job.ts` validates the two cleaner routes with `z.enum` instead of a free string so the bad value can no longer be written. The merged list is the **union** of both sets rather than the old canonical one — the divergent codes already exist in live rows, and keeping only the canonical set would have left exactly the tasks this unblocks still stuck. Adding a code is therefore safe; removing one makes any row still carrying it unsavable again.

### C3. Driver portal

All driver UI is v2 Estate (`app/v2/laundry/**`, components in `components/v2/laundry/`).

**Dashboard** (`app/v2/laundry/page.tsx`, "Today"). Reordered in 2026-07 so the actionable things come first: the **route card** (today's `LaundryRoute` — status, next incomplete stop via `nextIncompleteStop`, link into the builder/runner), then the **plan brief** (`components/v2/laundry/plan-brief.tsx` backed by `GET /api/laundry/plan-brief`), then a trimmed live queue. The plan brief endpoint (`app/api/laundry/plan-brief/route.ts`) returns today/tomorrow pickup+drop counts, keyless weather for the first stop's coordinates (`lib/briefing/weather`), a static AM-peak traffic note (first stop before 09:30 Sydney → "+20% buffer"), NSW public holidays (`lib/dates/au-nsw-holidays`), and **drop-deadline flags**: for each of today's DROP stops the clean start is resolved via `resolveCleanStart` and the cumulative projected arrival (naive model, ACTIVE route order preferred) is compared against it — late drops surface as `{taskId, propertyName, deadline, projectedArrival}`.

**Boards.** Queue (`/v2/laundry/queue`), Runs (`/v2/laundry/runs`) and Tracking (`/v2/laundry/tracking`) render from the shared week feed (`lib/laundry/week-feed.ts` — `fetchLaundryWeekTasks` and the route-candidate variant, all filtered by team visibility). Every Queue card, needs-attention row and Runs card carries a stage-relevant Sydney date chip (2026-07) — pickup date while pending/confirmed, drop-off due once picked up, delivered date once returned; "Today"/"Tomorrow"/weekday-date labels via the shared `sydneyRelativeDayLabel` helper, with overdue dates in the danger tone — so multi-day scopes can't show ambiguous duplicate properties. Status tones/labels are defined on the pages (`DROPPED` renders as "Delivered"; `SKIPPED_PICKUP` as "Skipped").

**Route builder (2026-07)** (`/v2/laundry/route`, `components/v2/laundry/route-builder.tsx`, API `app/api/laundry/route/route.ts`). Candidates are derived server-side in `lib/laundry/route-candidates.ts` as `(taskId, kind)` pairs across three buckets: **TODAY**, **TOMORROW** (pull-forward), and **OVERDUE** (scheduled before today, not DROPPED/SKIPPED, capped at 20 via `ROUTE_OVERDUE_CAP`); pickups are candidates while PENDING/CONFIRMED and `!noPickupRequired`, drops while not DROPPED/SKIPPED. POST validates every stop against the candidate set (plus stops already on the route, so completing one doesn't invalidate a later save), normalizes ordering (`normalizeStops` dedupes on taskId+kind and re-indexes 0..n-1), preserves existing `arrivedAt`/`completedAt` stamps, and upserts the caller's `LaundryRoute` for that Sydney day (`stops` is lean JSON: `{taskId, kind, order, propertyId, arrivedAt?, completedAt?}`). `activate:true` flips it ACTIVE with `startedAt` and **abandons any other ACTIVE route of the same driver** — one live route per driver per day. The pure math (ordering comparator `compareByTimeThenSuburb`, naive travel model at `NAIVE_SPEED_KMH` 35 km/h + `NAIVE_PER_STOP_MIN` 7 min service, `projectArrivalTimes`, `computeDropDeadlineFlags`) lives in `lib/laundry/route-plan.ts`, unit-tested in `tests/lib/route-plan.test.ts`.

**Runner mode + arrival auto-open.** While a route is ACTIVE the driver's browser posts GPS to `POST /api/laundry/location/ping` (`app/api/laundry/location/ping/route.ts`) — rate-limited to one ping per 10s per user, stored in the existing `CleanerLocationPing` table anchored to the job behind the most relevant laundry task (no schema change). Each ping runs `detectRouteArrival`: if the driver is within the **120 m** geofence (`ROUTE_ARRIVAL_RADIUS_M`, haversine via `isArrivedAtStop`) of the next incomplete stop's property, the stop's `arrivedAt` is stamped and the runner UI auto-opens that stop's action. The route map (`components/v2/laundry/route-map.tsx`) shows the live position.

**Allocation persistence (2026-08, ACCESS-4).** The laundry team lives in the free-form `Property.accessInfo` JSON, and both admin property routes used to *rebuild* that JSON from the request body alone — so any key the calling form did not send was reset. The v2 property detail sends only the five access text fields, so **every save from it silently wiped `laundryTeamUserIds` and `attachments`**, and because an empty team means "all active laundry users" (below), wiped properties kept working while notifying everyone — which is why it went unnoticed. Both routes now share `lib/properties/access-info.ts`, whose `buildPropertyAccessInfo(input, stored)` merges the requested `accessInfo` **over the stored row**, so absent keys are preserved (create passes no stored row and behaves as before). Because omission now means "leave alone", the v2 detail sends every key it owns as an explicit value — empty string, not `undefined` — otherwise clearing a field would be impossible; it also now carries a laundry-partner picker (`components/v2/admin/properties/property-detail.tsx`, Access & instructions block) that warns when the allocation is empty. Covered by `tests/lib/property-access-info.test.ts`.

**Team visibility scoping** (`lib/laundry/teams.ts`). A laundry user sees a property only if the property has laundry enabled AND either no laundry team is assigned in `property.accessInfo.laundryTeamUserIds` or the user is on it (`propertyIsVisibleToLaundry`). `getVisibleLaundryPropertyIds` scopes invoice/report exports, and `resolveLaundryInvoiceScope` narrows multi-property financial requests to the visible set (403 for a specifically-requested invisible task/property). ADMIN/OPS are unrestricted.

### C4. Reminders & scheduled jobs

`lib/laundry/reminders.ts` holds two pure selectors (tested in `tests/lib/laundry-reminders.test.ts`) plus the dispatcher:

- **Driver nudge (2026-07)** — `selectStaleDriverTasks`: tasks due today (either leg) still PENDING/CONFIRMED, or PICKED_UP for more than 24h. `dispatchLaundryDriverNudges` runs from the in-process web scheduler (`lib/ops/web-scheduler.ts`, entry `laundry-driver-nudge`, daily at **15:00 Sydney**): per-driver visibility filtering, one PUSH `Notification` row + web push per driver with a summarized property list, and a sweep that **ABANDONs ACTIVE routes left over from previous days** (they can never complete).

### C5. Cleaner- and client-facing laundry

**Previous-clean cycle card (2026-07).** The linen a cleaner needs on job day belongs to the *previous* clean's cycle at the same property. `lib/laundry/previous-cycle.ts` resolves it: `pickPreviousCleanJob` (pure) selects the latest other non-rework turnover before the current job that has a LaundryTask; `pickDropConfirmation` picks the latest confirmation whose `event` is `DROPPED` — revert-tolerant by design. The cleaner workspace card (see Section B for the cleaner portal itself) shows status, dates and the drop photo/notes proof.

**Live driver ETA (2026-07).** `GET /api/cleaner/jobs/[id]/laundry-eta` returns one of five states: `none`, `delivered` (droppedAt + drop photo — the route stop's `completedAt` counts even before the task status flips), `scheduled` (no ACTIVE route contains this cycle's DROP), `no_signal` (route active but no ping within 5 min), or `en_route` with `{isNextStop, stopsBefore, etaMinutes, driverLat, driverLng}`. The chained ETA math is pure in `lib/laundry/eta-chain.ts`: when the target is the next stop it tries a precise single-leg estimator (Google Distance Matrix, injected as `legEtaFn`, may be null without a server key) falling back to naive haversine; with N intermediate stops it uses naive legs only plus N × 7 min of service time — deliberately no Distance Matrix fan-out. Results round **up** to 5-minute precision, floor 5. The driver's identity is never exposed, and a 30s module-level cache bounds polling. (Cross-ref: Section B covers the cleaner workspace hosting this card.)

**Client views.** The client portal (`app/v2/client/laundry/page.tsx`) shows the laundry schedule for the client's properties with the same friendly status labels (Delivered/Skipped etc.); flagged tasks surface in the admin Approval Center rather than to clients.

### C6. QA assignments & queue

A QA inspection is a `QaAssignment` row (schema above at `prisma/schema.prisma`): job link, `assignedToId`/`createdById`/`pickedUpById`, status enum `QaAssignmentStatus` (OPEN → ASSIGNED → IN_PROGRESS → COMPLETED / CANCELLED), `dueAt` (deadline) vs `scheduledFor` (planned slot) vs `sequence` (admin-set 1-based visit order for the day), an immutable GPS **check-in** (`checkInAt/Lat/Lng/AccuracyM`, or `checkInSkippedReason` for an explicitly remote review), the on-site timer (`onSiteStartedAt/EndedAt/Minutes`, persisted via `POST /api/qa/jobs/[id]/timer`), the original-cleaner rework-offer lifecycle fields, and the 2026-07 pay block (C11).

**Starting before the cleaner submits (2026-08).** `POST /api/qa/jobs/[id]/pickup` — "start inspection" — previously ran *no* readiness check at all: an inspector could pick up a job the cleaner had not finished, and nothing recorded that or told the cleaner. It now runs the same predicate the rest of QA uses, `deriveReadiness` (`lib/qa/progress.ts`), through the pure gate `decideInspectionStart` (`lib/qa/inspection-gate.ts`, tested in `tests/lib/qa-inspection-gate.test.ts`). Ready → unchanged. Not ready and no reason → **409 `INSPECTION_REASON_REQUIRED`**. Not ready **with** a reason (≥10 chars) → allowed: the reason is stored on `QaAssignment.earlyStartReason` (nullable, mirroring `checkInSkippedReason`), the pickup audit row carries `startedBeforeSubmission: true`, and the assigned cleaner(s) get an in-app notification plus a web push telling them to complete the form (best-effort — a failed nudge never fails the inspection). The v2 queue prompts with a dialog; the legacy v1 queue (`components/qa/qa-queue-client.tsx`) uses a plain prompt so its inspectors are not hard-blocked. Deliberately a speed bump, not a block — inspectors have real reasons to walk in early. The reason is **read back** in two admin places: the inspection workspace (`components/v2/qa/qa-inspection-workspace.tsx`, beside the check-in banner — shared by `app/v2/qa/jobs/[id]` and the admin QA detail at `app/v2/admin/quality/[assignmentId]`), and the job detail's QA panel (`components/v2/admin/jobs/qa-assign-panel.tsx`). The panel's field is *optional* because the calendar agenda feeds the same component from `GET /api/jobs`, which does not carry it; the job-detail page selects it explicitly. Nothing surfaces it for a COMPLETED assignment on the job page, since that panel only queries the active one.

Assignment paths: `POST /api/admin/qa/assignments` accepts **1–100 jobIds** in one call — quick-assign and the new **bulk assign (2026-07)** are the same endpoint — validating the assignee is an active QA_INSPECTOR or OPS_MANAGER, and writing one `QA_ASSIGNMENT_CREATE` AuditLog for the batch. `assignments/reorder` sets day sequence, `assignments/[id]` edits, `assignments/pay` handles the pay overrides. The inspector queue (`app/api/qa/queue/route.ts`, workspace `components/v2/qa/qa-queue-workspace.tsx` + `qa-day-planner.tsx`) is **inspector-scoped**: an inspector sees OPEN work plus their own assignments, displayed against the *job's* scheduled date, with the on-site timer driving the IN_PROGRESS state.

**Inspection ownership — one rule, one module (2026-08).** A `QaAssignment` carries two people columns and, historically, five call sites each answered "whose inspection is this?" differently. `lib/qa/ownership.ts` is now the single source:

- **Visibility** (`qaAssignmentOwnerWhere`, `qaAssignmentClaimableWhere`) — either column matching is enough; "claimable" additionally includes unowned work.
- **Payee** (`qaAssignmentPayeeWhere`, `qaAssignmentPayeeId`, `qaAssignmentHasPayeeWhere`) — must resolve to exactly ONE person or an inspection can be billed twice across the two settlement rails. The performer wins: `pickedUpById ?? assignedToId`.

This fixed a silent money defect. `/pickup`, `POST /timer` and the submit path all stamp **only** `pickedUpById`, while QA pay (`lib/qa/pay.ts`), payroll (`lib/finance/payroll.ts`) and the cleaner-invoice rail (`lib/cleaner/invoice.ts`) all keyed on `assignedToId` — so **every inspection an inspector picked up themselves was invisible on their pay page and unpayable on both rails, permanently**. Deriving the payee rather than backfilling the column repaired historical rows without mutating any finance data.

Two scoping leaks were closed at the same time: `app/v2/qa/reviews/page.tsx` had **no `where` clause at all** (every inspector saw the last 30 assignments business-wide, each with a working open link), and the queue's `scope=completed` branch *replaced* the ownership filter instead of extending it. Assign-only is now a real setting — `settings.qaAutomation.assignedOnly` (default **on**) — rather than being inferred from `role === QA_INSPECTOR`, which had meant an inspector provisioned as OPS_MANAGER legitimately saw the whole board; a QA inspector can also no longer widen their own scope by passing `assignedOnly=0`. QA "today" tiles are viewer-scoped for inspectors (rework-transfer counts stay business-wide — they are a team signal about cleaners, not the inspector's workload). The reviews page now offers **Continue review** on an IN_PROGRESS assignment (it previously said "Start review") and floats open inspections to the top.

**Annotations: one flattened image, not two layers (2026-08).** `components/shared/image-annotator.tsx` deliberately exports a **transparent overlay PNG** holding only the marks — a CORS safety measure, since drawing the remote photo onto the canvas would taint it and make `toBlob` throw. That made every consumer responsible for recombining the layers, and most of them got it wrong:

- the cleaner feed (`app/api/cleaner/qa-feedback/route.ts`) mapped `.key` and **discarded `.annotatedKey` entirely** — so a cleaner saw the photo and none of the markup, which is the whole point of annotating;
- the admin issues workspaces preferred `annotatedKey`, rendering marks floating on transparency;
- the PDF pipeline re-encodes every image to JPEG, which has **no alpha channel**, so sharp flattened the transparent overlay onto black — turning each annotated photo into a solid black tile covering the photo, and putting the inspector's signature (transparent PNG, near-black ink) on a black rectangle.

`lib/qa/annotation-composite.ts` now owns the flattening (`compositeAnnotated`, extracted from its former home as a private function in `rework-jobs.ts`, plus `normalizeQaPhotoRefs` / `displayKeyFor` / `ensureFlattened`). The QA submit path composites **before** the transaction opens — S3 I/O must never run inside one — and stores the result as `flatKey` alongside `key`/`annotatedKey`, for per-item verdict photos, section `mediaAnnotations`, damage entries and rework flagged areas alike. Every reader then shows one ordinary opaque image; `displayKeyFor` never returns the bare overlay. The cleaner feed additionally **self-heals on read**: an issue predating flattening is composited once and persisted, so already-filed inspections gain their markup rather than only new ones.

`lib/reports/pdf.ts` no longer forces JPEG — images carrying an alpha channel are re-encoded as PNG, so a stray transparent image can never silently black out a report again.

`SubmissionMedia.annotatedS3Key` / `annotatedUrl` / `annotationData` remain **dead schema**: nothing writes them and the single reader always falls through. They are not the annotation store; `QaIssue.qaPhotoKeys` and the `__qaTools` blob are.

**The QA report, rebuilt (2026-08).** `lib/reports/qa-report.ts` is now one builder with two modes, and three separate defects are fixed:

1. **It had no pictures because it never asked for any.** The query included neither `qaIssues` nor the cleaner's `formSubmissions.media` — and in the accountability flow the inspector's primary photo capture *is* per-item on `QaIssue`. An inspection graded purely with verdicts rendered literally zero images. Both are now queried, so the report shows the inspector's evidence beside the cleaner's own.
2. **Its image URLs pointed nowhere.** It built them with `publicUrl()` — a bare `${S3_PUBLIC_BASE_URL}/key`, or a *relative* path when that env var is unset — while the PDF renders via `page.setContent()` on `about:blank`, where a relative URL resolves to nothing. Every key is now presigned in one pass into a `Map` before the (synchronous) template runs.
3. **The signature was black.** A remote transparent PNG hit the PDF image interceptor and was flattened to JPEG onto black. It is now inlined as a base64 `data:` URL, which that interceptor deliberately skips, over a white backstop.

`mode: "internal" | "cleanerSafe"` — the cleaner's copy omits damage cost estimates, rework pay movement and the inspector's private notes, **stripped in the view data, never merely hidden with CSS**. The mode is derived from the session role in `app/api/qa/jobs/[id]/report/route.ts`; it is never taken from a query param, so a cleaner cannot request the internal variant. Visibility is gated per inspection by `QAReview.cleanerReportVisible` (default true, mirroring `Report.cleanerVisible`), toggled from admin job details via `PATCH /api/admin/qa/reviews/[id]/visibility` with an audit entry.

Content added that the old report dropped entirely: the score breakdown (settings-driven deduction values, never hardcoded), per-item findings with evidence, rework flagged areas and their photos, and an attendance block (inspector check-in or remote-review reason, time on site, cleaner clock-in GPS + distance). Styling moved to the Estate skin with `@page` rules and `break-inside: avoid`, stamped `report-template:qa-v2-estate`. **Cleaners can now download it** — the API already permitted them, but no UI ever offered it; the button is on `qa-feedback-card.tsx`.

**The QA result email (2026-08).** What a cleaner used to receive was two lines — *"This clean did not pass inspection."* plus a bare count (*"Issues: 2 major, 1 minor"*). It named **not one actual issue**: no category, no description, no photo, no explanation of the score. Everything needed had already been computed at submit time and thrown away.

`lib/notifications/qa-result-email.ts` builds the real thing — pure, no I/O, so the content is unit-testable: the score with its **arithmetic shown** (deduction values read from `settings.accountability.scoring`, never hardcoded), every finding with its admin-configured category label, description, guest-ready flag and QA's **flattened** markup photo (an email client cannot stack a transparent overlay), a mechanical "what to focus on next" derived from the categories that actually recurred, and a plain-text fallback carrying the same substance.

Three delivery gaps closed at the same time:
- **Legacy-template inspections notified nobody.** The whole notification block sat inside `if (accountabilityInput && accountabilityResult)`, so an inspection graded by the legacy percent scorer could fail and the cleaner would never hear. There is now an `else` branch.
- **The admin QA save path (`app/api/admin/jobs/[id]/qa/route.ts`) sent nothing at all** — a cleaner could be marked down by an admin and only discover it by opening the app.
- **Only the primary assignment was notified**, so a co-cleaner on a shared job heard nothing about an inspection of work they had done. `notifyQaResultToCleaner` now fans out to every non-removed assignment when no explicit `cleanerId` is given.

The CTA also moved from the dead v1 path `/cleaner/jobs/{id}` to `/v2/cleaner/quality`, where the feedback and the report download now live.

**QA form: configuration that reaches the form, and a template derived from the property's own checklist (2026-08).**

*The blocking defect first.* `GET /api/qa/jobs/[id]` returned no `settings` key at all, while both inspection workspaces read `payload.settings.accountability.*`. They therefore **always** fell through to a hardcoded client-side copy of the original fourteen categories. Every category an admin added in Settings changed the admin filter dropdown and **nothing else** — the inspector's picker never saw it, and the on-screen "−3 / −10 / −25" deduction figures were the defaults rather than the configured values. The payload now carries `settings.accountability.{scoring, issueCategories}`, and the client-side list is reduced to a one-entry emergency fallback so a regression would be obvious rather than silently plausible.

*Taxonomy.* The seeded set grows from 14 to ~50, covering what real turnover checklists ask for: reset-to-reference standards, appliance interiors (oven / microwave / fridge / dishwasher / kettle / coffee machine), per-surface detail, floors split into vacuum vs mop, handover and access, and process failures like "checklist marked complete inaccurately". **Keys are add-only** — `sanitizeAccountabilityAssessment` coerces an unrecognised key to `"other"`, so renaming or removing one silently destroys the categorisation of every future verdict that used it.

*Generation.* `lib/qa/generate-from-checklist.ts` derives a QA template from the property's own cleaner checklist (bound through `settings.propertyFormTemplateOverrides` — note there is **no** `FormTemplate.propertyId`). Two rules that look cosmetic and are not: section titles are copied **verbatim**, because `lib/qa/section-match.ts` pairs QA and cleaner sections by normalised title containment and that pairing is what puts the cleaner's photos beside the grading; and each section **collapses** to a handful of outcome questions rather than mirroring every checkbox — P11's ~100 fields would otherwise become ~100 verdicts, which nobody completes honestly. Each generated question carries a "Covers: …" help line naming the checklist items it stands in for, uses the Pass / Minor issues / Fail shape (so the verdict is the single input rather than a star rating *and* a verdict), and every mirrored section gets an evidence upload. A cross-cutting **Common mistakes** section is appended. `qaTemplateMatchesChecklist` detects drift after a checklist changes — the failure mode is silent, so it needs surfacing.

*Ownership.* `QaFormTemplate.isSystemManaged` replaces the old name-prefix test. The auto-upgrade decided what it could rewrite by matching `"Default QA - …"`, so an admin who edited the default template **in place without renaming it** silently lost their work the next time anyone opened a job. `sourceFormTemplateId` records provenance; `QaAssignment.draft` adds server-side autosave (previously localStorage only, which is why an unfinished inspection was tied to one browser profile).

*"How was it done?".* The verdict block attached to every field except signature/instruction/inventory, so the inspector was asked to grade the cleaner on `qa_notes`, `issues_found`, `client_visible_summary`, `rework_required` and `qa_photos` — the inspector's *own* notes and uploads. It is now an explicit allowlist of gradeable field types minus a list of outcome field ids; those fields still render, they simply carry no verdict.

### C7. Inspection workflow

The inspection UI is `components/v2/qa/qa-inspection-workspace.tsx` (v2 Estate rebuild of the v1 flow, same wire contract): a **two-step workspace** — walk the sections scoring per-section, then a review/sign-off step. It talks to `GET/POST /api/qa/jobs/[id]` (job, template, assignment, property stock, cleaner candidates, **cleaner photos grouped per section** so the inspector judges against the cleaner's own evidence, media overrides), with `tools` (damage entries, rework proposal, etc.) defined in `lib/qa/inspection-tools.ts`.

- **Templates**: `QaFormTemplate` (per serviceType, optionally per property, versioned, `schema` JSON) is editable in the admin QA-templates screen (`app/v2/admin/qa-templates/page.tsx`, API `app/api/admin/qa/templates`). Section matching between the cleaner's checklist and the QA form is `lib/qa/section-match.ts`.
- **Verdicts**: per item PASS / MINOR / MAJOR / CRITICAL / NA; MINOR+ requires a category (from `settings.accountability.issueCategories`, invalid → "other") and description, and may carry QA evidence photos with optional **annotation overlays** (`qaPhotoKeys: [{key, annotatedKey}]`) plus references to the cleaner's `SubmissionMedia` ids. Each MINOR+ verdict persists as a structured `QaIssue` row (severity, false-confirmation status, rectification tracking, indexes for pattern detection).
- **Submission integrity**: the submit route rejects jobs not in a QA-inspectable status (409), and guards double submits twice — a pre-check returning 409 `QA_ALREADY_SUBMITTED`, then inside the transaction a **Postgres advisory lock** (`SELECT pg_advisory_xact_lock(hashtext(jobId))`) serializes concurrent submits so the re-check behind the lock sees the first request's review.
- **Amend / reopen**: `lib/qa/reopen.ts` is the pure decision layer (`canReopenInspection`, `reopenMoneyWarnings`), enforced by `app/api/qa/jobs/[id]/reopen/route.ts`. Roles ADMIN/OPS_MANAGER/QA_INSPECTOR (inspectors only their own), INVOICED jobs stay locked, reason ≥ 10 chars, every reopen writes an AuditLog. Reopening flips the assignment back to IN_PROGRESS and mutates nothing else — money in flight is handled in the Approval Center; re-submitting **updates the existing `QAReview` in place** (editedById/editedAt/adjustmentReason) so the job's authoritative score stays single-valued. A stale `reopenedReviewId` 409s.

### C8. Scoring

Two engines coexist:

- **Accountability engine** (`lib/accountability/scoring.ts`, pure, the contract between the submit API and the review UI). Deduction-based: start at **100**, subtract per verdict (defaults MINOR −3, MAJOR −10, CRITICAL −25 — all configurable in `settings.accountability.scoring`), **−5** per missing mandatory-evidence field, an **extra −10** per suspected false confirmation, floored at 0. Bands via `ratingForScore`: EXCELLENT / PASS / NEEDS_IMPROVEMENT / FAILED at configurable thresholds, and **any CRITICAL verdict force-routes the rating to MANAGEMENT_REVIEW** (when `criticalTriggersManagementReview` is on) regardless of the number. `sanitizeAccountabilityAssessment` defensively parses the request blob. Used whenever a QA submit carries an `accountability` assessment.
- **Legacy percent engine** (`lib/qa/scoring.ts`) for template-based scoring: radio Pass/Minor/Fail = 2/1/0, ratings clamped × weight, checkbox all-or-nothing, blanks excluded from both points and max (so N/A can't drag the percent to 0); bands PASS ≥ 80, WARNING ≥ 60, FAIL below, with per-section breakdowns.

**Authoritative-review dedupe** (`lib/qa/review-dedupe.ts`): historical double-submits left some jobs with multiple `QAReview` rows; `pickAuthoritativeReviews` keeps at most one per job — kind "QA" (real on-site inspection) outranks "ADMIN" (quick score), newest wins within a kind. Every feed that lists reviews (cleaner feedback, outcome approvals, stats) goes through it, mirroring `lib/qa/authority.ts`.

### C9. Rework pipeline

`lib/qa/rework-jobs.ts` owns rework/reclean jobs — real `Job` rows with `isRework: true` and `reworkOfJobId` set; they never generate laundry pickups (the planner gates on `isRework`). The cleaner's fix checklist is generated dynamically (`buildReworkFormSchema`): one section per flagged area with QA's photos (annotation overlays are flattened onto the originals with sharp via `compositeAnnotated`) as reference plus a required "after" photo per area (fields `rework_area_<id>`), fronted by a mandatory access-and-safety section (lockbox/key photo + doors/windows check) — rendered by the existing cleaner form engine, no new UI.

**Pay rule (owner spec).** Same cleaner redoes it → paid **$0** (custom payout 0), no deduction. Different cleaner → paid `reworkPayAmount` as a per-cleaner custom payout, and the **same amount is deducted from the original cleaner** as a negative `CleanerPayAdjustment` on the original job, with provenance `source: "REWORK_DEDUCTION"` and deterministic `sourceKey` `rework:<originalJobId>` (`buildReworkDeductionSourceKey` in `lib/accountability/rectification.ts`).

`applyReworkDeduction` is idempotent three ways: the `Job.reworkDeductionApplied` flag, a `(source, sourceKey)` lookup, and the invariants in `lib/qa/rework-invariants.ts` (`assertReassignedReworkMoney`, provenance and pending-not-in-payroll checks) asserted immediately before money is written. **reworkDeductionApplied-flag fix (2026-07):** the flag now means "APPROVED / feeding payroll", not merely "created" — when `settings.accountability.rectification.reworkDeductionsRequireApproval` is on (the default) the deduction lands **PENDING** (payroll filters on APPROVED so it's naturally excluded) and the flag stays false until approval; only an auto-approved deduction stamps it. `setReworkPayDecision` handles admin (re)assignment: it forces the amount to 0 for a same-cleaner decision, moves the primary `JobAssignment`, rewrites the custom payout, and on a *re-decision* with a changed amount posts a compensating APPROVED adjustment for the delta (sourceKey `…:correction:<ts>`) so the original cleaner's net deduction always equals the current decision — previously lowering the amount over-deducted and raising it left money unrecovered.

**QaReworkTransfer** (`lib/qa/rework-transfers.ts`) is the lighter sibling for "QA fixed it themselves": the inspector files a PENDING transfer (severity MINOR/MODERATE/MAJOR, reason, areas, `minutesFromCleaner`, `amountFromCleaner`, `affectsCleanerStats`). On admin approval it reuses existing plumbing rather than reinventing payroll: reduce the cleaner's latest stopped TimeLog by the minutes (with an approved `TimeLogAdjustmentRequest` audit row), write a **negative** approved `CleanerPayAdjustment` for the cleaner and a **positive** one for the inspector — both stamped `sourceKey` `rework-transfer:<id>` so the pair is traceable and deduped.

### C10. Admin QA review & cleaner feedback

**Admin quick score** — `POST /api/admin/jobs/[id]/qa/route.ts`. Only SUBMITTED/QA_REVIEW/COMPLETED jobs can be scored (409 otherwise — scoring anything else would fabricate a completion). Saves are protected by the same advisory-lock pattern plus a **2-minute idempotency window**: an identical score from the same admin within 120s is treated as a double-click and returns the existing review instead of filing a duplicate (the cleaner used to see two verdicts for one clean). Pass (score ≥ `qaAutomation.failureThreshold`) → job COMPLETED with `completedAt` stamped for payroll/invoice periods; fail → parked in `QA_REVIEW`.

**Confirm-gated rework creation** (`lib/qa/admin-rework.ts`). A below-threshold admin score no longer silently spawns a rework job (which schedules real work and emails the client twice). `getAdminReworkContext` first reports whether an open rework already exists (modern `reworkOfJobId` link or the legacy `rework-of:<id>` internalNotes tag), whether an on-site inspection was filed, and whether **the inspector actually requested rework** — a low score with the inspector deliberately not requesting one is a normal outcome the admin is told about before overriding. `createAdminReworkJob` then creates it explicitly, returning null if one exists so retries can't duplicate.

**QA outcomes approval queue** (`lib/qa/outcome-approvals.ts`). Failed inspections park the job in `QA_REVIEW` so billing can't run; `listQaOutcomeApprovals` lists those jobs (only ones that actually have a QA/ADMIN review), longest-waiting first, each with the authoritative review, assigned cleaners, and an advisory `openRework` flag. Shared by `GET /api/admin/qa/outcomes` and the all-approvals aggregate so the rows and the tab count can never disagree; approving (`POST /api/admin/qa/outcomes { jobIds }`) moves QA_REVIEW → COMPLETED.

**Cleaner-transparent feedback.** The cleaner sees their (deduped) review history via `lib/qa/feedback-history.ts` with per-section results and issue details, and each review carries `cleanerAcknowledgedAt` — the cleaner's **acknowledge button** stamps it, and the outcome queue displays whether the cleaner has seen the verdict.

### C11. QA inspection pay (2026-07)

QA inspections became first-class paid work in July 2026. The canonical pure calculator is `lib/finance/qa-pay.ts` (`computeQaAssignmentPay`) — the QA counterpart of `computeCleanerPay`:

- **Mode**: per-assignment `payMode` FIXED / HOURLY / NONE (free-text column, `normalizeQaPayMode` treats anything unrecognized — including "DEFAULT" — as "inherit `settings.qaPay.defaultMode`"). NONE is an explicit $0 decision, distinct from "unconfigured": a FIXED/HOURLY resolution with nothing configured returns `rateMissing: true` so the UI says "not set" instead of presenting $0.00 as decided.
- **Precedence, each level independent** — fixed $: assignment `payAmount` → settings default (an assignment 0 is a real decision; a settings 0 means unconfigured); rate: assignment `payHourlyRate` → inspector `User.hourlyRate` → settings default; hours: assignment `payHoursAllocated` → actual on-site timer hours (`onSiteMinutes`/60, only when > 0) → `settings.defaultHoursPerInspection`. The result reports `source` and `basis` so every number is explainable.
- **Settlement**: the same double-pay discipline as `CleanerPayAdjustment`. Only COMPLETED assignments count (`qaAssignmentCountsTowardPay`); `isQaAssignmentAvailableForSettlement` is *the* selector — a row stamped with either `includedInPayrollRunId` or `includedInCleanerInvoiceId` is spent, and `paySettledAmount` freezes the paid figure so later rate/settings changes never retro-alter it (`qaAssignmentSettlementAmount`). Both rails — payroll runs and cleaner invoices — can consume an inspection (see Section D for the settlement mechanics).

Admin editing happens on the assignment (`/api/admin/qa/assignments/pay` + per-assignment edit, with a `payNote` reason surfaced to the inspector) and bulk defaults in settings. ## Section D — Money, Client Portal & Marketing

### D1. Pricing & quotes

### Rate card and PriceBook

Public pricing is generated, not hand-entered. `lib/pricing/rate-card.ts` holds a labour-hours matrix (`LABOUR_HOURS`): each job type (Airbnb turnover, general, spring, deep, end-of-lease, move-in) has base + per-bedroom + per-bathroom hours. `estimateLabourHours()` turns a service × size combination into total cleaner-hours, and `priceForHours()` converts hours into a price: hours × the editable **rack hourly rate**, rounded to the nearest $5, never below `MIN_JOB_CHARGE` ($120). `computeRateCard()` regenerates the entire card (every service × 1–5 bedrooms × 1–3 bathrooms) from a single rack rate, so editing the rack rate at `/v2/admin/pricing` re-prices everything while preserving the target margin (owner's model: ~$32/hr cleaner cost, $58/hr rack, 40% margin floor).

The persisted price source is the `PriceBook` model (`prisma/schema.prisma`): one row per `(jobType, bedrooms, bathrooms)` with `baseRate`, JSON `addOns` (per-add-on prices — oven, fridge, carpet steam, ~40 options) and JSON `multipliers` (condition level light/standard/heavy). `lib/pricing/service-pricing-store.ts` and `lib/pricing/extras-catalog.ts` back the admin editors; `lib/pricing/gst.ts` is the single GST rule (`calculateGstBreakdown`: 10% when `gstEnabled`, applied identically to quotes and client invoices).

### The quote calculator and the margin floor

`lib/pricing/calculator.ts` computes a quote from a rich input (bedrooms/bathrooms/floors, area band, windows, parking, frequency, condition level, ~40 boolean add-ons, promo code). It resolves an exact PriceBook row where one exists (`pricingMode: "exact"`) or falls back to estimates (`isEstimate`/`requiresAdminApproval`). Promo codes are validated against `DiscountCampaign` rows (`lib/marketing/campaigns.ts` — code, PERCENT/FIXED value, min subtotal, job-type scoping, usage limits, date window). Crucially, the **margin-floor guard** runs after any discount: cost share = `cleanerHourlyCost / rackHourlyRate` from `AppSettings.pricing`, floor price = `subtotal × costShare / (1 − marginFloorPercent/100)` (default 40%); if the discounted price would fall below the floor, the discount is clamped and the line item is labelled "(capped to margin floor)" with `discountClamped: true`. A promo can therefore never sell a clean below the configured margin.

### Quote builder and lifecycle (2026-07 wave)

Admin quotes live at `app/v2/admin/quotes` (`components/v2/admin/quotes/quote-builder.tsx`, `quote-detail.tsx`, `quote-timeline.tsx`, `quotes-pipeline.tsx`). A `Quote` (schema ~line 2369) belongs to a `QuoteLead` and/or an existing `Client`, and carries: `lineItems` JSON, subtotal/GST/total, `frequency` (one_off/weekly/fortnightly/monthly — drives whether conversion creates a single job or a recurring schedule), explicit `serviceAddress`/`serviceSuburb` (so conversion can create the property), `serviceContext` (snapshot of condition/location/parking variables), `discountCode` (links back to the campaign for usage counting), and `showAddOnPrices` (default false — add-ons shown as "on request" to the client because prices change often). The builder embeds an editable per-quote **checklist** seeded from the service default (`lib/checklists`), and per-quote **extras** from `EXTRAS_BY_CATEGORY` in `lib/pricing/extras-catalog.ts`.

Client-facing view: sending a quote mints a `publicToken`; the client opens `/q/<token>` (`app/q/[token]/quote-view.tsx`) without logging in and always sees the latest saved version. From that page they can accept, decline, or request additional add-ons — requests land in `Quote.requestedAddOns` for the admin to price in and re-send. Every touch (EMAIL_SENT / VIEWED / ACCEPTED / DECLINED / ADDON_REQUESTED / CONVERTED / NOTE) is a `QuoteEvent` row rendered as the timeline on the admin quote detail. Quote PDFs come from `lib/pricing/quote-report.ts` + `app/api/admin/quotes/preview-pdf`.

### D2. Client invoicing

### Lifecycle and the transition graph (2026-07)

`ClientInvoice` (schema ~line 2599) has statuses DRAFT → APPROVED → SENT → PART_PAID → PAID, plus VOID. Since July 2026 every status move is validated against a single source of truth, `lib/finance/invoice-transitions.ts`:

- DRAFT → APPROVED / SENT / PART_PAID / PAID / VOID (Send is offered on drafts — approval is optional)
- APPROVED → SENT / PART_PAID / PAID / VOID
- SENT → PART_PAID / PAID / VOID
- PART_PAID → PAID / VOID
- PAID and VOID are terminal; VOID is reachable from any non-PAID status; no-op PATCHes always pass.

The PATCH endpoint `app/api/admin/invoices/[id]/route.ts` enforces `canTransitionInvoice()` and returns a 400 on an illegal move. The same route handles line edits (add/update/remove/reorder with `sortOrder`), GST toggling (totals recomputed through `calculateGstBreakdown`), due date and notes — the latter merged into **one** metadata object (a July fix: previously two separate `metadata` spreads meant a PATCH sending both fields dropped one).

### Record payment and the ledger

`recordPayment` on the same PATCH is the proper payment-recording procedure: amount + method (BANK_TRANSFER/CARD/CASH/STRIPE/MANUAL/OTHER) + optional paid date and reference. `paidAmount` **accumulates** across payments; the status stays PART_PAID until paidAmount reaches the total (with a half-cent tolerance), then flips to PAID. Every payment is appended to a `metadata.payments[]` ledger entry (amount, method, reference, paidDate, recordedAt, recordedBy) — `ClientPayment` couldn't be used because it is gateway-bound. `paidDate` is when the money arrived; `paidAt` remains the system timestamp.

### One-click Mark as paid (2026-07)

`components/v2/admin/finance/estate-invoices.tsx` offers "Mark as paid" from **any** payable status (`PAYABLE_STATUSES = DRAFT, APPROVED, SENT, PART_PAID`), behind a confirm dialog showing the outstanding figure. It settles through the payment ledger with method `MANUAL` (labelled "Marked as paid" in the ledger/receipt; MANUAL is deliberately absent from the record-payment dropdown), falling back to a legacy direct status flip when nothing is outstanding — in which case the PATCH route back-fills `paidAmount = totalAmount` so the paid figure is never blank. A settlement that skipped the send step (paid straight from DRAFT/APPROVED) is audited in `AuditLog` with the note "Marked paid without sending". The old blocker was `app/v2/admin/finance/invoices/page.tsx` — a read-only Estate preview table with no actions that shadowed the real workspace; it is now a stub that redirects to `/v2/admin/finance?tab=invoices`, where the full workflow (approve, send, record payment, mark paid, Xero) lives.

### Generation and Xero push

Invoices are generated per client from uninvoiced completed jobs by `generateClientInvoice` in `lib/billing/client-invoices.ts` (double-billing is inherently avoided by scanning existing `ClientInvoiceLine.jobId` entries); `lib/finance/auto-invoice.ts` wraps this per CLIENT user on a cadence (`lib/finance/cadence.ts`), emailing the client afterwards. `app/api/admin/invoices/[id]/xero-push/route.ts` pushes an invoice to Xero (`pushClientInvoiceToXero` in `lib/xero/client.ts`), mapping per-line item codes by the job's service type from Phase-3 integration settings, with an idempotency refusal when `xeroInvoiceId` is already set (a second push would duplicate the Xero invoice; `force: true` overrides). OAuth plumbing is `app/api/xero/{connect,callback,status,disconnect}`.

### D3. Staff pay — four streams, two rails (2026-07 overhaul)

This is the most safety-critical machinery in the platform. The mental model, enforced consistently across the code since July 2026:

**Four streams** of money owed to a worker:

1. **Job pay** — `computeCleanerPay` in `lib/finance/job-money.ts`, the single source of truth for what a job pays. Allocated hours (`Job.estimatedHours` split across active assignees) × the best rate (assignment `payRate` → per-cleaner job-type rate in settings → `User.hourlyRate`), or the cleaner's clocked timer when no allocation exists; per-cleaner custom payouts and transport allowances come from job internal-notes meta. Rework jobs pay **exactly** `Job.reworkPayAmount` as set by QA (null = $0) — never hours × rate, so an unpaid rework can't leak back to the hourly rate.
2. **Pay adjustments** — `CleanerPayAdjustment` (schema ~line 1327), **signed at the row level**: deductions (QA rework deductions, rectification deductions) are stored negative; additions (bonuses, rectification credits) positive. The canonical rules are the pure module `lib/finance/pay-adjustments.ts`: only APPROVED counts (`adjustmentCountsTowardPay`), `adjustmentSignedAmount` returns the signed cents value, and `partitionAdjustmentsForInvoice` splits rows into fold-into-job-line vs standalone carry-over lines.
3. **QA inspection pay** — `QaAssignment` pay fields (`payMode`, `payAmount`, `payHourlyRate`, `payHoursAllocated`, `onSiteMinutes`). `lib/finance/qa-pay.ts` (`computeQaAssignmentPay`) resolves a three-level precedence, most-specific-wins at each level independently: mode assignment → settings default; fixed amount assignment → settings; hourly rate assignment → inspector's `User.hourlyRate` → settings; hours allocated → actual on-site → settings default hours. `NONE` = explicitly unpaid ($0); an unconfigured rate instead sets `rateMissing` so the UI says "rate not set" rather than presenting $0.00 as a decision. Only COMPLETED inspections count.
4. **Shopping** — really two independent sub-streams sharing one `ShoppingSettlement` row (`lib/finance/shopping-settlement.ts`): **EXPENSE** (out-of-pocket reimbursement, sum of the run's line costs) and **TIME** (admin-approved shopping minutes at an approved rate). They settle independently — the primary payroll engine pays reimbursements but has never paid shopping time — so each carries its own stamp pair.

**Two rails** that settle those streams:

- **Payroll runs** — primary engine: `getPayrollSummary` in `lib/finance/payroll.ts` computes the period; `createPayrollRun` in `lib/payroll/engine.ts` commits it (DB `PayrollRun` + `Payout` rows, driven from `app/api/admin/payroll/runs` and `app/v2/admin/payroll`; ABA bank-file export in `lib/payroll/aba.ts`). Contractors are excluded — they invoice instead. A secondary rail, `lib/phase4/payruns.ts` (`app/api/admin/phase4/payruns`), stores runs as JSON in an AppSetting blob and reuses `getCleanerInvoiceData` per payee for its numbers.
- **Cleaner invoices** — self-service: `lib/cleaner/invoice.ts` (`getCleanerInvoiceData` + `buildCleanerInvoiceHtml`) and the send route `app/api/cleaner/invoice/send/route.ts`.

### The settlement-stamp discipline

Every stream row carries a stamp pair: `includedInPayrollRunId` and `includedInCleanerInvoiceId` (shopping time uses its own `timeIncludedIn*` pair). The invariant, repeated verbatim across all four stream modules:

- **Selection = eligible AND both stamps null.** Eligible means APPROVED (adjustments), COMPLETED (inspections), status admits pay (shopping), submitted/completed statuses (jobs, whose stamp is `Job.payrollRunId`). There is deliberately **no lower date bound** on adjustments and only an upper bound on inspections: *the stamp, not the date window, prevents double payment*. Date-window selection was the old design and it failed both ways — an adjustment approved after its period closed fell outside every subsequent window and was **never paid**, while a row inside two overlapping windows was **paid twice**. The read-only period report keeps the bounded window (a historical report must not change under you); the committable run drops it.
- **Claim = guarded `updateMany` after success.** Stamping is always `updateMany({ where: { id, bothStampsNull }, data: { stamp } })`, so the loser of a race between a concurrent run and invoice updates 0 rows and the money is paid exactly once. The one escape hatch is a rail recomputing **itself**: `includePayrollRunId` / `includeInvoiceId` options let a row stamped by *this* run/invoice stay visible to it (mirroring `Job.payrollRunId` + `includePaidRunId`), otherwise a refresh would drop its own rows as "already paid by someone else".
- **Frozen settled amounts.** Settling also freezes the figure paid: `QaAssignment.paySettledAmount`, `ShoppingSettlement.paySettledAmount` / `timePaySettledAmount`. `qaAssignmentSettlementAmount` / `shopping*SettlementAmount` return the frozen figure when present, so a later rate change, settings edit or line-cost edit can never retro-alter what a historical run actually paid. The frozen figure is always **the number rendered on the document** (threaded from the row), never a recomputation.

### The fixed bugs (design rationale)

Each rule above exists because a specific bug paid the wrong amount or the wrong person:

- **`Math.max(0, …)` erasing deductions.** Clamping a signed adjustment (or a net-negative pay-run line) silently deleted every deduction. `lib/finance/pay-adjustments.ts` forbids clamp/abs downstream; `sanitizeLine` in `lib/phase4/payruns.ts` now coerces only NaN, keeping negative line amounts (a payee whose period is dominated by a deduction is owed a negative amount).
- **Assignment-scoped adjustment selection.** The cleaner invoice used to select adjustments with `jobId IN (jobs on this invoice)`. A QA-inspector rectification credit is written against the *cleaner's* job — which the inspector was never assigned to — so approving it changed nothing anyone was paid; late approvals vanished the same way. Selection is now purely "APPROVED and unstamped"; rows without a job line become their own signed **carry-over lines** (`extraLineRows`, labelled "Deduction — …" when negative).
- **CLEANER-only payee queries.** `getPayrollSummary` filtered payees on `role: CLEANER`, so a QA_INSPECTOR owed an approved credit (or inspection pay) never appeared as a payroll row at all — the approval "took" in the database and paid nobody. Both rails now append `extraPayees` discovered through the adjustment/inspection/shopping streams (`lib/finance/payroll.ts` ~line 178; `findPayeeIds` in `lib/phase4/payruns.ts` queries all four streams, since a payee can hold any one stream alone; discovery is deliberately a superset of selection).
- **Wrong-payee rectification credits.** The QA-issue PATCH route used to credit the *session user* — an admin recording the fix on the inspector's behalf paid themselves. `resolveRectificationPayee` in `lib/accountability/rectification.ts` now resolves: explicit admin choice → the recorded rectifier on the issue → the session user *only if they are a QA_INSPECTOR* → the issue raiser; if none resolve it returns null and **no money is created** ("better no money than money to the wrong person"). Band amounts come from `resolveRectificationBand` (minutes-scaled, over-threshold routes to manager review).
- **Phase4 paying unstamped streams** (commit `9fd494b2`). The phase4 rail's `estimatedPay` already folded in adjustments/inspections/shopping but only jobs were ever stamped, so the other streams were payable a second time by the primary engine or the payee's next invoice. `createPayRun`/`refreshPayRun`/`deletePayRun` now stamp and release **all** streams atomically in one transaction (`releaseRunStamps` also clears frozen amounts on release — a frozen figure for a run that no longer pays it "is a lie"). LOCKED/PAID are metadata-only by design: settlement happens at create time on both rails.
- **Shopping's status-based pseudo-guard + sentinel backfill** (commit `c4fa967c`, 2026-07-27). Shopping selection used to filter on status + date window only; the payroll stamp existed but was never read, no invoice stamp existed at all, and approved time had no stamp of any kind — so a reimbursement paid by payroll was billed again on the next invoice. The migration adds the full stamp pairs and **backfills historically-invoiced runs with a sentinel id** (the opaque `includedInCleanerInvoiceReference`, else `legacy:<settlementId>`): a sentinel can never equal a real `CleanerInvoiceSubmission` id, so `includeInvoiceId` never un-excludes it and the row is permanently spent — the conservative reading of "already paid". A run whose expense was invoiced but whose time was only APPROVED keeps a null time stamp: that time is genuinely still owed.

### Pay notifications and settled-immutability

`lib/notifications/pay-adjustments.ts` notifies the affected worker on every **real** state transition of an adjustment (APPROVED / REJECTED / AMOUNT_CHANGED / REVERSED_TO_PENDING), with direction-aware copy ("Pay deduction approved — $X" vs "Extra payment approved"), via `deliverNotificationToRecipients` (the single in-app + web-push + email + SMS chokepoint honouring preferences). `notifyReworkMinutesChanged` separately covers minutes added/removed from a time log by a rework transfer. Callers fire these only on actual transitions, so retries can't double-notify.

**Settled money is immutable**: the admin PATCH `app/api/admin/pay-adjustments/[id]/route.ts` refuses (HTTP 409, "Raise a new adjustment to correct it") any status change or amount edit on an adjustment carrying either settlement stamp — re-deciding it would desynchronise the books from what was actually paid. Corrections are made by raising a new, opposite adjustment. Approved amounts are rounded to whole cents at write time so stored values can't drift 1c against rounded totals.

### Pay transparency & edit-anywhere (2026-07)

Correct money is not enough — every pay change must also be **visible, explained, and editable from wherever it is seen**. Three pieces enforce that:

- **One canonical per-job pay summary.** `computeJobPaySummary` in the pure module `lib/finance/job-pay-summary.ts` (DB loader next door in `job-pay-summary-load.ts`, exposed by `GET /api/admin/jobs/[id]/pay-summary`) returns, **per payee**: base pay + its basis, every adjustment on the job (signed amount, kind, what/why, origin, status, who decided and when, settlement stamp, editable flag), the `approvedTotal` (base + transport + APPROVED adjustments — what the rails will actually pay) and a separate `pendingDelta` (PENDING money, never mixed into the total). Base pay is `computeCleanerPay` with the *same* inputs the invoice uses, including the rework rule, so **`approvedTotal` equals the cleaner invoice's line for that job** — asserted by feeding identical fixtures through both paths in `tests/lib/job-pay-summary-invoice-consistency.test.ts`. Grouping is strictly by **payee** (`CleanerPayAdjustment.cleanerId`), which is not always a cleaner on the job: a QA rectification credit is written against the *cleaner's* job with the inspector as payee, so it appears under the inspector (base $0, `assigned: false`), never inside the cleaner's total.
- **Audience (2026-08).** `describeAdjustment(row, audience)` takes a REQUIRED `PayAdjustmentAudience` — `"internal"` (admin/ops/finance: the full reason including `Admin: {adminNote}`) or `"self"` (the payee reading their own money: `cleanerNote` only). `computeJobPaySummary` carries the same required field. It is deliberately required with no default: the cleaner's own job screen was serialising every adjustment through the internal variant, so the reviewing admin's private decision note travelled to the person it was about, and a default is precisely why nobody had to think about it. The cleaner endpoint `GET /api/cleaner/pay-adjustments` likewise answers through an explicit allowlist DTO instead of `{ ...row }` — a whole-row spread that shipped `adminNote`, `reviewedById`, `sourceKey` and both settlement stamps, and would have leaked any column added later. Settlement reaches the cleaner as a derived `settled` boolean; the run/invoice ids stay internal. Guarded by `tests/lib/cleaner-pay-adjustment-dto.test.ts` and the audience matrix in `tests/lib/job-pay-summary.test.ts`.
- **Two notes, one private (2026-08).** `CleanerPayAdjustment.adminNote` is the reviewing admin's PRIVATE record of a decision; `decisionMessage` is the explanation written for the payee. They were one field doing both jobs, and the admin edit box was even labelled *"Admin note (visible to the payee)"* while writing the private one — so an admin explaining a decision believed they were talking to the cleaner, and the text reached them anyway through three unintended routes: the cleaner's job screen, the pay-requests list, and the decision push/email (`to: cleaner.email` with the note in the body). The box now writes `decisionMessage` — what its label always promised — beside a separate, genuinely private note. `describeAdjustment` shows `decisionMessage` to both audiences and `adminNote` only to `internal`. Migration: `20260802010000_pay_adjustment_decision_message`.
- **Origin: AUTOMATIC vs MANUAL.** `deriveAdjustmentOrigin` maps the `(source, sourceKey)` provenance conventions to a display label — `REWORK_DEDUCTION` (`rework:<jobId>`), `REWORK_TRANSFER_DEDUCTION`/`_CREDIT` (`rework-transfer:<id>`), `QA_RECTIFICATION_PAY` / `RECTIFICATION_DEDUCTION` (`rect:<issueId>[:ded]`), `STREAK_5`/`STREAK_10`, `MONTHLY_RANK_1`/`_2` → "Automatic — …"; anything unknown, legacy or null → "Manual" (never fabricate an automatic provenance). Admin-raised corrections carry `ADMIN_CORRECTION` / `correction:<id>` and read "Manual — correcting adjustment".
- **The universal edit-or-navigate rule.** Wherever an adjustment or a per-job pay figure is shown, it is either **editable in place** or **one click from the single editable source**. The shared client component `components/v2/shared/pay-adjustment-list.tsx` renders the summary's items identically everywhere (signed amount with tone, origin badge, status chip, settled chip, what-changed line, timestamps) and — for ADMIN/OPS on an *unsettled* row — offers Edit, which always calls the ONE mutation endpoint (the pay-adjustment PATCH); never a second write path. A settled row shows the immutability tooltip plus **"Raise correcting adjustment"**, which POSTs a new PENDING row via `POST /api/admin/pay-adjustments` with `correctionOfId` (and an explicit `direction`, since the rail stores deductions negative), and links to the Approval Center history. Non-admin viewers get the same read-only display with a "view details" link to their own pay page. Freshness is real rather than optimistic: every successful mutation triggers the surface's own refetch (the job pay card also refetches on window focus), and a 409 from a just-settled row surfaces as "this was just settled — refresh".

Surfaces wired to it: the admin job **Cleaner pay** card (`components/v2/shared/job-pay-card.tsx`, embedded in `job-manage.tsx` → People & pay), the cleaner's submitted-job screen (`stage-wrapup.tsx`, fed by `payAdjustmentsForJob` / `payTotalForJob` on the job-form route and gated by the existing `cleanerPortalVisibility.showPayRequests` flag), the cleaner/inspector invoices panel (carry-over lines now carry origin + reason, in the panel and in the PDF), the Approval Center pay/rectification/bonus cards, the finance Adjustments manager (origin + settled badges, settled rows offer no button the PATCH would refuse), and — navigation-only, which satisfies the rule — the expected-invoices forecast (Extra column → the job's pay card), payroll run detail (Adjustments → the adjustments surface) and the QA pay page (each adjustment → its job).

### D4. Cleaner invoices (self-service) — and QA inspector self-invoicing (2026-07)

### Building the invoice

The payee picks a period on the cleaner portal; `getCleanerInvoiceData` (`lib/cleaner/invoice.ts`) assembles, using Sydney calendar-day boundaries (`lib/time/sydney-range.ts` — hardcoded UTC boundaries previously shifted the window ~10–14h and bucketed edge-of-period jobs differently from payroll):

- **Job rows** — jobs in SUBMITTED/QA_REVIEW/COMPLETED/INVOICED bucketed by `completedAt ?? scheduledDate`, restricted to *currently active* assignments (`removedAt: null` — a cleaner reassigned off a job used to keep invoicing it via the stale assignment row). Each row is `computeCleanerPay` output: split, rate ("Not set" when `rateMissing`), paid vs original hours (cleaner hour-overrides are highlighted with a change note), base, approved extras folded in, transport, total. Jobs already on a prior non-VOID `CleanerInvoiceSubmission` (tracked in `lineData.jobIds`) are excluded; the cleaner can also transiently remove jobs/runs from this invoice.
- **Fixed pay (2026-08).** A per-cleaner flat amount for one job, set from the admin job detail's People tab ("Fixed pay (AUD)", stored in the job meta as `cleanerPayouts[cleanerId]`) — `computeCleanerPay` returns `source: "CUSTOM"` and bypasses hours × rate entirely. Every surface that renders pay now says so rather than printing arithmetic that was never done: the invoice row carries `paySource` and prints **Fixed** in the rate column with no hours figure, and the job pay card reads "Fixed pay (flat amount)". The rework rule is the same mechanism (an unpaid rework is a fixed $0, a paid one is exactly QA's amount), which is why the invoice's hours-override branch **must** use `effectiveCustomPayout` — it re-read the raw meta instead, so an admin hours adjustment on a rework job silently reverted it to hourly pay. Regression: `tests/lib/cleaner-invoice-fixed-pay.test.ts`.
- **Extra lines** — carry-over adjustments (signed; see D3). Each line also carries its **origin** ("Automatic — rework deduction" / "Manual"), reason text and originating `jobId` (2026-07 pay-transparency wave), printed under the description on the PDF and rendered through the shared adjustment component in the panel.
- **QA inspection rows** — the invoice mirror of the payroll `extraPayees` fix: an inspector holds no cleaner assignments, so without this stream an inspections-only invoice came out empty. Selected by stamp (upper date bound only; a COMPLETED row with null `completedAt` is included — it is work that was done and is owed), priced by `computeQaAssignmentPay`, frozen-amount aware, $0 rows dropped but left unstamped so they become payable if later given a real amount.
- **Shopping expense + time rows** — via `listCleanerReimbursableShoppingRuns` / `listCleanerApprovedShoppingTimeRuns` (`lib/inventory/shopping-runs.ts`) under the stamp discipline, frozen-amount aware.

`estimatedPay` = jobs + extra lines + expenses + shopping time + QA inspections. The PDF (`buildCleanerInvoiceHtml` → `renderCleanerInvoicePdf`) can hide **all** hour-bearing columns (`showHours: false`) — this is the figure cleaners forward to accounts, so hiding must be total, down to collapsing "rate × hours" basis text to a bare rate.

### Earnings vs reimbursements, and the payee's pay claim (2026-08)

An adjustment now carries a **category** (`SERVICE` / `PARKING` / `REIMBURSEMENT`) and a derived `taxable` flag (`lib/finance/pay-categories.ts`; `taxable` is never accepted from a client, only computed from the category, so the two cannot contradict each other). Parking fees and receipts were previously paid through the same rows as work, so a $12 parking ticket was added to the payee's services total as if they had earned it — they hadn't, they were being put back where they started. The invoice prints the two groups under separate headings with their own subtotals (`taxableTotal` / `nonTaxableTotal`; shopping expense reimbursements join the non-taxable side), and the document's header changed from "Tax Invoice" to **Invoice** — no GST arithmetic is applied anywhere, so claiming to be a tax invoice claimed something it does not do (owner decision). The category is picked by the payee in the pay-request panel and by an admin when adding a payment; existing rows default to `SERVICE`/taxable, which is exactly what they always were.

**Removing an adjustment from an invoice** (`excludedAdjustmentIds`, on preview/download/send) is applied *before* the partition, not after it. That single placement is what keeps the carry-over lines, `perJobTotals` and the stamped-as-settled set in agreement: filtering afterwards would leave an excluded job-linked row's money inside its job's line while the payee believed they had taken it off. An excluded row is never stamped, so it stays owed and appears on the next invoice. Regression: `tests/lib/invoice-excluded-adjustments.test.ts`.

**PAID_CLAIMED.** The only way an invoice reached PAID was an admin marking it, so a payee who saw the money land had no way to say so. `PATCH /api/cleaner/invoice/submissions/[id]` accepts exactly one transition — `SUBMITTED`/`XERO_PUSHED` → `PAID_CLAIMED`, own invoices only, 409 if the office already recorded payment — writing `paidClaimedAt`/`paidClaimedNote`/`paidClaimedProofKeys` and **not** the `paid*` settlement block: the record of money leaving the business is the business's, written when an admin confirms. Claims queue in the Approval Center as `cleanerInvoicePayClaims` (so they feed the nav badge counts automatically); confirming goes through the ordinary mark-paid endpoint with its existing `Job.cleanerPaidAt` stamping, rejecting returns the invoice to SUBMITTED with the claim fields intact so the disagreement stays on the record. Related fix: the admin status PATCH used to clear the whole payment record on **every** non-PAID status, erasing when/how much/by what method an invoice was paid as a side effect of any other status change; it now only clears on an explicit VOID or SUBMITTED reversal. Migration: `20260802020000_pay_category_and_invoice_pay_claim`.

The Pay page's invoice shortcuts no longer fire an invoice on the spot. They used to email a PDF built from silent defaults — no visible period, no preview, no exclusions, no undo — so they now navigate to `/v2/cleaner/invoices?preset=` with the period pre-chosen, keeping the review step that catches a wrong period or an already-settled job.

### Sending: idempotency anchor and stamping

`app/api/cleaner/invoice/send/route.ts` first blocks on **profile completeness**: `invoicePayeeMissingFields` (`lib/profile/completeness.ts`) requires name, phone, email, address, ABN, and bank BSB/account/name before an invoice can be emailed, returning the missing fields plus a fix URL. A $0 invoice with pending (unapproved) extras is refused with a 409 so the cleaner waits for approvals instead of billing zero.

The send itself is anchored for idempotency: inside a transaction holding a per-cleaner Postgres advisory lock (`pg_advisory_xact_lock(hashtext(userId))`), a `CleanerInvoiceSubmission` row for the same cleaner + `periodStart` created within the last 2 minutes means a send is in flight → 409; otherwise the snapshot row is created with status `SENDING` **before** any email. (Previously the email went first and the snapshot after, unguarded — a double-tap emailed accounts twice and created two pay claims.) The email (PDF attached, one admin-editable "cleanerInvoice" template for the whole rail) goes to `settings.accountsEmail`. On failure the anchor is deleted so a retry is legitimate; on success the route stamps, in order: shopping (marking runs INVOICED first, because that guarantees the settlement row exists for a time-only run, then stamping only runs whose ownership was verified), then adjustments, then QA inspections (stamp + timestamp + frozen amount = exactly the PDF figure, guarded on both stamps null) — and finally flips the anchor to `SUBMITTED`. The snapshot's `lineData` carries contact details, `payeeRole`, all bill lines, `jobIds` and `qaAssignmentIds` for admin review and the Xero **bill** (ACCPAY) push at `app/api/admin/cleaner-invoices/[id]/xero-push/route.ts`; admin marks submissions paid with amount/bank/method/date fields on the model.

### QA inspector self-invoicing (2026-07, commit `de680737`)

The rail is no longer cleaner-only. `lib/invoicing/access.ts` is the shared gate for every `/api/cleaner/invoice/*` endpoint: `requireInvoicePayeeSession()` admits `INVOICE_PAYEE_ROLES` (CLEANER + QA_INSPECTOR, defined once in `lib/profile/completeness.ts`). Widening the role gate is safe **only** because every endpoint derives the payee from `session.user.id`, never a caller-supplied id — a payee can only ever bill their own work. The cleaner portal's "invoices" visibility toggle still applies to CLEANERs only (it is an admin switch for the cleaner portal; flipping it must not cut off an inspector's ability to get paid). Role-aware presentation: `invoiceFileStem()` names the PDF `qa-inspector-invoice-…` for inspectors, and `adaptInvoiceEmailForPayee()` relabels "Cleaner Invoice" → "QA inspector invoice" in the shared email template (appending "(QA inspections)" if the admin rewrote the copy such that the phrase is gone). An inspections-only invoice renders complete — the "no payable work" empty-state only appears when *every* section is empty.

### Admin expected-invoices forecast

`lib/cleaner/expected-invoice.ts` predicts what each payee (CLEANER **and** QA_INSPECTOR, contractor vs payrolled flagged via `employmentType`) will invoice for a period, *before* they submit — reusing `getCleanerInvoiceData` so the prediction and the payee's own number come from one source of truth. It surfaces overridden hours, approved vs pending extras, rate-missing lines, per-stream totals, a grand expected total, and — once a submission exists — the variance between submitted and expected, including expected jobs missing from the submission ("forgot to add"). Rendered as the prediction tab on `app/v2/admin/cleaner-invoices/page.tsx`.

### D5. Payroll runs

### Primary rail

Admin builds a run at `app/v2/admin/payroll` from a date range. `getPayrollSummary` (`lib/finance/payroll.ts`) returns per-payee rows across all four streams: job lines (canonical `computeCleanerPay`, rework governed by `reworkPayAmount`, skipped cleans never paid), signed adjustment rows, QA inspection rows (frozen-amount aware, $0 dropped), shopping reimbursement rows (one settlement per run — an invariant every write path enforces), and a placeholder shopping-time map (the primary engine has never paid shopping time; that stream settles on the invoice/phase4 rails). With `excludePaidJobs: true` (run creation) it applies the full stamp discipline; without it (read-only period view) it keeps bounded date windows so historical reports are stable.

`createPayrollRun` (`lib/payroll/engine.ts`) filters to payees with positive gross pay, **drops CONTRACTORs** (they invoice; the run errors helpfully if everyone in range is a contractor), and in one transaction creates the `PayrollRun` (DRAFT) + `Payout` rows (bank details + payout method snapshotted) and stamps jobs, adjustments, QA inspections and shopping-expense settlements — each guarded on null stamps, shopping/QA with frozen amounts. Confirm/process steps later move status and money but touch no stamps (already written at create). Payslips render via `buildPayslipHtml` (`app/api/admin/finance/payroll/payslip`); ABA bank files via `lib/payroll/aba.ts`.

### Phase4 (secondary) runs

`lib/phase4/payruns.ts` stores `PayRunRecord`s (DRAFT/LOCKED/PAID) as JSON under AppSetting key `phase4_payruns_v1` via `lib/phase4/store.ts` (line field names keep legacy `cleaner*` naming for stored-blob compatibility; `payeeRole` records the truth). `findPayeeIds` discovers payees from all four streams; `computeLines` calls `getCleanerInvoiceData` per payee with `excludePaidJobs` + `includePaidRunId`; `buildComputedLines` (pure) folds invoices into lines plus the id sets to stamp. Create stamps everything atomically; **refresh** (DRAFT only) reconciles — release stamps no longer included, re-claim included ones under null-stamp guards, re-freeze amounts — so a refresh can neither drop its own rows nor steal a row a concurrent invoice claimed; **delete** (DRAFT only) releases every stamp so the work becomes payable again (releasing only jobs previously left adjustments/inspections stamped by a run that no longer existed: money marked paid that nothing had paid). LOCKED/PAID transitions are metadata only, and block refresh/delete, so a locked run's stamps can no longer be released.

### Job detail: timeline, live ETA, and the "Manage this clean" hub (2026-07)

**One-open-per-type limit**: `hasOpenRequestOfType` ("open" = `approvalStatus === PENDING_APPROVAL` and execution not cancelled/completed) makes the route return **409** ("You already have an open request of this type") — decided or completed requests no longer block a new one. ### D7. Marketing hub (2026-07 expansion)

### Base hub: assets, discount campaigns, social

The **asset library** is the `MarketingAsset` model (schema ~line 2906): IMAGE/VIDEO/GIF with S3 key, dimensions, tags and duration; CRUD at `app/api/admin/marketing/assets`. **Discount campaigns** — the promo codes consumed by the quote calculator (D1) — are *not* rows of the Prisma `DiscountCampaign` model in practice: they are stored as a JSON blob in an AppSetting (`marketing_discount_campaigns_v1`) via `lib/marketing/store.ts`, with validation/redemption rules (PERCENT/FIXED, min subtotal, job-type allowlist, usage limit, date window) in `lib/marketing/campaigns.ts`. AI caption drafting lives in `lib/marketing/ai-composer.ts`.

### Email campaigns: model, engines, segments

One `EmailCampaign` row (schema ~line 2792) is shared by **two engines with two parallel status fields**: the legacy email engine (`lib/marketing/email-campaigns.ts`, string `status` draft/scheduled/sending/sent + `scheduledAt`) and marketing-engine-v1 (`lib/marketing/campaign-sender.ts`, enum `campaignStatus` + `scheduledFor` + `channel` EMAIL/SMS/BOTH, optional `MessageTemplate` link). The dispatchers deliberately exclude each other's rows so a campaign can never be double-sent by both. Relations: `CampaignSend` (per-recipient send ledger, unique `(campaignId, email)`) and `EmailCampaignEvent` (webhook telemetry).

**Audience segments** (`lib/marketing/segments.ts`) are pure predicates over flat client/lead "facts" loaded in one query each: `all_active_clients`, `clients_with_job_last_90d`, `dormant_90d`, `airbnb_property_clients`, `clients_with_active_recurring`, `leads_only` (from `QuoteLead`, excluding converted/lost). `resolveSegment` returns a deduped recipient list; `resolveAllSegmentCounts` powers the **live counts** the editor shows before send (`app/api/admin/marketing/segments/route.ts`). The legacy audience type `segment` delegates wholesale to this module; older ad-hoc audiences (all clients / inactive / by service type) remain.

**Test-send** (`app/api/admin/email-campaigns/[id]/test-send/route.ts`) emails one `[TEST]`-prefixed copy to the signed-in admin: deliberately transactional + critical (bypasses suppression, since the admin may be suppressed themselves), writes no `CampaignSend` row, and leaves `{{variables}}` unresolved (there is no client context).

### Scheduling: 5-minute dispatcher and atomic claim

Two schedule drivers coexist without double-firing. The pg-boss worker (`workers/boss.ts`, opt-in via `SNEEK_WORKERS_ENABLED=true`) runs `email-campaign-dispatch` / `marketing-campaign-dispatch` hourly. The true **5-minute dispatcher** is the in-web fallback `lib/ops/web-scheduler.ts`: `kickWebScheduledOps()` fires from the root layout on render, throttled to once per 5 minutes, and *stands down* whenever a dedicated pg-boss worker is detected (it queries the pgboss schedule tables). Each dispatch tick performs an **atomic claim**: select due campaigns, then a conditional `updateMany` flipping scheduled→sending — only a `count === 1` result proceeds, so two concurrent ticks can never both send the same campaign (20 campaigns max per tick). Per recipient, the `CampaignSend` unique constraint is the idempotency ledger: a P2002 on create means already-contacted → skip; a hard send failure deletes the claim row so a later tick retries. Successful sends store the Resend `email_id` as `externalId` so webhook events map back.

### Template gallery (2026-07)

`lib/marketing/campaign-templates.ts` ships **12 fully written campaigns** (`CAMPAIGN_TEMPLATES`): spring-clean promo, EOFY tax time, Christmas holiday hours, Airbnb host welcome, post-clean review request, win-back dormant, referral offer, bond-clean promo, laundry service launch, price-update notice, meet-your-cleaner, monthly newsletter — categorised seasonal/lifecycle/promotion/announcement/trust/newsletter, in Australian English with GST-inclusive copy. ### Block composer: design JSON embedded in htmlBody (2026-07)

`lib/templates/email-blocks.ts` defines the block model (`EmailBlock` = heading/text/button/image/divider/spacer; `EmailDesign` adds page/card backgrounds). The **no-dual-source-of-truth** trick: `renderEmailHtml(design)` serialises the entire design to JSON and embeds it as the first line of the output HTML inside a comment (`<!--SNEEK_EMAIL_DESIGN:{…}-->`), followed by table-based, inline-styled email-safe HTML rendered from the same blocks. `htmlBody` alone therefore carries both the rendered email and its editable source — no extra DB column that could drift. `parseEmailHtml(html)` finds the marker and parses the JSON back into the editor; legacy raw HTML without a marker degrades gracefully into a single text block. The manager UI (`components/v2/admin/marketing/email-campaigns-manager.tsx`, block editing in `email-block-editor.tsx`) re-parses/re-renders on every blocks↔HTML mode toggle so the two views stay in sync.

### Resend webhook analytics and suppression

`app/api/webhooks/resend/route.ts` verifies signatures (Svix `RESEND_WEBHOOK_SIGNING_SECRET` first, legacy HMAC shared-secret second; no secret configured → rejected, bad signature → 401 — an unauthenticated webhook must never write suppressions). Events (sent/delivered/opened/clicked/bounced/complained/delayed) are matched to `CampaignSend` rows by `externalId === email_id` and appended to `EmailCampaignEvent` (append-only; duplicates harmless). `lib/marketing/campaign-analytics.ts` computes stats in two queries with **distinct-recipient counting** — five open-pixel fires from one reader count as one open; `sent` comes from the `CampaignSend` ledger (trusted) rather than Resend's non-guaranteed `email.sent` events, and open/click rates fall back to the sent base when no delivered events arrive.

Bounces and complaints feed the **suppression list** (`lib/email/suppression.ts`, `EmailSuppression` model): COMPLAINT, SOFT_BOUNCE or HARD_BOUNCE per address. The list is address-keyed (not user-keyed) so it covers client emails with no `User` row; `suppress()` writes both the list and `User.emailStatus`, and `isSuppressed()` checks both. **The send-now suppression fix (2026-07)**: the immediate "Send now" path previously skipped the suppression list entirely. `dispatchEmailCampaignById` now checks `isSuppressed()` per recipient **before** the `CampaignSend` ledger claim ("so a suppressed address leaves no phantom 'contacted' row") and reports a `suppressed` count; engine-v1's `sendCampaign` applies the same guard (checking after its claim and deleting the claim row so the address isn't counted as contacted). Both dispatch paths now honour suppressions; an admin can clear one at `app/api/admin/system/email/[email]/unsuppress`.

- **2026-08-04** — Cleaner photo upload: the ACTUAL root cause. The B1 pause-revalidation listener made the job workspace re-run its full `load()` on every `visibilitychange`/`focus`, and `load()` opened with `setLoading(true)` — swapping the workspace to the loading skeleton and **unmounting the file input**. On a phone the picker always hides the tab, so returning with a photo fired this instantly: the change event had no input left to land on. Seen as "quick flash, nothing uploads"; desktop file dialogs don't hide the tab, so it never reproduced locally; laundry has no such listener. Fixed: only the first load may blank the screen — refreshes update in place, the form stays mounted, the pick lands. Verified by simulating the hide→return→pick cycle against the real report form (input survived, upload 200, photo counted). The 2026-08-03 full-resolution-decode fix below remains a real memory fix, but this listener was the deterministic trigger.
